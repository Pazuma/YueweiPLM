# 数据库服务器 1 TB 数据盘迁移与回滚手册

适用主机：数据库服务器 `172.19.49.226`。已确认系统盘约 100 GB，目标盘分区为 `/dev/vdb2`、现有文件系统为 NTFS。目标是把 PostgreSQL、业务附件、1Panel 备份、Docker 和 containerd 的持久数据迁入 `/data`，并让数据盘未挂载时相关服务启动失败。

本手册中的格式化、快照回滚、删除旧副本和防火墙变更都属于高风险动作。执行前必须在当次维护窗口再次确认目标、快照状态和回滚点。

## 1. 不可违反的边界

- 必须先为 `/dev/vda` 与 `/dev/vdb` 分别创建阿里云快照，并等待控制台状态变为“已完成”。快照至少保留 14 天。
- 必须先完成全库压缩逻辑备份、角色权限备份、SHA-256 校验和 `pg_restore --list` 校验，并把副本放到另一台服务器。
- `/dev/vdb2` 格式化前必须只读挂载，导出文件清单、大小、时间和所有者信息；清单与云盘快照共同保留原 NTFS 内容。
- 不猜测 PostgreSQL 卷名、DockerRootDir、containerd root 或业务附件源路径；每个源路径都由本机只读命令确认并记录。
- `/etc/fstab` 不使用 `nofail`。数据盘缺失时 Docker、containerd 和 PostgreSQL 必须启动失败，禁止回写系统盘。
- 开放流量前失败可以恢复原配置或云盘快照；开放流量后失败必须停止写入并使用最新逻辑备份恢复，禁止直接回滚旧磁盘造成数据倒退。

## 2. 维护窗口前的只读基线

记录输出并保存到工单：

```bash
date -Is
lsblk -o NAME,SIZE,FSTYPE,LABEL,UUID,MOUNTPOINTS
findmnt --verify --verbose
df -hT
df -ih
docker info --format '{{.DockerRootDir}}'
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Mounts}}'
docker inspect 1Panel-postgresql-1o2G
systemctl show containerd -p FragmentPath -p DropInPaths
containerd config dump | grep -E '^[[:space:]]*(root|state)[[:space:]]='
du -xhd1 /opt/1panel /var/lib/docker /var/lib/containerd /datauser 2>/dev/null
```

从 `docker inspect` 记录 PostgreSQL 容器内数据路径和对应宿主机源路径。将实际源目录分别记录为：

- `PG_SOURCE`：现有 PostgreSQL 数据目录。
- `FILES_SOURCE`：现有业务附件目录。
- `BACKUP_SOURCE`：现有 1Panel 备份目录。
- `DOCKER_SOURCE`：`docker info` 返回的 DockerRootDir。
- `CONTAINERD_SOURCE`：containerd 配置中的持久 `root`；`state` 必须继续位于 `/run`。

## 3. 快照和 NTFS 内容清单

1. 在阿里云控制台分别为系统盘 `/dev/vda` 与数据盘 `/dev/vdb` 创建快照。记录快照 ID、创建时间和磁盘 ID，等待两个快照均为“已完成”。
2. 在系统内只读挂载 NTFS 分区；`norecover` 防止回放 NTFS 日志：

   ```bash
   mkdir -p /mnt/vdb2-readonly /root/storage-migration-evidence-20260817
   mount -t ntfs3 -o ro,norecover /dev/vdb2 /mnt/vdb2-readonly
   find /mnt/vdb2-readonly -xdev -printf '%y\t%u\t%g\t%s\t%TY-%Tm-%TdT%TH:%TM:%TS\t%p\n' \
     > /root/storage-migration-evidence-20260817/vdb2-ntfs-files.tsv
   du -xah /mnt/vdb2-readonly \
     > /root/storage-migration-evidence-20260817/vdb2-ntfs-sizes.txt
   sync
   umount /mnt/vdb2-readonly
   ```

3. 校验清单非空，并复制到应用服务器和离线运维目录。没有完成快照与清单时不得继续。

## 4. 停止写入和冷关闭

维护窗口开始后先从反向代理摘除业务流量，再停止所有业务容器。不要直接停止 Docker 来代替数据库正常关闭。

```bash
docker ps --format '{{.Names}}'
docker stop -t 120 1Panel-postgresql-1o2G
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' 1Panel-postgresql-1o2G
# 按基线清单逐个停止其余业务容器，并验证全部退出。
docker ps
systemctl stop docker.service
systemctl stop containerd.service
systemctl is-active docker.service containerd.service
```

确认 PostgreSQL 日志是正常 fast shutdown/complete，而不是被 kill。若任何业务仍在写入，停止迁移并恢复维护窗口控制。

## 5. 重建 `/dev/vdb2` 为 ext4

下面命令会永久删除 `/dev/vdb2` 的 NTFS 内容，只能在当次再次确认磁盘、快照和清单后执行：

```bash
findmnt /dev/vdb2
wipefs -n /dev/vdb2
umount /dev/vdb2 2>/dev/null || true
wipefs -a /dev/vdb2
mkfs.ext4 -L dbdata /dev/vdb2
mkdir -p /mnt/dbdata
mount /dev/vdb2 /mnt/dbdata
```

建立目标布局：

```bash
install -d -m 0750 /mnt/dbdata/services/postgresql
install -d -m 0750 /mnt/dbdata/datauser/files
install -d -m 0750 /mnt/dbdata/backups/1panel
install -d -m 0710 /mnt/dbdata/runtime/docker
install -d -m 0710 /mnt/dbdata/runtime/containerd
```

## 6. 冷迁移与校验

用第 2 节记录的真实源路径替换下列变量。`rsync -aHAX --numeric-ids` 保留权限、所有者、硬链接、ACL 与扩展属性。

```bash
rsync -aHAX --numeric-ids --info=progress2 "$PG_SOURCE"/ /mnt/dbdata/services/postgresql/
rsync -aHAX --numeric-ids --info=progress2 "$FILES_SOURCE"/ /mnt/dbdata/datauser/files/
rsync -aHAX --numeric-ids --info=progress2 "$BACKUP_SOURCE"/ /mnt/dbdata/backups/1panel/
rsync -aHAX --numeric-ids --info=progress2 "$DOCKER_SOURCE"/ /mnt/dbdata/runtime/docker/
rsync -aHAX --numeric-ids --info=progress2 "$CONTAINERD_SOURCE"/ /mnt/dbdata/runtime/containerd/
sync
```

对每一组源/目标记录文件数、字节数和抽样校验：

```bash
du -sx --bytes "$PG_SOURCE" /mnt/dbdata/services/postgresql
find "$PG_SOURCE" -xdev -type f | wc -l
find /mnt/dbdata/services/postgresql -xdev -type f | wc -l
rsync -aHAX --numeric-ids --dry-run --delete "$PG_SOURCE"/ /mnt/dbdata/services/postgresql/
```

其余四组目录执行同样校验。对数据库、附件和备份各抽取至少 20 个文件执行 SHA-256 对比；任何差异都必须查明，不能靠再次启动服务掩盖。

## 7. 固定 UUID 挂载并设置服务依赖

记录新 UUID，然后写入 `/etc/fstab`：

```bash
blkid /dev/vdb2
```

`/etc/fstab` 使用实际 UUID，条目形式如下；不得加入 `nofail`：

```fstab
UUID=<实际-ext4-UUID> /data ext4 defaults,noatime 0 2
```

切换临时挂载：

```bash
umount /mnt/dbdata
mkdir -p /data
mount /data
findmnt -no SOURCE,FSTYPE,OPTIONS /data
```

安装仓库中的 systemd drop-in：

```bash
install -D -m 0644 deploy/systemd/docker.service.d/10-require-data.conf \
  /etc/systemd/system/docker.service.d/10-require-data.conf
install -D -m 0644 deploy/systemd/containerd.service.d/10-require-data.conf \
  /etc/systemd/system/containerd.service.d/10-require-data.conf
systemctl daemon-reload
```

drop-in 同时使用 `RequiresMountsFor=/data` 和 `mountpoint -q /data`；数据盘未挂载时服务会失败。

## 8. Docker、containerd 和 PostgreSQL 配置

1. 合并而不是覆盖现有 `/etc/docker/daemon.json`，确保最终包含：

   ```json
   {
     "data-root": "/data/runtime/docker"
   }
   ```

2. 合并现有 `/etc/containerd/config.toml`：

   ```toml
   root = "/data/runtime/containerd"
   state = "/run/containerd"
   ```

3. 在 1Panel 持久 Compose 配置中，把 PostgreSQL 原 named volume 的宿主机来源改成 `/data/services/postgresql`，但保持 `docker inspect` 记录的容器内目标路径不变（通常为 `/var/lib/postgresql/data`）。使用 long syntax bind mount，并设置 `create_host_path: false`，避免 `/data` 缺失时创建系统盘目录。修改前备份 1Panel 配置；修改后执行 `docker compose config` 静态校验。
   同时把 `POSTGRES_IMAGE` 显式设置为维护前 `docker inspect` 记录的同一 PostgreSQL major 版本；冷迁移 PGDATA 不是版本升级，禁止让新镜像直接读取不同 major 的数据目录。需要升级 major 时必须另开变更，通过 `pg_upgrade` 或逻辑备份恢复演练执行。
4. 将业务附件和 1Panel 备份配置分别指向 `/data/datauser/files` 与 `/data/backups/1panel`。禁止用软链接掩盖未挂载的数据盘。

## 9. 启动、业务验证和整机重启

```bash
systemctl start containerd.service
systemctl start docker.service
docker info --format '{{.DockerRootDir}}'
containerd config dump | grep -E '^[[:space:]]*(root|state)[[:space:]]='
docker compose -f <1Panel-PostgreSQL-Compose路径> config -q
docker compose -f <1Panel-PostgreSQL-Compose路径> up -d
```

开放流量前必须全部满足：

- `findmnt` 显示 `/data` 来自 `/dev/vdb2` 的 ext4 UUID。
- 对 PostgreSQL 数据目录、附件、备份、DockerRootDir 和 containerd root 执行 `df -hT`，全部落在 1 TB 数据盘。
- PostgreSQL 为 healthy；全库可连接，`plm.plm_product` 与 `plm.flyway_schema_history` 存在，`public` 原有对象未删除。
- 使用迁移前逻辑备份在隔离库完成一次恢复演练。
- PLM 登录、核心查询和受控写入通过。

随后执行一次整机重启演练：

```bash
reboot
```

重启后重新执行本节所有挂载、路径、数据库、容器与业务检查。数据盘缺失演练应在无业务流量的受控环境完成，预期 Docker/containerd 启动失败而不是写入系统盘。

## 10. 监控、容量和安全收口

- 启用 `sysstat` 定时采样，并确认 `/var/log/sa/sa$(date +%d)` 当天文件持续增长。
- 告警：容器 5 分钟重启超过 3 次；CPU 连续 5 分钟超过 80%；系统盘和数据盘 75% 预警、85% 严重；inode 低水位；PostgreSQL 不可用；`/data` 未挂载；备份失败。
- 私网验证完成后，安全组和主机防火墙只允许应用服务器 `172.19.49.227` 访问 PostgreSQL `172.19.49.226:5432`；关闭 Redis、MySQL、Kafka 等不必要公网入口。
- 单独核查阿里云中危告警和 `/.1panel_clash`，确认归属前不删除。
- 最终系统盘使用率应低于 50%，数据盘低于 70%。

## 11. 回滚和旧副本清理

- 开放流量前失败：停止服务，恢复原配置；必要时按快照恢复 `/dev/vda`、`/dev/vdb`，并重新核验所有挂载与数据库。
- 开放流量后失败：立即停止写入，使用最新逻辑备份和最新附件副本恢复；不得回滚到旧云盘快照造成业务数据倒退。
- 系统盘旧数据副本只在整机重启、恢复演练、监控和业务连续稳定后删除。删除前再次记录确切路径、大小和挂载来源，并取得当次确认。
- 快照和异机逻辑备份至少保留 14 天；确认新备份周期和告警均正常后再清理。
