# 两台生产服务器钉钉告警设计

日期：2026-08-18

## 目标

在不购买额外监控服务、不重启业务容器的前提下，为应用服务器和数据库服务器部署轻量级本地监控。告警通过现有企业钉钉机器人单独发送给数据库中唯一匹配的“施鸣坤”用户，故障恢复时发送恢复通知。

## 非目标

- 不接入付费云监控、短信、OSS 或新的外部服务。
- 不调整业务容器、数据库结构、Nginx 或公网端口。
- 不在代码、日志、journal 或告警正文中记录 webhook、应用密钥、完整钉钉用户 ID 或数据库密码。
- 不自动重启容器、数据库或服务器；监控仅检测和通知。

## 架构

每台服务器独立运行一个 root 权限的 systemd oneshot 检查服务，由同名 timer 每 5 分钟触发。检查脚本只读取本机指标和容器状态，把当前状态写入 `/var/lib/local-infra-alert/state`，把运行日志写入 systemd journal。

两台服务器使用同一个现有企业钉钉机器人，通过钉钉单聊 API 按 userId 向“施鸣坤”发送 Markdown 消息。机器人凭据和接收人 ID 分别保存在两台服务器的 root-only 环境文件中，目录权限为 0700，文件权限为 0600。

## 检查项与阈值

### CPU

- 每 5 分钟计算最近一个完整 5 分钟窗口的平均 CPU 使用率。
- 平均使用率大于或等于 80% 时进入告警状态。
- 平均使用率连续降到 70% 以下时发送恢复通知。
- 优先读取 sysstat/sar；不可用时使用 `/proc/stat` 的短采样作为降级方案，并在日志中标明数据来源。

### 磁盘、inode 与数据盘挂载

- 对 `/` 和 `/data` 检查容量与 inode。
- 使用率大于或等于 75% 为预警，大于或等于 85% 为严重告警。
- 容量恢复到 70% 以下、inode 恢复到 70% 以下时发送恢复通知。
- `/data` 必须是独立挂载点、文件系统为 ext4，并且块设备 UUID 与部署时记录的基线一致；任一条件不满足立即告警。

### Docker 容器

- 检查 Docker daemon 是否可用。
- 检查所有当前运行容器的 `unhealthy`、`restarting` 状态。
- 对部署时记录的核心容器清单检查意外退出或缺失。
- 保存每个容器的 RestartCount；相邻两个 5 分钟窗口增量大于 3 次时告警。
- 状态恢复为 running/healthy 且重启不再增长时发送恢复通知。

### 核心服务

- 应用服务器：PLM 数据库健康接口、PLM Web、FIFO，以及本机 Docker。
- 数据库服务器：PostgreSQL、MySQL、RAG 后端，以及本机 Docker。
- HTTP 健康检查要求连接成功且返回预期状态；数据库使用容器内现有健康命令或只读 readiness 检查，不在脚本中保存数据库密码。
- 单次超时不超过 5 秒，避免一个故障检查拖住整个 timer。

## 状态、去重与恢复

- 每个检查项以稳定 key 保存 `OK`、`WARNING` 或 `CRITICAL` 状态。
- 仅在状态发生变化时立即发送告警或恢复通知。
- 未恢复的 WARNING/CRITICAL 每 6 小时最多提醒一次。
- 通知失败时保留待发送状态，下一个 5 分钟窗口重试；监控检查本身不因钉钉失败而中断。
- 告警正文包括服务器角色、主机名、发生时间、检查项、当前值、阈值和简短处理提示，不包含密钥或个人数据。

## 安全与变更控制

- 钉钉接收人从 `dingtalk_oa.ding_user_snapshot` 只读查询，必须满足姓名“施鸣坤”当前有效记录、userId 和企业均唯一；部署记录只保存校验结果和 ID 指纹，不输出完整 ID。
- 从现有配置复制机器人凭据时不经过终端输出，目标文件严格限制为 root 可读。
- systemd 服务启用 `NoNewPrivileges`、`PrivateTmp`、只读系统保护，并只开放状态目录的写权限。
- systemd 服务设置 `MemoryMax=128M`、`CPUQuota=10%`、`TasksMax=32`、低 I/O 优先级和 120 秒超时；检查脚本不是常驻进程，每次执行完成即退出。
- 部署前保存现有 systemd 单元清单；卸载时停止并禁用 timer，删除新单元和状态目录即可，不触碰业务配置。

## 验证

1. 在不启用 timer 的情况下运行脚本自检，确认所有当前健康项返回 OK。
2. 使用测试模式模拟 CPU、磁盘、掉挂载、容器重启和数据库不可用，验证状态转换、去重和恢复逻辑。
3. 向“施鸣坤”发送一条标记为测试的单聊消息，并验证钉钉 API 返回成功且接收人不是群聊。
4. 启用两台服务器的 timer，确认 `OnCalendar` 为 5 分钟周期、随机延迟受控、下一次触发时间正确。
5. 等待至少一个真实周期，确认服务退出码为 0、journal 无密钥、当前业务容器没有重启。

## 验收标准

- 两台服务器每 5 分钟各执行一次检查，单次运行不重叠。
- 当前健康状态下不发送重复通知。
- 模拟故障只向“施鸣坤”发送一次告警，模拟恢复发送一次恢复通知。
- 机器人或网络故障不会阻塞后续检查，恢复后能够重试通知。
- PLM、FIFO、RAG、PostgreSQL、MySQL 和全部现有业务容器在部署期间保持运行，RestartCount 不增加。
