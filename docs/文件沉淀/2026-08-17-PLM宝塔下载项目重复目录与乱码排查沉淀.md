# 2026-08-17 PLM 宝塔下载项目重复目录与乱码排查沉淀

## 背景

从宝塔面板下载线上项目后，本地曾出现项目目录重复嵌套、压缩包不可打开、IDE 打开的文件与实际构建目录不一致等现象。为了避免后续部署、排查和代码修改时误判，本次对当前工作区重新审查并沉淀统一判断口径。

本次审查目录：

```text
D:\work\Yuewei-plm
```

## 当前结论

当前主项目根目录应以 `D:\work\Yuewei-plm` 为准。

主项目目录下存在正常的核心模块：

```text
plm-web
plm-server
plm-database
docs
scripts
docker-compose.yml
docker-compose.baota.yml
.env
```

重复项目的大部分内容已经移除，但仍残留一个 `Yuewei` 目录：

```text
Yuewei/plm-web/src/api/request.ts
```

该目录已经不是完整重复项目，因为 `Yuewei/.git` 不存在，并且 `rg --files Yuewei` 只发现 1 个文件。后续应继续把它视为残留误放目录，避免 IDE 继续打开 `Yuewei/...` 下的文件。

## 发现的问题

### 1. IDE 仍可能打开残留路径

当前 IDE 打开的路径曾是：

```text
Yuewei/plm-web/src/api/request.ts
```

但实际应编辑和构建的文件是：

```text
plm-web/src/api/request.ts
```

如果继续打开 `Yuewei/...`，会出现“改了代码但页面或 Docker 构建不生效”的错觉。

### 2. 前端请求文件实际编码正常

主项目的 `plm-web/src/api/request.ts` 中，业务逻辑本身结构正常：

- `baseURL` 使用 `VITE_API_BASE_URL`，为空时走同源 `/api/v1`
- 请求头自动追加 `Authorization`
- 请求头自动追加 `X-Request-Id`
- `FormData` 自动移除 `Content-Type`
- 401 或业务码 `40101` 会清理 token 并跳转登录页

排查过程中，PowerShell 直接输出文件内容时曾显示出类似乱码：

```text
缃戠粶璇锋眰澶辫触
鎺ュ彛璇锋眰澶辫触
```

但使用 UTF-8 读取并按 Unicode 码点检查后，确认文件实际包含的是正确中文：

```text
网络请求失败
接口请求失败
```

因此这里不是源码损坏，而是终端显示编码不一致导致的误判。该文件暂不需要因为这两个文案做修复。

### 3. nginx 配置注释实际编码正常

`plm-web/nginx.conf` 中 SPA fallback 注释在 PowerShell 输出时曾显示出类似：

```text
鈥?serve index.html
```

但按 UTF-8 读取后确认文件实际包含的是正常 em dash，且没有 Unicode replacement character。该问题同样属于显示层编码误判，不影响 nginx 运行。

### 4. `.env` 包含生产连接信息

根目录 `.env` 中包含数据库连接地址、用户名、密码、Web 端口等部署参数。该文件可以用于本地复现宝塔部署环境，但不应提交、外发或打包进公共归档。

后续文档和日志中引用 `.env` 时，只记录字段名，不记录真实密码。

## 当前配置判断

### Docker Compose

当前 `docker-compose.yml` 是偏宝塔生产部署的版本：

- 只声明 `redis`、`server`、`web`
- 不内置 `postgres`
- 后端数据库通过 `.env` 中的 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD` 注入
- 前端默认映射端口为 `WEB_PORT`，未设置时为 `8111`

`docker-compose.baota.yml` 与主 compose 基本一致，但默认 Web 端口为 `8110`。实际部署时应确认宝塔站点、反向代理和 compose 使用的是同一个端口。

### 前端生产环境

`plm-web/.env.production` 当前配置：

```text
VITE_API_BASE_URL=
```

该配置表示前端请求会走同源路径：

```text
/api/v1
```

再由容器内 nginx 的 `/api/` 反向代理到：

```text
http://plm-server:8080
```

这套配置适合 `web` 和 `server` 同在 Docker compose 网络内的部署方式。

## 宝塔下载项目后的排查清单

### 1. 先确认压缩包是否有效

下载后先检查压缩包内容：

```powershell
tar -tzf "D:\Users\46733\Downloads\Yuewei-plm_xxx.tar.gz"
```

如果无法列出内容，优先怀疑下载中断、宝塔在线打包失败或下载到错误页面。

### 2. 再确认是否多套项目嵌套

在项目根目录执行：

```powershell
Get-ChildItem -Force
rg --files -g "request.ts" -g "docker-compose.yml" -g "package.json" -g ".env*"
```

如果同时出现：

```text
plm-web/...
Yuewei/plm-web/...
```

说明项目被解压到了已有项目内部，必须先确认唯一根目录。

### 3. 确认是否还有嵌套 Git 仓库

```powershell
Test-Path Yuewei\.git
```

如果返回 `True`，说明 `Yuewei` 仍是一套完整项目，不要混用两边文件。

如果返回 `False`，再查残留文件数量：

```powershell
rg --files Yuewei
```

只剩少量文件时，可以把它作为残留目录处理。

### 4. 确认 IDE 打开的文件是否属于主项目

正确路径应类似：

```text
D:\work\Yuewei-plm\plm-web\src\api\request.ts
```

需要避免打开：

```text
D:\work\Yuewei-plm\Yuewei\plm-web\src\api\request.ts
```

### 5. 确认前端请求链路

当前推荐链路：

```text
浏览器 -> web 容器 nginx -> /api/ -> plm-server:8080 -> 后端 /api/v1
```

对应配置：

```text
plm-web/.env.production: VITE_API_BASE_URL=
plm-web/src/api/request.ts: baseURL = /api/v1
plm-web/nginx.conf: location /api/ proxy_pass http://plm-server:8080
```

## 后续处理建议

1. IDE 工作区统一打开 `D:\work\Yuewei-plm`，不要打开 `D:\work\Yuewei-plm\Yuewei`。
2. 后续修复代码时，应修复主项目下的 `plm-web/src/api/request.ts`，不要修复残留目录。
3. 若希望减少 Windows PowerShell 显示误判，可把 `nginx.conf` 注释中的 em dash 换成 ASCII 连字符，但这不是运行问题。
4. 删除残留 `Yuewei` 目录前，先确认其中唯一文件没有未迁移内容。
5. 宝塔再次下载项目时，建议使用服务器命令行打包并用 SFTP 下载，同时对比文件大小或哈希。
6. `.env` 中生产连接信息只保留在部署环境，不进入公开文档、截图或提交记录。

## 本次审查结论

重复项目问题已经从“完整嵌套项目”降级为“残留目录单文件”。当前真正需要关注的是：

- 主项目中文兜底文案是否被终端显示误判为乱码

在这些点确认后，项目结构本身已经恢复到可继续开发和部署排查的状态。
