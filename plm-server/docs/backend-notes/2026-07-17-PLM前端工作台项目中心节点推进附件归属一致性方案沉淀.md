# 2026-07-17 PLM 前端工作台项目中心节点推进附件归属一致性方案沉淀

## 0. 本次范围声明

本次只生成方案沉淀文档，不修改任何实际业务代码。

本次只涉及前端，不涉及后端 Controller、Service、数据库、迁移脚本、状态机和接口实现。文档中的代码均为后续实施草稿，用于评审和二次开发。

## 1. 问题现象

用户在前端整体测试中反馈：

1. 工作台点击“确认当前节点”后，看起来没有推进到下一步节点。
2. 上传文件时选择了节点，但上传结束后没有显示到对应节点那里。
3. 工作台弹窗中的进度与项目中心详情里的项目流程不一致。

截图表现：

- 工作台弹窗显示项目已到“第 7 步：测试模具”，且第 5、6、7 步在同一个大节点区域内展示。
- 工作台中“第 6 步：制作模具”仍显示“待上传”，但“第 7 步：测试模具”显示“已上传 3 个”。
- 项目中心详情却显示“立项确认”大节点仍为“待开始”，第 1、2 步也都是“待开始”。

这会导致用户无法判断：

- 当前到底进行到哪一个小节点。
- 当前点击确认后是否真的推进。
- 上传的文件属于哪一个小节点。
- 工作台与项目中心哪一个视图可信。

## 3. 前端现状分析

### 3.1 工作台问题点

对应文件：

```text
D:\Yuewei\git\YUEWEI\plm-web\src\views\dashboard\DashboardView.vue
```

当前关键逻辑：

```ts
const dashboardProgressNodes = computed<DashboardProgressNode[]>(() => {
  if (activeProgressTimeline.value?.nodes?.length) {
    return activeProgressTimeline.value.nodes.map(toDashboardProgressNode)
  }
  ...

```

问题：

1. 工作台把后端 `timeline.nodes` 每个节点映射成前端 `DashboardProgressNode`。
2. 同时又尝试把一个节点展示成“大节点 + 包含的小节点”。
3. 如果后端返回的是小节点列表，而前端又按本地模板拼大节点，就会出现“大节点、小节点、当前节点”混用。
4. 附件数量使用 `node.documentCount`，没有建立 `stepNo/nodeKey -> documentCount` 的全局索引。

当前附件数量逻辑：

```ts
function getStepUploadCount(step: DashboardChildStep, node: DashboardProgressNode) {
  if (!step.requireUpload) return 0
  if (step.stepNo !== currentProgressStepNo.value) return 0
  return Number(node.documentCount || 0)
}
```

问题：

- 只有当前小步骤才可能显示附件数量。
- 已上传到第 6 步的文件，在当前走到第 7 步后，前端可能显示为“待上传”。
- 用户看到的“待上传”不一定代表后端没有文件，而是前端没有按小节点聚合附件数量。

### 3.3 项目中心问题点

对应文件：

```text
D:\Yuewei\git\YUEWEI\plm-web\src\views\project\ProjectCenterView.vue
```

当前项目详情打开逻辑仍混合两套数据：

```ts
const presentation = await getProductPresentation(row.productId)
const timeline = await getProjectTimeline(row.productId)
```

问题：

1. `getProductPresentation` 属于旧的产品展示适配入口，不应再作为项目流程的主数据源。
2. 项目中心展示的流程基于 `detailPresentation.timeline`，而工作台展示的是 `activeProgressTimeline.nodes`。
3. 两边各自有 `mapTimelineToPresentationNodes`、`toDashboardProgressNode` 等映射逻辑，字段口径不一致。
4. 当旧展示数据为空、失败或未刷新时，项目中心可能仍显示“待开始”，而工作台已经显示到第 7 步。

## 4. 根因结论

前端根因不是“后端没有推进”，而是前端存在三类不一致：

1. **数据源不一致**  
   工作台以 `getProjectTimeline()` 为主，项目中心仍混用 `getProductPresentation()` 和 `getProjectTimeline()`。

2. **映射规则不一致**  
   工作台和项目中心各自维护流程节点映射，导致同一个后端节点在两个页面上显示不同阶段、不同状态。

3. **附件计数维度不一致**  
   上传文件绑定的是小节点 `nodeKey`，但页面显示时没有按小节点建立附件计数索引，只拿当前节点或当前大节点的 `documentCount`。

## 5. 目标效果

后续实施完成后，前端应达到：

1. 工作台和项目中心都以 `getProjectTimeline(projectId)` 作为项目流程唯一前端数据源。
2. 同一个项目在两个入口显示相同的：
   - 当前小节点编号。
   - 当前小节点名称。
   - 大节点/阶段名称。
   - 当前确认状态。
   - 附件数量。
   - 下一步动作。
3. 点击“确认当前节点”后：
   - 如果后端返回已进入下一小节点，前端立即显示下一小节点。
   - 如果后端只确认当前小节点但未推进，前端明确显示“已确认，等待进入下一步/资料门禁”。
4. 上传资料后：
   - 上传到哪个小节点，哪个小节点立即变绿。
   - 不因为当前节点变化导致历史已上传步骤显示为“待上传”。
5. 项目中心打开同一个项目时，和工作台弹窗看到的进度一致。

## 6. 推荐方案

### 6.1 方案 A：抽一个前端 Timeline Adapter（推荐）

新增统一适配器：

```text
D:\Yuewei\git\YUEWEI\plm-web\src\utils\timelineAdapter.ts
```

作用：

- 统一把 `TimelineDetailVO` 转为前端展示模型。
- 工作台和项目中心都调用同一个 adapter。
- 统一计算小节点状态、附件计数、当前节点、阶段分组。

优点：

- 一处改动，两个页面一致。
- 适合企业级维护。
- 后续后端字段变化时，只改 adapter。

缺点：

- 需要一次性梳理两个页面的数据结构。

### 6.2 方案 B：分别修工作台和项目中心

分别在两个页面修各自的映射逻辑。

优点：

- 短期改动少。

缺点：

- 后续仍容易再次不一致。
- 不符合企业级项目的统一适配层原则。

### 6.3 结论

推荐方案 A。

### 8.1 新增统一 Timeline Adapter

拟新增：

```ts
// src/utils/timelineAdapter.ts
import type { TimelineDetailVO, TimelineNodeVO } from '@/api/modules/project'

export interface TimelineStepView {
  nodeKey: string
  stepNo: number
  stepName: string
  stageCode?: string | null
  stageName?: string | null
  phaseName: string
  status: 'completed' | 'current' | 'pending' | 'rejected'
  confirmed: boolean
  documentCount: number
  requiredFileCategory?: string | null
  isCurrent: boolean
  isConfirmed: boolean
  hasUploaded: boolean
  visualStatus: 'confirmed' | 'current' | 'uploaded' | 'missing-upload' | 'pending' | 'rejected'
}

export interface TimelineStageView {
  stageCode: string
  stageName: string
  phaseName: string
  status: 'completed' | 'current' | 'pending' | 'rejected'
  currentStepNo: number
  documentCount: number
  steps: TimelineStepView[]
}

function getStepVisualStatus(node: TimelineNodeVO, currentStepNo: number): TimelineStepView['visualStatus'] {
  const confirmed = Boolean(node.confirmed) || node.stepNo < currentStepNo || node.status === 'completed'
  const uploaded = Number(node.documentCount || 0) > 0

  if (node.status === 'rejected') return 'rejected'
  if (confirmed) return 'confirmed'
  if (node.status === 'current') return uploaded ? 'current' : 'missing-upload'
  if (uploaded) return 'uploaded'
  return 'pending'
}

export function mapTimelineSteps(timeline: TimelineDetailVO): TimelineStepView[] {
  const currentStepNo = Number(timeline.currentStepNo || 1)

  return timeline.nodes.map((node) => {
    const documentCount = Number(node.documentCount || 0)
    const isCurrent = node.stepNo === currentStepNo || node.status === 'current'
    const isConfirmed = Boolean(node.confirmed) || node.stepNo < currentStepNo || node.status === 'completed'

    return {
      nodeKey: node.nodeKey,
      stepNo: node.stepNo,
      stepName: node.nodeName,
      stageCode: node.stageCode,
      stageName: node.stageName,
      phaseName: node.phaseName,
      status: node.status,
      confirmed: Boolean(node.confirmed),
      documentCount,
      requiredFileCategory: node.requiredFileCategory,
      isCurrent,
      isConfirmed,
      hasUploaded: documentCount > 0,
      visualStatus: getStepVisualStatus(node, currentStepNo)
    }
  })
}

export function mapTimelineStages(timeline: TimelineDetailVO): TimelineStageView[] {
  const steps = mapTimelineSteps(timeline)
  const groups = new Map<string, TimelineStepView[]>()

  steps.forEach((step) => {
    const key = step.stageCode || step.nodeKey
    groups.set(key, [...(groups.get(key) || []), step])
  })

  return Array.from(groups.entries()).map(([stageCode, groupSteps]) => {
    const current = groupSteps.find((step) => step.isCurrent)
    const rejected = groupSteps.some((step) => step.status === 'rejected')
    const allCompleted = groupSteps.every((step) => step.isConfirmed)

    return {
      stageCode,
      stageName: current?.stageName || groupSteps[0]?.stageName || groupSteps[0]?.stepName || stageCode,
      phaseName: current?.phaseName || groupSteps[0]?.phaseName || '',
      status: rejected ? 'rejected' : current ? 'current' : allCompleted ? 'completed' : 'pending',
      currentStepNo: timeline.currentStepNo,
      documentCount: groupSteps.reduce((sum, step) => sum + step.documentCount, 0),
      steps: groupSteps
    }
  })
}

export function findCurrentTimelineStep(timeline: TimelineDetailVO): TimelineStepView | null {
  return mapTimelineSteps(timeline).find((step) => step.isCurrent) || null
}
```

## 9. 修改内容说明

### 9.1 工作台

修改内容：

- 删除工作台内部独立计算步骤状态的逻辑。
- 改为使用 `timelineAdapter`。
- 上传成功后定位到上传的小节点。

- 项目中心显示的当前大节点、小节点、确认状态与工作台一致。

目标效果：

- 用户知道文件上传到了哪一步。

## 11. 风险点

1. 如果后端 `TimelineDetailVO.nodes` 没有返回全部小节点，只返回当前节点，则前端无法完整显示大节点内所有小节点。
2. 如果后端 `documentCount` 只统计当前节点，历史步骤仍无法显示真实附件数量。
3. 如果附件上传返回值没有 `timelineStageCode/timelineStepCode/timelineStepName`，前端只能通过上传时选择的 `nodeKey` 临时定位。
4. 本次方案不改后端，因此以上字段如果后端缺失，需要后续由后端补齐。

## 12. 后续维护建议
