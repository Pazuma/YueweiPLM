# PLM 通过前端测试 M0/M1/M2 后端验收步骤

日期：2026-07-10

## 1. 文档目标

本文用于本地联调时，通过 `plm-web` 前端页面验证 `plm-server` 后端 M0、M1、M2 的核心链路。

重点说明三件事：

- 怎么测：按什么顺序启动、登录、进入页面、观察接口和页面。
- 为什么测：每一步覆盖哪个后端能力。
- 怎样算通过：页面效果、接口响应、错误状态分别应该是什么。

## 2. 测试范围

### 2.1 M0 覆盖范围

M0 主要是后端底座、健康检查、数据库连通、产品主数据基础能力。

通过前端测试时，M0 分两类确认：

- 直接确认：后端健康接口、数据库健康接口必须正常。
- 间接确认：M2 的项目列表、工作台数据当前来自 Product-as-project，也就是后端把 `plm_product` 作为项目视图返回。因此只要前端能看到项目数据，并且字段如 `productId`、`productType`、`status` 正常，说明 M0 产品基础数据也被后端正常读取。

如果当前前端没有单独的“产品主数据 / Product”页面，则 M0 的产品创建、编辑、冻结、发布不强制通过前端页面验收，可用 Apifox 或数据库导入数据补充验证。

### 2.2 M1 覆盖范围

M1 通过前端主要验证：

- 登录。
- 当前用户恢复。
- token 携带。
- 未登录拦截。
- 退出登录。
- 操作日志可通过后端接口记录，前端当前主要间接覆盖登录、退出和带 token 请求。

### 2.3 M2 覆盖范围

M2 通过前端主要验证：

- 工作台进行中项目。
- 项目中心列表。
- 项目详情。
- 项目时间轴查询。
- `productType` 数据筛选结果是否能在页面或接口请求中体现。

## 3. 前置条件

### 3.1 Docker Desktop 已启动

原因：本地 PostgreSQL 跑在 Docker 容器里。Docker daemon 没启动时，后端无法连接数据库。

命令：

```powershell

```

通过标准：

- 能正常显示容器列表。
- 不出现以下错误：

```text
failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine
```

如果 Docker 没启动，先执行：

```powershell
Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"
```

等待 Docker Desktop 显示 Running 后再继续。

### 3.2 PostgreSQL 容器已启动

命令：

```powershell
docker start c641b26339ec_plm-postgres
docker ps
```

数据库连通检查：

```powershell
docker exec c641b26339ec_plm-postgres psql -U plm -d plm -c "select 1;"
```

通过标准：

- `docker ps` 能看到 `plm-postgres` 容器。
- `select 1;` 返回 `1`。

命令：

## 4. 测试前清理浏览器状态

在浏览器 F12 Console 执行：

```javascript
localStorage.removeItem('plm_token')
location.href = '/#/login'
```

原因：旧 token 可能来自上一次后端进程。当前后端 token 是内存态，后端重启后旧 token 会失效，容易导致刷新后 401 或白屏误判。

通过标准：

- 页面回到登录页。
- Application / Local Storage 中没有 `plm_token`。

## 5. M1 前端测试步骤

### 5.1 登录成功

页面操作：

1. 打开 `http://localhost:5174/#/login`。
2. 输入账号 `engineer01`。
3. 输入密码 `plm123456`。
4. 点击登录。

原因：验证 M1 的 `POST /api/v1/auth/login`、密码校验、token 生成、前端保存 token。

通过标准：

- 页面跳转到首页或工作台。
- Network 中 `POST /api/v1/auth/login` 返回 HTTP 200。
- 响应 `code=0`。
- 响应 `data.token` 有值。
- Local Storage 中出现 `plm_token`。

失败判断：

- HTTP 401：账号或密码错误，或初始化用户数据未导入。
- HTTP 500：看后端日志，不要当成前端问题。

### 5.2 当前用户恢复

页面操作：

1. 登录成功后刷新页面。
2. 观察是否仍保持登录状态。

原因：验证前端会带 `Authorization: Bearer <token>` 请求 `GET /api/v1/auth/profile`，后端能从 token 恢复当前用户。

通过标准：

- 刷新后不跳回登录页。
- Network 中 `GET /api/v1/auth/profile` 返回 HTTP 200。
- 响应 `code=0`。
- 页面顶部或用户区域能显示当前用户信息。

失败判断：

- HTTP 401：token 失效，清理 `plm_token` 后重新登录。
- 页面空白：打开 Console 看是否有 profile 401 未被路由守卫处理。

### 5.3 未登录拦截

页面操作：

1. 执行：

```javascript
localStorage.removeItem('plm_token')
location.href = '/#/'
```

2. 尝试进入首页或项目页面。

原因：验证没有 token 时，前端不会放行到业务页面，后端也会拒绝受保护接口。

通过标准：

- 页面回到登录页。
- 受保护接口如果被请求，后端返回 HTTP 401。
- 响应业务码为 `40101`。

### 5.4 退出登录

页面操作：

1. 登录成功。
2. 点击右上角退出登录。
3. 刷新页面。

原因：验证 M1 的 `POST /api/v1/auth/logout` 和前端清理登录态。

通过标准：

- Network 中 `POST /api/v1/auth/logout` 返回 HTTP 200。
- 响应 `code=0`。
- Local Storage 中 `plm_token` 被清除。
- 刷新后仍停留在登录页。

## 6. M2 前端测试步骤

### 6.1 工作台进行中项目

页面操作：

1. 登录。
2. 进入首页 / 工作台。
3. 查看进行中项目区域。

原因：验证 M2 的 `GET /api/v1/workbench/projects/in-progress`。

通过标准：

- Network 中出现 `GET /api/v1/workbench/projects/in-progress`。
- 返回 HTTP 200。
- 响应 `code=0`。
- 有数据时页面显示项目卡片或项目列表。
- 无数据时页面显示空状态，但不能报错或白屏。

数据字段通过标准：

- 每条数据至少能看到或在响应中确认：
  - `projectId`
  - `productId`
  - `productName`
  - `productType`
  - `status`
  - `currentStepNo`
  - `currentNodeName`

### 6.2 项目中心列表

页面操作：

1. 登录。
2. 进入项目中心 / 项目管理页面。
3. 查看项目列表。

原因：验证 M2 的 `GET /api/v1/projects`，并间接验证 M0 的 Product 数据能作为项目视图读取。

通过标准：

- Network 中出现 `GET /api/v1/projects`。
- 返回 HTTP 200。
- 响应 `code=0`。
- 页面列表数据与后端 `data.content` 数量和核心字段一致。
- `projectId` 与 `productId` 当前应保持一致，因为 M2 采用 Product-as-project。

无数据通过标准：

- 响应 `code=0`。
- `data.content=[]`。
- 页面显示空状态，不显示假 mock 数据。

### 6.3 项目详情

页面操作：

1. 在项目中心点击任意项目。
2. 打开详情或详情弹窗。

原因：验证 M2 的项目详情查询，接口通常为：

```text
GET /api/v1/projects/{projectId}
GET /api/v1/projects/{projectId}/summary
```

通过标准：

- Network 中至少出现详情或摘要接口。
- 返回 HTTP 200。
- 响应 `code=0`。
- 页面展示的项目名称、产品类型、状态、负责人、当前节点与响应一致。

失败判断：

- HTTP 404 或业务码 `40401`：项目不存在，检查点击的 `projectId` 是否存在。
- HTTP 500：优先检查数据库字段是否补齐，例如 `current_step_no`、`timeline_*` 字段。

### 6.4 项目时间轴

页面操作：

1. 打开任意项目详情。
2. 查看时间轴区域。

原因：验证 M2 的 `GET /api/v1/projects/{projectId}/timeline`。

通过标准：

- Network 中出现 `GET /api/v1/projects/{projectId}/timeline`。
- 返回 HTTP 200。
- 响应 `code=0`。
- `data.nodes.length=6`。
- 只有一个节点状态为 `current`。
- 当前节点之前为 `completed`，之后为 `pending`。
- 页面能按节点状态渲染时间轴。

### 6.5 productType 筛选

页面操作：

1. 如果页面有产品类型筛选，分别选择产品线和型号线。
2. 观察列表变化。
3. 打开 F12 Network 查看请求参数。

原因：验证 M2 的 `productType` 筛选参数。

通过标准：

- 请求中带有 `productType=product_line` 或 `productType=model_variant`。
- 返回 `code=0`。
- 有数据时，返回内容全部符合所选 `productType`。
- 无数据时，返回 `content=[]`，页面显示空状态。

如果当前前端页面没有筛选控件：

- 不判定前端失败。
- 可在 Network 或 Apifox 单独验证：

```text
GET http://localhost:8080/api/v1/projects?page=1&size=20&productType=product_line
GET http://localhost:8080/api/v1/workbench/projects/in-progress?page=1&size=20&productType=model_variant
```

## 7. M0 前端测试步骤

### 7.1 健康检查

操作：

```powershell
Invoke-RestMethod http://localhost:8080/api/v1/health
Invoke-RestMethod http://localhost:8080/api/v1/health/db
```

原因：前端页面能不能正常调后端，前提是后端和数据库都健康。

通过标准：

- 两个接口均返回 HTTP 200。
- `code=0`。
- 数据库状态为 `UP`。

### 7.2 产品数据间接验证

页面操作：

1. 登录前端。
2. 进入工作台或项目中心。
3. 查看项目列表中是否有你导入的产品数据。

原因：M2 当前把 `plm_product` 映射为项目视图。只要项目列表能看到导入的产品，就说明 M0 的产品主数据可被后端读取，并且能流转到前端展示。

通过标准：

- 导入的产品名称能在项目中心或工作台中出现。
- 响应中 `productId` 有值。
- 响应中 `productType` 正确，例如 `product_line` 或 `model_variant`。
- 响应中 `status` 正确。

### 7.3 产品页面直接验证

如果当前前端存在“产品主数据 / 产品中心”页面，可按以下方式测：

1. 进入产品页面。
2. 查看产品列表。
3. 新建一条测试产品。
4. 打开产品详情。
5. 如页面支持，测试编辑、冻结、发布。

原因：这是 M0 产品接口的直接前端验证。

通过标准：

- 列表请求命中 `GET /api/v1/products`。
- 新建请求命中 `POST /api/v1/products`。
- 详情请求命中 `GET /api/v1/products/{id}`。
- 冻结请求命中 `POST /api/v1/products/{id}/freeze`。
- 发布请求命中 `POST /api/v1/products/{id}/publish`。
- 每个成功请求都返回 `code=0`。
- 页面刷新后数据仍存在。

如果当前前端没有这些入口，则本节不作为前端验收失败项。

## 8. 数据导入后的重点检查

你后续导入数据后，建议按这个顺序复测：

1. 后端健康检查。
2. 登录。
3. 工作台进行中项目。
4. 项目中心列表。
5. 打开一条 `product_line` 的详情和时间轴。
6. 打开一条 `model_variant` 的详情和时间轴。
7. 按产品类型筛选。
8. 刷新页面确认登录态恢复。
9. 退出登录。

通过标准：

- 所有接口返回 `code=0`。
- 前端没有白屏。
- Console 没有未处理的 Axios 401/500 报错。
- Network 中请求都指向 `http://localhost:8080/api/v1/...`。
- 页面展示的数据来自后端响应，不是固定 mock。

## 9. 常见问题与处理

### 9.1 Docker API 连接失败

现象：

```text
failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine
```

原因：

- Docker Desktop 没启动。
- Docker Linux Engine 没启动。

处理：

```powershell
Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"
```

等待 Docker 启动完成后再执行：

```powershell
docker ps
```

### 9.2 PowerShell 把提示符当命令

错误示例：

```powershell
PS D:\Yuewei\git\YUEWEI\plm-server> docker start c641b26339ec_plm-postgres
```

正确输入：

```powershell
docker start c641b26339ec_plm-postgres
```

原因：`PS D:\...>` 是 PowerShell 提示符，不是命令内容。

### 9.3 前端登录 401

原因：

- 账号密码错误。
- 用户初始化 SQL 未执行。
- 浏览器保存了旧 token。

处理：

```javascript
localStorage.removeItem('plm_token')
location.href = '/#/login'
```

然后重新登录：

```text
engineer01 / plm123456
```

### 9.4 前端登录或项目接口 500

原因可能是：

- 数据库容器断开或重启后，后端连接池里有失效连接。
- 本地数据库缺少迁移字段。
- 导入数据不符合后端字段约束。

处理顺序：

1. 查后端日志。

```powershell
Select-String -Path logs\backend-dev.out.log -Pattern 'Unhandled exception|PSQLException|BadSqlGrammarException|Connection|Hikari|auth/login|projects' -Context 3,80 | Select-Object -Last 220
```

2. 查数据库健康。

```powershell
Invoke-RestMethod http://localhost:8080/api/v1/health/db
```

3. 如果日志出现 Hikari 连接失效，重启后端。
4. 如果日志出现 `column does not exist`，补齐对应 migration 字段。

### 9.5 前端页面空白

检查顺序：

1. F12 Console 是否有 Axios 401/500。
2. Network 是否请求到了 `localhost:8080`。
3. 是否清理过旧 `plm_token`。
4. 前端是否使用 x64 Node 启动。

前端启动建议始终使用：

```powershell
D:\Yuewei\program\node-v20.15.0-win-x64\node.exe node_modules\vite\bin\vite.js --host 0.0.0.0 --port 5174
```

## 10. 最终验收清单

| 模块 | 验收项 | 通过标准 |
| --- | --- | --- |
| M0 | 后端健康 | `/api/v1/health` 返回 `code=0` |
| M0 | 数据库健康 | `/api/v1/health/db` 返回 `code=0` 且 DB 为 `UP` |
| M0 | 产品数据读取 | 工作台或项目中心能看到导入的 Product 数据 |
| M1 | 登录 | 登录成功，保存 `plm_token` |
| M1 | 当前用户 | 刷新后 profile 成功，保持登录 |
| M1 | 未登录拦截 | 无 token 访问业务页会回登录页，接口返回 401 |
| M1 | 退出登录 | logout 成功，token 清空，刷新仍在登录页 |
| M2 | 工作台进行中项目 | `/workbench/projects/in-progress` 返回 `code=0` 并正确展示 |
| M2 | 项目列表 | `/projects` 返回 `code=0` 并正确展示 |
| M2 | 项目详情 | `/projects/{projectId}` 或 `/summary` 返回 `code=0` |
| M2 | 时间轴 | `/projects/{projectId}/timeline` 返回 6 个节点 |
| M2 | 产品类型筛选 | 有筛选时结果全部符合 `productType`，无数据时显示空状态 |

全部通过后，可以认为前端已经完成对 M0/M1/M2 后端核心链路的本地联调验收。
