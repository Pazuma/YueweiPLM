结论：当前系统具备“当前节点确认后推进下一节点”的基础能力，但当前文档需按最新业务口径调整为“大节点资料校验，小步骤逐步推进”。项目操作对象应是第 1 步、第 2 步这类小节点；小节点逐步完成；准备进入下一个大节点时，后端校验当前大节点下要求的资料是否上传齐套。上传资料时，用户可以在当前大节点内选择资料对应的小步骤。系统尚未形成企业级“阶段门禁 + 当前大节点内步骤资料归档 + 文件中心项目可读字段”的闭环。最小 MVP 可继续跑通基础推进和上传；若要求按业务严格验收，则必须补齐小步骤状态模型、阶段资料门禁和文件中心字段。

## 2. 业务理解

工作台是项目推进入口，项目中心和文件中心是同一套后端数据的不同视角：

1. 用户在工作台打开当前项目。
2. 系统只允许推进当前小步骤，例如“第 1 步：产品立项”。
3. 当前大节点如果包含需要上传资料的小步骤，用户可在当前大节点内选择资料对应的小步骤并上传。
4. 用户点击“确认”即完成当前小步骤，并自动进入下一小步骤，例如从“产品立项”进入“确认立项”。
5. 当前大节点下最后一个小步骤确认时，后端先校验当前大节点要求的资料是否齐套；齐套后才自动进入下一个大节点的第一个小步骤。
6. 资料写入附件表，并绑定 Product 项目、当前大节点和用户选择的小步骤。
7. 文件中心应能按项目查看归档资料，并展示项目编码、项目名称、时间轴大节点、小步骤、资料分类、版本、上传人等字段。

### 2.1 业务口径调整记录

用户在 2026-07-15 补充明确：推进操作对象是步骤/小节点，不是大节点；资料门禁对象是大节点。例如：

- 大节点：立项确认。
- 小步骤 1：产品立项。
- 小步骤 2：确认立项。
- 用户在“产品立项”点击确认后，应进入“确认立项”。
- “产品立项”和“确认立项”都完成后，系统准备进入下一个大节点。
- 进入下一个大节点前，系统校验“立项确认”大节点所需资料是否已经上传齐。
- 上传资料时可以在当前大节点中选择资料属于哪一个小步骤，例如选择“产品立项资料”或“确认立项资料”。

因此后续实现不能再把 `TimelineNodeDefinition` 仅理解为大节点。建议将时间轴拆成两层：

| 层级 | 作用 | 是否由用户直接操作 |
| --- | --- | --- |
| 阶段大节点 | 用于页面分组、进度概览、阶段统计和资料齐套门禁，例如立项确认、设计确认、开模试模 | 不直接推进；作为门禁对象 |
| 小步骤 | 用于确认和推进，例如产品立项、确认立项、画图查看；上传资料时可作为归属选择项 | 是 |

## 4. 企业级开发符合性结论

| 能力 | 当前状态 | 企业级要求 | 结论 |
| --- | --- | --- | --- |
| 状态流转 | 普通推进只能当前节点、确认后下一步，但当前节点粒度是阶段，不是小步骤 | 后端以小步骤为唯一可信门禁 | 需调整 |
| 资料门禁 | 未在进入下一大节点前校验当前大节点必传附件 | 当前大节点资料缺失时后端阻止进入下一大节点，返回明确业务错误 | 不合格 |
| 附件归属 | 附件挂 Product + timeline node | 不新增文件根对象，可追溯到项目和节点 | 合格 |
| 上传边界 | 节点存在即可上传 | 普通上传仅允许选择当前大节点内的小步骤；历史大节点补传需独立权限/原因/日志 | 不合格 |
| 文件中心可读性 | 只显示 Product ID | 必须展示项目编码、项目名称，支持按业务字段识别 | 不合格 |
| 审计 | 普通推进/附件操作有日志 | 强制推进、补传历史大节点资料、删除附件必须高风险审计 | 部分合格 |
| 最小 MVP | 可登录后基础推进、上传、文件中心查看，但不符合小步骤业务粒度 | 严格业务闭环需小步骤门禁 | 基础可跑，业务口径不通过 |

## 5. 推荐实施方案

采用“后端门禁为准、前端清晰呈现”的方案：

1. 后端将时间轴定义调整为“大节点 + 小步骤”两层模型。
2. Product 当前进度以 `currentStepNo` 指向当前小步骤，不以大节点作为推进对象。
3. 用户点击确认当前小步骤时，后端标记该小步骤完成，并自动进入下一小步骤。
4. 如果当前小步骤是当前大节点的最后一步，后端先校验当前大节点资料是否齐套；齐套后才进入下一大节点。
5. 在 `uploadTimelineAttachment()` 中增加普通上传只能选择当前大节点内小步骤的校验。
6. 文件中心不改 `plm_attachment` 表结构，通过 Product 批量查询补充 `projectCode`、`projectName`，并补充大节点名、小步骤名。
7. 前端工作台上传资料时提供“当前大节点内小步骤”下拉选择；在阶段详情中展示当前大节点资料缺口。
8. 文件中心表格新增“项目编码”“项目名称”“阶段”“步骤”列。
9. 强制推进不混入普通确认。后续如启用，必须单独后端接口、权限、原因、审计日志。

不推荐方案：

- 不推荐只在前端禁用按钮，因为可绕过。
- 不推荐把 `projectCode`、`projectName` 冗余写入 `plm_attachment`，会产生名称变更后的数据一致性问题。
- 不推荐把资料文件升级成独立根对象，违反 7 核心对象规则。

### 7.2 小步骤确认并在跨大节点时校验资料草稿

```java
// TimelineActionServiceImpl.java
@Transactional
public TimelineActionResultVO confirmStep(Long projectId, String stepCode, TimelineActionDTO dto, HttpServletRequest request) {
    Product product = getProductOrThrow(projectId);
    TimelineStepContext context = requireCurrentStep(product, stepCode);
    CurrentUser currentUser = requireCurrentUser();
    String remark = dto == null ? null : dto.getRemark();

    int currentIndex = context.steps().indexOf(context.currentStep());
    boolean hasNextStep = currentIndex >= 0 && currentIndex < context.steps().size() - 1;
    TimelineStepDefinition nextStep = hasNextStep ? context.steps().get(currentIndex + 1) : null;
    boolean crossingStage = nextStep != null && !nextStep.stageCode().equals(context.currentStep().stageCode());

    if (crossingStage) {
        requireCurrentStageDocuments(product, context.currentStage());
    }

    product.setCurrentStepNo(hasNextStep ? nextStep.stepNo() : context.currentStep().stepNo());
    product.setTimelineCurrentConfirmed(!hasNextStep);
    product.setTimelineConfirmedNodeKey(context.currentStep().stepCode());
    product.setStatus(resolveProductStatus(product.getCurrentStepNo(), context.steps().size()));
    applyTimelineAudit(product, currentUser, "confirm_step", remark);
    productRepository.updateById(product);

    Long logId = writeLog(
        product,
        OperationActionConstants.TIMELINE_CONFIRM,
        detailJsonForConfirmStep(product, context.currentStage(), context.currentStep(), nextStep, remark),
        request
    );

    return buildStepResult(product, "confirm_step", context.currentStage(), context.currentStep(), nextStep, logId);
}
```

关键逻辑：

- 用户点“确认”操作的是当前小步骤。
- 确认成功后自动进入下一小步骤。
- 如果下一小步骤仍属于当前大节点，不做阶段资料门禁，只继续推进小步骤。
- 如果下一小步骤属于下一大节点，先校验当前大节点资料是否齐套；通过后返回新的 `currentStageCode/currentStageName`，前端自动切换阶段。
- 原有 `advance()` 可保留为兼容接口，但新业务推荐将普通用户入口收敛到 `confirmStep()`。

// TimelineActionServiceImpl.java
private final AttachmentRepository attachmentRepository;

private void requireCurrentStageDocuments(Product product, TimelineStageDefinition currentStage) {
    TimelineStageDocumentRequirement requirement =
        timelineDefinitionProvider.getStageRequirement(currentStage.stageCode());
    if (requirement == null || requirement.stepRequirements().isEmpty()) {
        return;
    }

    Set<String> existingKeys = attachmentRepository.selectList(new LambdaQueryWrapper<Attachment>()
            .eq(Attachment::getOwnerObjectType, AttachmentOwnerTypeConstants.PRODUCT)
            .eq(Attachment::getOwnerObjectId, product.getProductId())
            .eq(Attachment::getDeletedFlag, 0))
        .stream()
        .map(attachment -> attachment.getTimelineNodeKey() + "::" + attachment.getFileCategory())
        .collect(Collectors.toSet());

    List<String> missing = requirement.stepRequirements().stream()
        .filter(TimelineStepDocumentRequirement::required)
        .filter(item -> !existingKeys.contains(item.stepCode() + "::" + item.fileCategory()))
        .map(item -> item.stepCode() + "/" + item.fileCategory())
        .toList();

    if (!missing.isEmpty()) {
        throw new BusinessException(
            ErrorCodeConstants.STATUS_TRANSITION_ILLEGAL,
            "当前阶段资料未上传齐：" + String.join(",", missing)
        );
    }
}

// confirmStep() 中，只有即将跨大节点时调用：

}

## 9. 风险与维护建议

1. 节点编码必须统一。当前前端存在旧展示节点 key（如 `sampling-process`）和后端节点 key（如 `PRODUCT_LINE_SAMPLE_PROCESS`）的历史痕迹，后续要以 `GET /api/v1/projects/{id}/timeline` 返回的 `nodeCode` 为准。
2. 后续应统一命名：大节点建议命名为 `stage`，小节点建议命名为 `step`，避免继续把阶段和步骤都叫 node。
3. 大节点不允许被用户直接确认或推进，只由其下小步骤完成状态自动推导。
4. 必传资料规则必须集中配置，不要散落在多个 Vue 组件里。
5. 文件中心字段只做 VO 聚合，不改附件表冗余项目名称。
6. 普通确认和强制推进必须分离。强制推进必须有权限、原因、日志、管理层可追溯。
7. 历史大节点补传资料不要复用普通上传接口，应单独做 backfill/admin 接口。
8. 删除附件会影响大节点资料门禁，删除后应刷新项目时间轴 documentCount 和门禁状态。
9. 后续可将大节点资料要求从 Java 常量迁移为配置表，但首版建议先常量化，降低实现和迁移风险。
