# PLM 钉钉出站连接器地址配置说明

日期：2026-07-29

## 1. 背景

当前新型号线的目标链路是：

```text
钉钉实际审批表提交
-> PLM 创建新型号项目
-> PLM 项目流程走到 运模 / MODEL_VARIANT_MOLD_TRANSFER
-> PLM 项目在系统内归档
-> PLM 调用钉钉出站连接器
-> 钉钉代审批人自动同意
-> 钉钉审批继续流转到后续节点
```

已确认入站链路可用，也就是“钉钉审批表传数据到 PLM”已经通了。

现在缺的是出站链路：

```text
PLM 项目完成 -> 钉钉代同意
```

这个出站链路由环境变量 `DINGTALK_OUTBOUND_ENDPOINT` 控制。

## 2. DINGTALK_OUTBOUND_ENDPOINT 是什么

`DINGTALK_OUTBOUND_ENDPOINT` 是 PLM 项目完成后主动 POST 的出站服务地址。

它应该指向一个中间服务或出站连接器，这个服务负责：

1. 接收 PLM 发来的项目完成消息。
2. 根据钉钉审批实例 ID 查询当前等待节点的 `taskId`。
3. 调用钉钉接口，以指定审批人身份执行“同意”动作。
4. 把执行结果返回给 PLM。

它不是下面这些地址：

| 不能填的地址 | 原因 |
| --- | --- |
| `http://服务器/api/v1/integrations/ding` | 这是 PLM 入站接口，只负责接收钉钉表单数据，不能代同意钉钉 |
| `formUrl` / 审批单链接 | 这是人工打开审批单看的链接，不是机器执行审批的接口 |
| 钉钉审批模板链接 | 只能打开或配置模板，不能作为 PLM 出站回调地址 |
| cpolar 404 页面地址 | 说明隧道域名或路径不对，请换成真实能 POST 的服务路径 |

正确的地址应该类似：

```text
https://你的域名/dingtalk/outbound
https://你的域名/api/dingtalk/outbound
http://dingtalk-connector:8080/api/dingtalk/outbound
```

实际路径以你部署的出站连接器服务为准。

## 3. 当前 PLM 会发送什么

### 3.1 查询 taskId

如果钉钉实际审批表没有传 `taskId`，PLM 会先向 `DINGTALK_OUTBOUND_ENDPOINT` 发起兜底查询：

```json
{
  "action": "workflow-task-lookup",
  "projectId": 42,
  "projectCode": "PRD-xxx",
  "projectName": "HR X8D",
  "productType": "model_variant",
  "model": "HR X8D",
  "nodeKey": "MODEL_VARIANT_MOLD_TRANSFER",
  "nodeName": "运模",
  "sourceApprovalInstanceId": "钉钉审批实例ID",
  "processCode": "PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C",
  "processInstanceId": "钉钉审批实例ID",
  "approvalInstanceId": "钉钉审批实例ID",
  "actionerUserId": "02356802443226388318"
}
```

出站连接器需要返回：

```json
{
  "taskId": "钉钉当前等待节点任务ID"
}
```

PLM 兼容下面几个返回字段名：

```text
taskId
approvalTaskId
task_id
id
```

### 3.2 执行代同意

拿到 `taskId` 后，PLM 会继续向同一个 `DINGTALK_OUTBOUND_ENDPOINT` 发送：

```json
{
  "action": "agree",
  "projectId": 42,
  "projectCode": "PRD-xxx",
  "projectName": "HR X8D",
  "productType": "model_variant",
  "model": "HR X8D",
  "nodeKey": "MODEL_VARIANT_MOLD_TRANSFER",
  "nodeName": "运模",
  "sourceApprovalInstanceId": "钉钉审批实例ID",
  "processCode": "PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C",
  "processInstanceId": "钉钉审批实例ID",
  "approvalInstanceId": "钉钉审批实例ID",
  "taskId": "钉钉当前等待节点任务ID",
  "actionerUserId": "02356802443226388318",
  "result": "agree",
  "remark": "PLM 运模已完成，项目已归档，自动代同意钉钉等待节点"
}
```

出站连接器建议返回：

```json
{
  "status": "success",
  "approvalInstanceId": "钉钉审批实例ID",
  "externalUrl": "钉钉审批单链接，可为空"
}
```

PLM 会兼容这些返回字段：

| PLM 含义 | 兼容字段 |
| --- | --- |
| 外部实例 ID | `instanceId` / `processInstanceId` / `approvalInstanceId` |
| 外部链接 | `url` / `externalUrl` / `formUrl` |
| 外部状态 | `status` / `externalStatus` |

## 4. 配置方式

### 4.1 根目录 .env

建议在 `D:\work\Yuewei\.env` 中配置：

```env
DINGTALK_OUTBOUND_ENDPOINT=https://你的出站连接器域名/api/dingtalk/outbound
DINGTALK_AUTO_APPROVER_USER_ID=02356802443226388318
```

如果出站连接器部署在同一个 Docker Compose 网络内，可以用服务名：

```env
DINGTALK_OUTBOUND_ENDPOINT=http://dingtalk-connector:8080/api/dingtalk/outbound
DINGTALK_AUTO_APPROVER_USER_ID=02356802443226388318
```

### 4.2 docker-compose.yml

`server.environment` 里需要把环境变量传给后端容器：

```yaml
server:
  environment:
    DINGTALK_OUTBOUND_ENDPOINT: "${DINGTALK_OUTBOUND_ENDPOINT:-}"
    DINGTALK_AUTO_APPROVER_USER_ID: "${DINGTALK_AUTO_APPROVER_USER_ID:-02356802443226388318}"
```

当前 `docker-compose.yml` 已经有 `DINGTALK_AUTO_APPROVER_USER_ID`，但需要确认是否已经加入 `DINGTALK_OUTBOUND_ENDPOINT`。

### 4.3 重启服务

配置完成后重启 server：

```powershell
cd D:\work\Yuewei
docker compose up -d --build server
```

确认环境变量已进入容器：

```powershell
docker compose exec -T server printenv DINGTALK_OUTBOUND_ENDPOINT
docker compose exec -T server printenv DINGTALK_AUTO_APPROVER_USER_ID
```

期望第一条输出真实 URL，第二条输出：

```text
02356802443226388318
```

## 5. 出站连接器需要实现的动作

同一个 `DINGTALK_OUTBOUND_ENDPOINT` 可以按 `action` 字段分发。

| action | 用途 | 出站连接器要做什么 |
| --- | --- | --- |
| `workflow-task-lookup` | 查询等待节点 taskId | 根据 `approvalInstanceId` 和 `actionerUserId` 查当前待办任务 |
| `agree` | 新型号线代同意 | 用 `taskId` 和 `actionerUserId` 调用钉钉同意接口 |
| `cc` | 新产品线完成抄送 | 发送钉钉通知或抄送消息 |

新型号线要实现前两个动作：

```text
workflow-task-lookup
agree
```

如果实际审批表已经能直接传 `taskId` 给 PLM，那么 `workflow-task-lookup` 可以不执行，但出站连接器仍然必须支持 `agree`。

## 6. 配置完成后的验证

### 6.1 跑实际审批表

1. 在钉钉提交一张新型号实际审批表。
2. 确认 PLM 创建了新型号项目。
3. 在 PLM 前端把该项目流程确认到 `运模 / MODEL_VARIANT_MOLD_TRANSFER`。
4. 点击确认运模。
5. 回到钉钉审批单，确认等待节点已被自动同意，后续节点继续流转。

### 6.2 查集成记录

```powershell
cd D:\work\Yuewei
docker compose exec -T postgres psql -U plm -d plm -c "select integration_record_id, integration_type, external_instance_id, external_status, processing_status, project_id, error_code, error_message, node_key, created_at, updated_at from plm_integration_record where integration_type='model_variant_mold_transfer_completed' order by integration_record_id desc limit 10;"
```

期望结果：

```text
integration_type = model_variant_mold_transfer_completed
processing_status = success
external_status = success
node_key = MODEL_VARIANT_MOLD_TRANSFER
```

如果看到：

```text
external_status = dry_run
processing_status = success
```

说明 PLM 只是生成了本地模拟记录，没有真实调用钉钉。通常是 `DINGTALK_OUTBOUND_ENDPOINT` 没配或容器没有重启。

如果看到：

```text
processing_status = failed
error_message 包含 taskId
```

说明没有拿到当前等待节点任务 ID。处理方式：

1. 优先在钉钉实际表单入站 JSON 中映射 `taskId` / `approvalTaskId`。
2. 或者让出站连接器的 `workflow-task-lookup` 能根据 `approvalInstanceId` 查询到 taskId。

### 6.3 看日志

```powershell
docker compose logs --tail=300 server | Select-String -Pattern "DingTalk project completion return|workflow-task-lookup|taskId|dry_run|model_variant_mold_transfer_completed|ERROR|WARN" -Context 3,6
```

## 7. 常见问题

### 7.1 为什么调试接口通了，实际流程还是不代同意

调试接口通的是入站：

```text
钉钉 -> PLM
```

代同意是出站：

```text
PLM -> 钉钉
```

两条链路不是一个配置。入站通了，只说明 PLM 能收到审批表，不代表 PLM 能回打钉钉。

### 7.2 formUrl 没有审批单链接选项怎么办

不影响代同意。

`formUrl` 只是查看链接，可为空。代同意真正需要的是：

```text
approvalInstanceId
taskId
actionerUserId
```

如果没有 `taskId`，就需要 `workflow-task-lookup` 兜底查询。

### 7.3 可以直接把 DINGTALK_OUTBOUND_ENDPOINT 配成 PLM 地址吗

不建议，也不能配成 PLM 入站接口。

PLM 入站接口只认识“创建项目”的 JSON，不会执行钉钉同意动作。出站地址必须是能调用钉钉审批任务接口的服务。

### 7.4 没有出站连接器服务怎么办

有两个方案：

1. 临时方案：让钉钉实际审批表入站时直接传 `taskId`，同时补一个很小的出站中间服务，只处理 `agree`。
2. 完整方案：做一个钉钉出站连接器服务，同时支持 `workflow-task-lookup`、`agree`、`cc`，统一处理钉钉 access token、接口错误和日志。

建议采用完整方案。PLM 保持只负责项目流程和出站记录，中间服务负责钉钉 API 细节，后续维护更清晰。

## 8. 维护建议

1. `DINGTALK_OUTBOUND_ENDPOINT` 使用 `.env` 配置，不要硬编码到 Java 代码。
2. 出站连接器必须记录每次请求的 `approvalInstanceId`、`taskId`、`actionerUserId` 和钉钉返回结果。
3. `DINGTALK_AUTO_APPROVER_USER_ID` 必须是钉钉等待节点中有权限审批的人。
4. 钉钉审批模板改节点或审批人后，要重新验证 `workflow-task-lookup` 是否还能查到正确待办任务。
5. 每次联调失败先查 `plm_integration_record`，再查 server 日志，最后查出站连接器自己的日志。
6. 如果后续新增重试按钮，可按 `processing_status=failed` 的 outbound 记录重新触发。

## 9. 本次文档结论

当前要让“项目流程完成 -> 钉钉代同意”生效，必须先准备一个真实可访问的出站连接器地址，并配置到：

```text
DINGTALK_OUTBOUND_ENDPOINT
```

只配钉钉实际审批表的入站接口不够。入站负责建项目，出站负责代同意。
