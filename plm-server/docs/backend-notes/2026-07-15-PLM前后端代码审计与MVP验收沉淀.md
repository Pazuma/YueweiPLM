## 1. 总结论

当前代码已经具备 PLM M1-M5 局部能力：登录/当前用户/操作日志骨架、进行中项目工作台、项目时间轴动作、BOM、工艺路线、附件上传下载、冻结发布归档门禁。

但按业务文档和架构文档要求，当前尚未达到企业级完整交付，也不能判定“最小 MVP 全链路可跑通”。核心原因是：

- 本机默认后端启动依赖 `localhost:5433` PostgreSQL，当前端口未连通，默认 `spring-boot:run` 会因 Flyway/数据库连接失败而无法启动。
- Flyway 迁移链路不是空库自洽：仓库内未看到完整 `plm_product` 初始建表基线，后续 M2/M3/M5 直接 `alter table plm_product`，空库重建存在失败风险。
- 前端本地默认 API 指向不完整：`.env.development` 中 `VITE_API_BASE_URL=` 为空，`vite.config.ts` 未配置 `/api` proxy，默认 dev server 会请求 `localhost:5173/api/v1`，不能自动打到后端 8080/8081。
- 业务对象覆盖不完整，业务文档要求的七个核心对象 Customer/Product/Order/ProductionOrder/Process/Inventory/Workstation 未全部实现真实后端闭环。
- 企业级安全、RBAC、数据权限、对象存储、Docker 一键运行、OpenAPI 文档沉淀、全模块审计日志仍不完整。

MVP 结论：
- M3-M5 项目研发闭环的局部代码能力：部分通过。
- 以前后端 + 数据库 + 文件 + 权限 + 七核心对象为口径的最小企业级 MVP：不通过。
- 若只定义为“项目中心查看项目、时间轴、BOM、工艺路线、附件、发布门禁”的窄口径 MVP：代码具备基础，但当前环境未能端到端验证通过。

## 6. MVP 修复路径

### 6.1 先跑通最小端到端

1. 提供本地运行环境：
   - PostgreSQL：`localhost:5433/plm`
   - Redis：`localhost:6379`
   - 文件存储：开发期可继续 `data/uploads`
2. 先修复数据库迁移：
   - 补齐 `plm_product` 等基础表基线。
   - 用空 schema 执行完整 Flyway migrate。
   - 迁移通过后再验收业务接口。
3. 执行后端：
   - `mvn "-Dmaven.repo.local=C:/Users/JT/.m2/repository" test`
   - `mvn "-Dmaven.repo.local=C:/Users/JT/.m2/repository" spring-boot:run`
4. 执行前端：
   - 修复当前 shell 的 `node`/`npm` PATH。
   - 设置 `VITE_API_BASE_URL=http://localhost:8080`，或配置 Vite `/api` proxy。
   - `npm run type-check`
   - `npm run test:run`
   - `npm run build`
   - `npm run dev`
5. 验收窄 MVP：
   - 登录
   - 查看进行中项目
   - 查看项目时间轴
   - 确认/推进/退回节点
   - 维护 BOM
   - 维护工艺路线
   - 上传/下载/删除附件
   - 查看发布门禁
   - 冻结、发布、归档、废弃动作

### 6.2 再补企业级能力

1. RBAC 和数据权限。
2. MinIO/S3 对象存储。
3. Docker Compose 一键运行。
4. 七核心对象真实后端闭环。
5. OpenAPI 导出与版本化。
6. 操作日志、审批日志、下载日志全覆盖。
7. CI 中强制后端测试、前端 type-check/test/build。
