## 3. 核心代码逻辑

### 3.1 时间轴触发点

`TimelineActionServiceImpl.confirm(...)` 在确认最后一个 PLM 节点时处理项目完成：

```java
completeModelVariantAtMoldTransfer(product, context.current(), currentUser);
completeProductLineAtFinalStep(product, context.current(), currentUser);
```

项目状态保存和操作日志写入后，只在终点节点触发钉钉出站：

```java
if (!hasNextStep) {
    triggerDingTalkCompletionReturn(product, context.current(), currentUser.displayName());
}
```

在 Spring 事务上下文中，出站动作注册为 `afterCommit`，避免 PLM 项目状态未提交时就调用外部系统。

### 3.2 新型号线代同意

`DingTalkProjectCompletionReturnService` 判断：

```text
productType = model_variant
nodeKey = MODEL_VARIANT_MOLD_TRANSFER
```

命中后：

- 查找入站记录：`source_system=dingtalk`、`integration_type=model_variant`、`direction=inbound`、`project_id=当前项目`。
- 从入站 payload 提取 `taskId / approvalTaskId / task_id / form.taskId / form.审批任务ID`。
- 生成出站 payload：

```json
{
  "action": "agree",
  "processInstanceId": "钉钉审批实例ID",
  "taskId": "钉钉等待节点任务ID",
  "actionerUserId": "02356802443226388318",
  "result": "agree",
  "remark": "PLM 运模已完成，项目已归档，自动代同意钉钉等待节点"
}
```

- 写入出站记录：`integration_type=model_variant_mold_transfer_completed`。
- 出站记录的 `externalInstanceId` 保留原钉钉审批实例 ID，便于后续按 `approvalInstanceId` 追踪和补偿。
- 如果已有成功出站记录，直接返回幂等命中，不重复调用钉钉；当数据库同时存在 failed 和 success 时，优先识别 success。
- 如果缺少 `taskId` 或审批人配置，写 `failed` 记录和错误原因，便于后续补偿。

### 3.3 新产品线完成抄送

判断：

```text
productType = product_line
nodeKey = PRODUCT_LINE_PRODUCTION_DECISION_STEP
```

命中后：

- 将产品线项目状态置为 `released`，写入 `releasedAt/releasedBy`。
- 查找入站记录：`integration_type=product_line`。
- 生成抄送 payload：

```json
{
  "action": "cc",
  "processInstanceId": "钉钉审批实例ID",
  "receiverUserIds": ["02356802443226388318"],
  "title": "PLM 新产品线流程已完成",
  "content": "PLM 新产品线流程已完成：产品名称"
}
```

- 写入出站记录：`integration_type=product_line_completed_cc`。
- 出站记录的 `externalInstanceId` 同样保留原钉钉审批实例 ID；通知接口返回内容保存在 payload 和状态字段里。
- 如果已有成功出站记录，不重复发送。

### 3.4 出站客户端

`DingTalkOutboundApprovalClient` 新增：

```java
public DingTalkOutboundResult executeWorkflowTask(Map<String, Object> payload)
public DingTalkOutboundResult sendCompletionNotice(Map<String, Object> payload)
```

当前保持项目既有模式：

- 未配置 `outboundEndpoint` 时，返回 `dry_run`，并把 payload 写入出站记录。
- 配置 `outboundEndpoint` 时，向该地址 POST JSON，并解析返回的 `instanceId/processInstanceId/approvalInstanceId`、`url/externalUrl/formUrl`、`status/externalStatus`。

## 4. 配置项

配置前缀：

```yaml
plm:
  integrations:
    dingtalk:
      auto-approver-user-id: ${DINGTALK_AUTO_APPROVER_USER_ID:02356802443226388318}
      product-line-cc-user-ids: ${DINGTALK_PRODUCT_LINE_CC_USER_IDS:02356802443226388318}
```

Docker Compose 同步增加：

```yaml
DINGTALK_AUTO_APPROVER_USER_ID: "${DINGTALK_AUTO_APPROVER_USER_ID:-02356802443226388318}"
DINGTALK_PRODUCT_LINE_CC_USER_IDS: "${DINGTALK_PRODUCT_LINE_CC_USER_IDS:-02356802443226388318}"
```

维护口径：

- 新型号线等待节点审批人应配置为 `DINGTALK_AUTO_APPROVER_USER_ID` 对应的钉钉用户。
- 新产品线抄送人变化时，优先改 `DINGTALK_PRODUCT_LINE_CC_USER_IDS`，不要改代码。
- 多个抄送人可用逗号分隔，由 Spring 配置绑定为列表。

## 5. 好处

- 避免钉钉连接器 HTTP 超时：创建项目和项目完成回传拆成两个阶段。
- 避免审批模板冲突：PLM 不新建钉钉审批实例，只推动原实例等待节点继续走。
- 审计清晰：入站和出站都落 `plm_integration_record`，能查到审批实例、节点、状态和错误。
- 幂等安全：同一个项目、节点、方向、出站类型已有成功记录时，不重复发送。
- 配置可维护：审批人和抄送人通过配置切换。
- 失败可补偿：缺 `taskId`、缺配置或接口异常都会写 `failed`，后续可按记录重试。

## 6. 后续维护建议

1. 钉钉模板里必须把等待节点任务 ID 映射给 PLM，字段名建议用 `taskId` 或 `approvalTaskId`。
2. 如果钉钉无法在连接器节点直接拿到等待节点 `taskId`，后续应增加“审批任务变更事件监听”或“审批实例详情查询”兜底。
3. 生产环境接真实钉钉 API 时，建议把 `DingTalkOutboundApprovalClient` 替换为正式客户端，补 access token 获取、过期刷新、请求签名和接口错误码解析。
4. 出站失败重试可继续复用当前 `plm_integration_record`，按 `processing_status=failed`、`integration_type`、`project_id` 查待补偿记录。
5. 前端如要展示回传状态，可在项目详情增加“钉钉回传状态”区域，读取该项目的 outbound 集成记录。
6. 钉钉日期字段允许传 `2026-08-30`、`2026-8-30`、`2026/8/30` 或 `2026-08-30T10:30:00+08:00`；后端会统一解析为 `LocalDate`。日期格式确实错误时应返回参数校验错误，不能抛 500。
7. 允许同一来源产品下重复创建相同手机型号的新型号项目。钉钉入站幂等键只使用审批实例 `approvalInstanceId`，同一审批实例重复回调不重复建项目；不同审批实例即使 `model` 相同，也创建新的 PLM 项目。

## 7. 前端测试方法

### 7.1 新型号线

1. 用钉钉连接器或 Postman 调用：

```text
POST /api/v1/integrations/dingtalk/approval-callbacks
```

请求体中至少包含：

```json
{
  "processCode": "PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C",
  "approvalInstanceId": "ding-instance-001",
  "taskId": "ding-task-001",
  "approvalStatus": "approved",
  "form": {
    "parentProductId": 1,
    "tipo": "Fantasia Case",
    "model": "HR X8D",
    "generatedCode": "MFA101291\\nMFA201291"
  }
}
```

2. 在前端项目中心打开创建出来的新型号项目。
3. 逐步确认时间轴，直到 `运模 / MODEL_VARIANT_MOLD_TRANSFER`。
4. 点击确认运模。
5. 预期前端看到项目状态变为 `archived`，时间轴停在运模。
6. 查询后端集成记录，预期有：

```text
integration_type = model_variant_mold_transfer_completed
direction = outbound
processing_status = success 或 failed
```

如果没有配置真实 `outboundEndpoint`，状态为 `success` 且外部状态为 `dry_run`，表示本地已生成出站 payload，但未真实调用钉钉。

### 7.2 新产品线

1. 通过钉钉新产品线审批或 Postman 创建产品线项目。
2. 在前端项目中心打开该产品线。
3. 逐步确认到最后节点 `投产决策 / PRODUCT_LINE_PRODUCTION_DECISION_STEP`。
4. 点击确认。
5. 预期项目状态变为 `released`，并写入 `releasedAt/releasedBy`。
6. 查询 `plm_integration_record`，预期有：

```text
integration_type = product_line_completed_cc
direction = outbound
source_payload_json 包含 receiverUserIds
```
