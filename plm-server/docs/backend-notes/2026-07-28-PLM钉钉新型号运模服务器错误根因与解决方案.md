# PLM 钉钉新型号运模服务器错误根因与解决方案

日期：2026-07-28

## 1. 事故现象

从钉钉创建的新型号项目，在 PLM 走到最后一步 `运模 / MODEL_VARIANT_MOLD_TRANSFER` 并点击确认后，前端显示服务器错误。用户感知为：项目没有归档、钉钉后续审批没有继续、集成记录也没有正常沉淀。

本次抓到的服务端日志 requestId：

```text
b4466bf6-475e-4b75-8d10-94dd9c165390
```

日志核心报错：

```text
org.springframework.dao.DataIntegrityViolationException
ERROR: null value in column "external_status" of relation "plm_integration_record" violates not-null constraint
Failing row contains (..., dingtalk, model_variant_mold_transfer_completed, 111, null, ..., failed, ..., project_id=42,
error_code=DINGTALK_PROJECT_COMPLETION_RETURN_FAILED,
error_message=钉钉等待节点 taskId 未保存，无法自动代同意,
process_code=PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C,
direction=outbound,
node_key=MODEL_VARIANT_MOLD_TRANSFER, ...)
```

## 2. 根因结论

根因有两个叠加点：

1. 钉钉入站记录里没有保存待审批节点的 `taskId`，所以 PLM 运模完成后无法调用“代审批人同意”接口。这本来应该变成一条 outbound 失败记录，方便后续补偿。
2. 旧数据库结构中 `plm_integration_record.external_status` 是 `not null`，但失败记录保存时原代码写入了 `null`。结果失败记录本身也保存失败，抛出数据库异常。

影响接口返回 500 的直接原因：

```java
record.setExternalStatus(result == null ? null : result.externalStatus());
```

当 `taskId` 缺失时，`result == null`，于是 `externalStatus = null`，撞上数据库非空约束。

另一个设计缺陷是：钉钉回传是在 PLM 最后一步确认后的后置动作，失败时不应该影响 PLM 归档结果；但原代码没有兜底捕获后置动作异常，异常冒泡后前端就看到服务器错误。

## 4. 核心代码

### 4.1 outbound 记录状态兜底

`DingTalkProjectCompletionReturnService.saveOutbound(...)`：

```java
record.setExternalStatus(resolveExternalStatus(result, errorMessage));
record.setProcessingStatus(errorMessage == null ? PROCESSING_SUCCESS : PROCESSING_FAILED);
record.setErrorCode(errorMessage == null ? null : "DINGTALK_PROJECT_COMPLETION_RETURN_FAILED");
record.setErrorMessage(errorMessage);
```

新增状态解析：

```java
private String resolveExternalStatus(DingTalkOutboundResult result, String errorMessage) {
    if (result != null && StringUtils.hasText(result.externalStatus())) {
        return result.externalStatus();
    }
    return StringUtils.hasText(errorMessage) ? PROCESSING_FAILED : PROCESSING_SUCCESS;
}
```

效果：

- 钉钉真实返回 `dry_run/success/...` 时，保存钉钉返回状态。
- 本地校验失败或远程调用异常时，保存 `failed`。
- 即使旧库仍然有 `external_status not null`，也不会再因为空值导致 500。

### 4.2 后置钉钉回传异常隔离

`TimelineActionServiceImpl.triggerDingTalkCompletionReturn(...)`：

```java
Runnable task = () -> {
    try {
        dingTalkProjectCompletionReturnService.handleProjectCompleted(product, currentNode, operator);
    } catch (Exception ex) {
        log.warn(
            "DingTalk project completion return failed after PLM timeline completion, projectId={}, nodeKey={}",
            product.getProductId(),
            currentNode.nodeCode(),
            ex
        );
    }
};
```

效果：

- PLM 运模确认和项目归档是主流程。
- 钉钉代同意是后置集成动作。
- 后置动作失败只进入日志和集成记录，不再把 PLM 接口打成 500。

### 4.3 数据库兼容迁移

`V20260728_1010__integration_record_external_status_outbound_compatibility.sql`：

```sql
update plm_integration_record
set external_status = processing_status
where external_status is null;

alter table if exists plm_integration_record
    alter column external_status drop not null;
```

效果：

- 旧数据如果存在空 `external_status`，先用 `processing_status` 补齐。
- 放开非空约束，适配 inbound/outbound 不同类型集成记录。
- 代码层仍会尽量写非空状态，数据库层只做兼容兜底。

## 5. 目标效果

新型号线：

- PLM 流程只跑到 `MODEL_VARIANT_MOLD_TRANSFER / 运模`。
- 运模确认后，PLM 项目状态变为 `archived`，写入 `archivedAt / archivedBy / archiveReason`。
- 之后触发钉钉代同意。
- 如果钉钉 `taskId` 缺失或接口异常，PLM 项目仍然归档，集成状态记录为 `failed`，日志里保留失败原因。

新产品线：

- PLM 跑完产品线对应项目流程后，项目状态进入完成态。
- 完成后触发钉钉抄送给配置的人员。
- 抄送失败不阻断 PLM 项目完成，失败原因进入日志和 outbound 集成记录。

## 6. 当前项目补偿检查

本次日志里出现的项目是：

```text
project_id = 42
approvalInstanceId/external_instance_id = 111
```

由于当前 PowerShell 会话找不到 `docker` 命令，尚未直接确认项目 42 的数据库状态。部署修复后建议先执行：

```powershell
docker compose exec -T postgres psql -U plm -d plm -c "select product_id, product_code, product_name, product_type, status, current_step_no, timeline_current_confirmed, timeline_confirmed_node_key, archived_at, archive_reason from plm_product where product_id = 42;"
```

再查集成记录：

```powershell
docker compose exec -T postgres psql -U plm -d plm -c "select integration_record_id, integration_type, external_instance_id, external_status, processing_status, project_id, error_code, error_message, process_code, direction, node_key, approval_task_id from plm_integration_record where project_id = 42 order by integration_record_id;"
```

处理规则：

- 如果 `status = archived`，说明 PLM 主流程已完成，只需要补钉钉代同意。
- 如果仍不是 `archived`，部署后在前端重新进入项目，重新确认 `运模`。
- 如果 outbound 记录显示 `processing_status = failed` 且错误包含 `taskId`，需要在钉钉连接器映射中补上 `taskId / approvalTaskId`，再做补偿重试。

## 7. 钉钉连接器参数建议

新型号入站时，建议继续保留以下字段：

```json
{
  "processCode": "PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C",
  "approvalInstanceId": "钉钉审批实例ID",
  "approvalNo": "钉钉审批编号",
  "approvalStatus": "approved",
  "approvedAt": "2026-07-28T10:30:00+08:00",
  "taskId": "钉钉等待节点任务ID",
  "applicant": {
    "userId": "申请人UserID",
    "userName": "申请人姓名"
  },
  "form": {
    "parentProductId": 1,
    "tipo": "Fantasia Case",
    "model": "HR X8D",
    "generatedCode": "MFA101291\nMFA201291",
    "moldMarking": "HR X8D",
    "expectedDeliveryDate": "2026-08-30",
    "remark": "钉钉连接器联调"
  },
  "attachments": []
}
```

关键点：

- `processCode` 必须映射。
- `approvalStatus` 必须映射。
- `approvalInstanceId` 用于幂等和追踪。
- `taskId` 或 `approvalTaskId` 必须映射，否则 PLM 无法代同意钉钉等待节点。
- `generatedCode` 可以传多行，后端会自行拆分模具编码。

## 9. 维护建议

1. 钉钉连接器映射必须把当前等待节点任务 ID 传给 PLM，字段名优先用 `taskId`，备选 `approvalTaskId`。
2. 后续建议做一个“钉钉回传失败重试”后台按钮或管理接口，按 `processing_status=failed` 查询并重放 outbound payload。
3. 生产接真实钉钉 API 时，需要把 access token 获取、过期刷新、接口错误码解析沉淀在 `DingTalkOutboundApprovalClient` 内。
4. 日志排查优先用 `requestId`、`project_id`、`approvalInstanceId` 三个维度串起来。
5. 后续任何外部系统回调或后置通知，都应遵循同一原则：PLM 主流程提交成功后，外部通知失败不能反向打断 PLM 状态。
