# 2026-07-18 PLM 工序成品标识与产品工序物料状态编码方案沉淀

## 1. 本次任务

用户在 2026-07-18 补充工艺路线编码口径：

1. 在工艺路线弹窗的工序明细行右侧，即当前“操作”按钮旁边，增加一个字段：该工序是否是成品。是成品时用户点击勾选即可。
2. 产品名例如“亮甲”，产品编码为 `BA`。
3. 工序阶段产品编码需要在产品编码前加 `N`，即 `N + BA = NBA`。
4. 工艺编码例如：注塑 `10`，注塑组装 `11`，打印 `20`，喷油 `30`，产品品组装 `40`，CNC `51`，贴磁铁 `52`。
5. 材料/状态编码例如：TPU `10`，PC `20`，半成品 `30`，以及后续 TPU1、PC1、PC2、PC3、PC4、PC5 等扩展编码；`成品` 不再放入材料/状态编码。
6. 编码规则示例：
   - TPU 亮甲注塑编码：`NBA` + `10` + `10` = `NBA1010`
   - PC 亮甲注塑编码：`NBA` + `10` + `20` = `NBA1020`
7. `成品` 是工序行上的独立勾选标识，不占用材料/状态编码；如历史资料中存在 `PET=40` 或 `成品=40` 的口径，后续应迁移为独立成品标识。
8. 上述编码规则是大部分场景的默认规则，填写工艺路线时必须支持人工修改工序业务编码，并由后端校验唯一性和格式。

本次只生成方案沉淀文档，不修改前端、后端、数据库业务代码。

## 3. 业务理解

本次不是单纯新增一个前端勾选框，而是要把“工序明细中的每一道工序”与企业内部产品工序编码规则打通。

推荐业务口径：

```text
产品工序业务编码 = 工序阶段前缀 + 产品短编码 + 工艺编码 + 材料/状态编码
```

以“亮甲”为例：

```text
产品短编码：BA
工序阶段前缀：N
工序阶段产品编码：NBA
工艺：注塑 = 10
材料/状态：TPU = 10，PC = 20，半成品 = 30

TPU 亮甲注塑 = NBA1010
PC 亮甲注塑 = NBA1020
```

其中：

1. `PROC_INJECTION` 这类编码是系统工序库技术编码，用于识别工序主数据。
2. `NBA1010` 这类编码是业务产品工序编码，用于现场、资料、BOM、工艺路线展示和追溯。
3. 两者不能混在一个字段里，否则后续既查不清工序库，也查不清产品工序业务编码。
4. 默认编码规则覆盖大部分场景，但填写工艺路线时允许用户人工修改业务工序编码；人工修改后的编码仍必须由后端校验并保存修改标识。

## 4. 推荐方案

采用“编码字典 + 工序行字段 + 后端默认生成业务编码 + 人工覆盖校验”的方案。

### 4.1 字典设计

不要把 `10/20/30/40` 写死在前端组件里，应在“系统管理 - 编码管理”或“基础资料 - 工艺管理”中维护。

建议至少拆成三类字典：

| 字典类型 | 示例 | 说明 |
| --- | --- | --- |
| `PROCESS_STAGE_PREFIX` | 工序阶段 = `N` | 用于把产品短编码 `BA` 转成工序阶段产品编码 `NBA`。 |
| `PROCESS_OPERATION_CODE` | 注塑 `10`、注塑组装 `11`、打印 `20`、喷油 `30`、产品品组装 `40`、CNC `51`、贴磁铁 `52` | 表示工艺/工序类别编码。 |
| `PROCESS_MATERIAL_STATUS_CODE` | TPU `10`、TPU1 `11`、PC `20`、PC1 `21`、PC2 `22`、PC3 `23`、PC4 `24`、PC5 `25`、半成品 `30` | 表示材料或中间状态编码；`成品` 不放入此字典，改由 `finishedProductFlag` 表达。 |

### 4.2 工序行字段设计

在项目工艺路线的每一行工序中增加：

| 字段 | 前端字段 | 后端字段建议 | 说明 |
| --- | --- | --- | --- |
| 工艺编码 | `operationCraftCode` | `operation_craft_code` | 例如注塑 `10`，来自工序库或工艺编码字典。 |
| 材料/状态编码 | `materialStatusCode` | `material_status_code` | 例如 TPU `10`、PC `20`、半成品 `30`，不包含成品。 |
| 是否成品 | `finishedProductFlag` | `finished_product_flag` | 勾选后表示该工序输出成品。 |
| 产品工序业务编码 | `businessOperationCode` | `business_operation_code` | 例如 `NBA1010`，系统按默认规则生成，用户填写工艺路线时可人工修改。 |
| 是否人工改码 | `businessOperationCodeManualFlag` | `business_operation_code_manual_flag` | 标识该业务编码是否被人工覆盖，便于审计和后续维护。 |

如果第一期不新增数据库列，可临时放入 `process_param_json`，但企业级建议后续落为明确列，便于唯一校验、查询、导出和文件归档引用。

### 4.3 勾选“成品”的联动规则

推荐交互：

1. 工序行新增一列“成品”，使用 `el-checkbox` 或 `el-switch`。
2. 用户勾选“成品”时：
   - `finishedProductFlag = true`
   - 不修改 `materialStatusCode`
   - 材料/状态仍由用户选择 TPU、PC、半成品等
   - `businessOperationCode` 按当前材料/状态刷新默认预览，但用户可人工修改
3. 用户取消勾选时：
   - `finishedProductFlag = false`
   - 不清空材料/状态
4. 材料/状态下拉中不提供“成品 / 40”。
5. 用户修改材料/状态时，只刷新默认编码预览；如果用户已经人工改过编码，需要提示“是否用系统默认编码覆盖人工编码”。

### 4.4 编码生成规则

编码由后端按默认规则生成，前端可做预览；填写工艺路线时允许人工修改：

```text
businessOperationCode =
  processStagePrefix + productShortCode + operationCraftCode + materialStatusCode
```

示例：

| 产品 | 产品短编码 | 工序阶段前缀 | 工艺 | 材料/状态 | 生成编码 |
| --- | --- | --- | --- | --- | --- |
| 亮甲 | BA | N | 注塑 `10` | TPU `10` | `NBA1010` |
| 亮甲 | BA | N | 注塑 `10` | PC `20` | `NBA1020` |
| 亮甲 | BA | N | 注塑 `10` | 半成品 `30` | `NBA1030` |
| 亮甲 | BA | N | 打印 `20` | PC `20` | `NBA2020` |
| 亮甲 | BA | N | CNC `51` | PC `20` | `NBA5120` |

待确认点：

1. 当前系统里的 `Product.productCode` 可能是 `NBA4030` 这类完整产品编码，不一定等于用户口径里的短编码 `BA`。
2. 企业级落地时建议新增或明确 `productShortCode`，不要靠前端截取字符串。
3. 如果产品编码已经包含 `N` 前缀，后端生成时要避免重复生成 `NNBA...`。
4. 人工修改后的 `businessOperationCode` 是否必须仍符合 `N + 产品短编码 + 工艺编码 + 材料/状态编码`，需要业务确认；建议第一期允许偏离默认规则，但必须填写修改原因。

### 6.3 前端联动逻辑草稿

```ts
function handleFinishedProductChange(operation: ProcessOperationSavePayload) {
  operation.businessOperationCode = resolveEditableBusinessOperationCode(operation)
}

function handleMaterialStatusChange(operation: ProcessOperationSavePayload) {
  operation.businessOperationCode = resolveEditableBusinessOperationCode(operation)
}

function resolveEditableBusinessOperationCode(operation: ProcessOperationSavePayload) {
  if (operation.businessOperationCodeManualFlag && operation.businessOperationCode?.trim()) {
    return operation.businessOperationCode.trim().toUpperCase()
  }
  return previewOperationBusinessCode(operation)
}

function markBusinessOperationCodeManual(operation: ProcessOperationSavePayload) {
  operation.businessOperationCodeManualFlag = Boolean(operation.businessOperationCode?.trim())
}

function previewOperationBusinessCode(operation: ProcessOperationSavePayload) {
  const productShortCode = props.productShortCode || deriveProductShortCode(props.productCode)
  const operationCraftCode = operation.operationCraftCode || findCraftCodeByOperation(operation.operationMasterProcessId)
  const materialStatusCode = operation.materialStatusCode || ''
  if (!productShortCode || !operationCraftCode || !materialStatusCode) return ''
  return `N${productShortCode}${operationCraftCode}${materialStatusCode}`.toUpperCase()
}
```

注意：`previewOperationBusinessCode` 只能用于前端默认预览；用户人工修改后前端提交人工值，最终保存结果仍必须以后端返回为准。

### 7.2 编码生成服务草稿

建议独立出一个小服务或方法，避免编码拼接散落在 Controller、Service、Vue 中。

```java
private String buildBusinessOperationCode(ProductEntity product,
                                          ProcessEntity operationMaster,
                                          ProcessOperationDTO dto) {
    String productShortCode = resolveProductShortCode(product);
    String stagePrefix = codeDictionaryService.getRequiredCode("PROCESS_STAGE_PREFIX", "PROCESS_OPERATION");
    String operationCraftCode = resolveOperationCraftCode(operationMaster, dto);
    String materialStatusCode = resolveMaterialStatusCode(dto);

    if (!StringUtils.hasText(productShortCode)) {
        throw new BusinessException(ErrorCodeConstants.VALIDATION_ERROR, "product short code is required");
    }
    if (!StringUtils.hasText(operationCraftCode)) {
        throw new BusinessException(ErrorCodeConstants.VALIDATION_ERROR, "operation craft code is required");
    }
    if (!StringUtils.hasText(materialStatusCode)) {
        throw new BusinessException(ErrorCodeConstants.VALIDATION_ERROR, "material/status code is required");
    }
    String defaultCode = (stagePrefix + productShortCode + operationCraftCode + materialStatusCode).toUpperCase();
    if (Boolean.TRUE.equals(dto.getBusinessOperationCodeManualFlag())
        && StringUtils.hasText(dto.getBusinessOperationCode())) {
        return dto.getBusinessOperationCode().trim().toUpperCase();
    }
    return defaultCode;
}
```

## 8. 目标效果

实施后用户看到的效果：

1. 工艺路线弹窗工序行右侧多一个“成品”勾选项。
2. 用户勾选“成品”后，只改变该行成品标识，不改变材料/状态。
3. 行内产品工序编码按默认规则预览，例如 `NBA1010`、`NBA1020`，并允许人工修改。
4. 选择 TPU 时编码为 `NBA1010`，选择 PC 时编码为 `NBA1020`。
5. 工序库仍显示工序名称和系统工序编码，例如“注塑成型 / PROC_INJECTION”，但项目工艺路线展示业务编码，例如 `NBA1010`。
6. 文件中心、项目中心、工艺管理后续都能通过同一套后端字段展示产品工序业务编码。
7. 材料/状态字典不再包含成品；成品只作为独立勾选标识。

### 9.1 工序行成品勾选

1. 启动前端和后端。

2. 选择“注塑”。
3. 材料/状态选择 PC。

1. 产品工序编码显示 `NBA1020`。

### 9.3 人工修改工序编码

4. 保存并刷新页面。

合格标准：

1. 前端允许编辑产品工序编码。
2. 保存时后端校验该编码在当前产品/项目工艺路线范围内不重复。
3. 刷新后显示人工修改后的 `NBA10A1`。
4. 该工序保存 `businessOperationCodeManualFlag=true` 或等价审计标识。

3. 查看材料/状态编码字典。

合格标准：

1. 工艺编码包含注塑 `10`、注塑组装 `11`、打印 `20`、喷油 `30`、产品品组装 `40`、CNC `51`、贴磁铁 `52`。
2. 材料/状态编码包含 TPU `10`、PC `20`、半成品 `30`。
3. 材料/状态编码不显示“成品 / 40”。
4. 如历史数据存在 `PET=40` 或 `成品=40`，应在后续数据清洗中迁移为独立成品标识。

### 9.5 保存与回显

测试步骤：

1. 新建包含 TPU 注塑、PC 注塑、成品工序的工艺路线。
2. 保存。
3. 刷新页面。
4. 重新打开该工艺路线。

合格标准：

1. 所有工序行的产品工序编码保存后不丢失。
2. 成品勾选状态保存后不丢失。
3. 材料/状态保存后不丢失。
4. 控制台无 400、404、500。
5. 自动生成编码和人工修改编码都能回显；如后端返回与前端预览不一致，前端以后端返回为准。

## 10. 企业级开发判断

| 维度 | 判断 |

## 11. 风险与待确认

1. `BA` 是产品短编码还是 `Product.productCode` 的一部分，需要确认。当前 seed 中存在 `NBA4030` 这类完整编码，不应前端硬截。
2. `N` 是所有产品工序阶段固定前缀，还是不同阶段可配置，需要确认。
3. “产品品组装”是否应命名为“产品组装”或“成品组装”，需要业务确认。
4. 历史 `PET=40` 或 `成品=40` 是否需要清洗为 `finishedProductFlag=true`，需要确认。
5. 同一路线是否允许多个“成品”工序。建议第一期允许多个输出分支，但发布门禁提示业务确认。
6. 如果后续文件中心按产品工序编码归档资料，则附件上传时也应增加 `businessOperationCode` 或 `processId` 绑定。

## 12. 后续维护建议

1. 工艺编码、材料/状态编码统一由编码管理维护，必须支持启用、停用、排序、备注。
2. 工序库维护时应选择工艺编码；项目工艺路线默认继承并自动生成业务编码，但允许用户在填写工艺路线时人工修改业务编码。
3. 产品短编码应作为 Product 的明确字段维护，例如 `productShortCode`，避免从展示名称或长编码中截取。
4. 项目工艺路线保存时以后端最终保存编码为准；自动生成和人工修改都必须保存后重新拉取详情。
5. 成品标识后续可参与发布门禁：最终确认的工艺路线至少应有一个成品输出工序。
6. 历史 `PROC_...` 编码继续保留为系统工序库编码，不要直接替换为 `NBA1010`，否则会破坏工序库引用关系。
