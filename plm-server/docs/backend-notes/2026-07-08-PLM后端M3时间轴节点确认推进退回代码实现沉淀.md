字段作用：

```text

timeline_last_reason：最近一次备注或退回原因。
timeline_last_operated_at：最近一次操作时间。
timeline_last_operator_user_id / name：最近一次操作人。
```

## 5. 接口实现

### 5.1 confirm

```http
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/confirm
```

规则：

```text
只能确认 current 节点。
确认后 current_step_no 不变。
写 timeline_current_confirmed=true。
写 timeline_confirmed_node_key=nodeKey。
写 TIMELINE_CONFIRM 操作日志。
```

合格响应：

```text
code=0
data.action=confirm
data.currentStepNo 不变
data.currentConfirmed=true
data.logId 有值
```

### 5.2 advance

```http
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/advance
```

规则：

```text
只能推进 current 节点。
必须先 confirm 当前节点。
最后节点不能继续推进。
推进后 current_step_no + 1。
推进后 timeline_current_confirmed=false。
推进后 timeline_confirmed_node_key=null。
按节点更新 Product.status。
写 TIMELINE_ADVANCE 操作日志。
```

状态映射：

```text
stepNo <= 1 -> draft
中间节点 -> developing
最后节点 -> reviewing
released 仍由发布接口处理，不由 M3 advance 直接发布。
```

合格响应：

```text
code=0
data.action=advance
data.currentStepNo > data.beforeStepNo
data.currentConfirmed=false
data.logId 有值
```

### 5.3 return

```http
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/return
```

规则：

```text
只能从 current 节点退回。
reason 必填。
returnToPrevious=true 时退回上一节点。
第一个节点不能退回上一节点。
returnToPrevious=false 时只记录当前节点退回修改原因，不改变 current_step_no。
退回后 timeline_current_confirmed=false。
退回后 timeline_confirmed_node_key=null。
写 TIMELINE_RETURN 操作日志。
```

合格响应：

```text
code=0
data.action=return
data.currentConfirmed=false
data.logId 有值
```

## 6. 核心代码逻辑

### 6.1 当前节点校验

`TimelineActionServiceImpl.requireCurrentNode` 统一完成：

```text
查询 Product。
根据 productType 取 TimelineNodeConstants 中的节点定义。
规范化 currentStepNo。
取当前节点定义。
比较 path nodeKey 与当前节点 nodeCode。
不一致时抛 STATUS_TRANSITION_ILLEGAL。
```

这样保证：

```text
不能操作非 current 节点。
不能跳过节点。
confirm / advance / return 三个动作使用同一套当前节点判断。
```

### 6.2 成功动作写日志

`TimelineActionServiceImpl.writeLog` 调用：

```text
OperationLogService.logSuccess(...)
```

写入字段：

```text
action=TIMELINE_CONFIRM / TIMELINE_ADVANCE / TIMELINE_RETURN
businessType=PRODUCT
businessId=productId
businessCode=productCode
businessName=productName
detailJson=节点、step、reason/remark、from/to 信息
```

业务校验全部在写日志之前执行，所以失败动作不会写成功日志。

### 6.3 查询增强

`GET /api/v1/projects/{projectId}/timeline` 现在额外返回：

```text
currentConfirmed
confirmedNodeKey
lastAction
lastReason
lastOperatedAt
lastOperatorUserId
lastOperatorUserName
nodes[].confirmed
```

`nodes[].confirmed` 第一阶段只标记当前已确认节点，不聚合历史节点确认。

### 9.2 OperationLog

```sql
select
    log_id,
    request_id,
    operator_user_id,
    operator_user_name,
    action,
    business_type,
    business_id,
    business_code,
    business_name,

where business_type = 'PRODUCT'

detail_json 包含 nodeKey / fromStepNo / toStepNo / reason 或 remark。
```

## 10. 维护注意事项

1. 当前实现没有新增流程实例表，完整历史以 `plm_operation_log` 为准。
2. 如果后续需要节点级历史查询、多人会签、节点审批意见，再新增 `plm_timeline_action`。
3. 当前 `advance` 不会把 Product.status 改为 `released`，正式发布仍由发布接口处理。
4. 当前权限沿用 M1 的当前用户和全权限简化模型，后续 RBAC 成熟后再加工程部专项权限。
5. 如果多人同时操作同一项目，后续建议加入乐观锁条件更新，避免重复推进。
6. APIFOX 测试时必须先确认服务启动时安全开关为启用状态，否则未登录拦截无法验收。
