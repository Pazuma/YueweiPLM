# PLM 钉钉出站中间服务方案 B 实施方案

日期：2026-07-29

## 1. 目标

采用方案 B：新增一个独立的钉钉出站中间服务，不把钉钉审批 API 细节直接写进 PLM 后端。

目标链路：

```text
钉钉实际审批表提交
-> PLM 创建新型号项目
-> PLM 新型号项目流程走到 运模 / MODEL_VARIANT_MOLD_TRANSFER
-> PLM 项目归档
-> PLM 调用 DINGTALK_OUTBOUND_ENDPOINT
-> 钉钉出站中间服务查询当前待办 taskId
-> 钉钉出站中间服务代审批人同意
-> 钉钉审批继续流转到后续节点
```

第一版只要求跑通新型号线代同意：

```text
workflow-task-lookup
agree
```

新产品线完成抄送：

```text
cc
```

先保留接口动作和配置位，后续再接钉钉通知能力。

## 2. 为什么选择方案 B

当前 401 和 404 的排查结论：

1. `401 未登录或登录已失效`：说明钉钉连接器已经能打到远程服务，但被 PLM 登录鉴权拦截。
2. 加上 `Authorization` 后变成 `404 资源不存在`：说明 cpolar 后面转发到了 PLM 后端，但 PLM 没有 `/api/dingtalk/outbound` 这个接口。
3. PLM 当前入站接口只负责创建项目，不负责代同意钉钉审批。

因此，出站代同意不应该继续配置到 PLM 入站接口，而应该单独部署一个中间服务：

```text
dingtalk-outbound-connector
```

好处：

- PLM 保持项目流程、归档、集成记录沉淀职责。
- 钉钉中间服务专门处理 access token、taskId 查询、审批同意、钉钉错误码。
- 钉钉 API 变化时，只维护中间服务，不影响 PLM 主流程。
- 生产排障更清晰：PLM 看 outbound 记录，中间服务看钉钉 API 日志。

## 3. 总体架构

```text
+------------------+        +--------------------+        +---------------------------+
| 钉钉实际审批表    | -----> | PLM Server          | -----> | dingtalk-outbound-connector |
| 创建新型号项目    |        | 项目流程到运模归档  |        | 查询 taskId / 代同意         |
+------------------+        +--------------------+        +---------------------------+
                                                                  |
                                                                  v
                                                        +------------------+
                                                        | 钉钉审批 API      |
                                                        +------------------+
```

部署后，PLM 的环境变量配置为：

```env
DINGTALK_OUTBOUND_ENDPOINT=http://dingtalk-outbound-connector:8090/api/dingtalk/outbound
```

如果通过 cpolar 调试，则 cpolar 应转发到中间服务端口 `8090`，而不是 PLM 后端 `8080`：

```text
http://35487b62.r31.cpolar.top/api/dingtalk/outbound
```

## 4. 服务职责边界

### 4.1 PLM Server 负责

- 接收钉钉实际审批表入站数据。
- 创建新型号项目。
- 维护新型号 PLM 时间线。
- 在 `MODEL_VARIANT_MOLD_TRANSFER / 运模` 完成时归档项目。
- 向 `DINGTALK_OUTBOUND_ENDPOINT` 发送出站 payload。
- 在 `plm_integration_record` 中记录出站结果。

PLM 不直接做：

- 钉钉 access token 获取。
- 钉钉审批任务查询。
- 钉钉审批同意 API 调用。
- 钉钉接口错误码细节解析。

### 4.2 dingtalk-outbound-connector 负责

- 暴露统一 HTTP 接口：

```text
POST /api/dingtalk/outbound
```

- 根据 `action` 分发：

| action | 第一版状态 | 说明 |
| --- | --- | --- |
| `workflow-task-lookup` | 必须实现 | 根据审批实例和审批人查当前待办 taskId |
| `agree` | 必须实现 | 根据 taskId 代审批人同意 |
| `cc` | 预留 | 新产品线完成后发送抄送或通知 |

- 管理钉钉开放平台调用所需配置：

```text
DINGTALK_CORP_ID
DINGTALK_APP_KEY
DINGTALK_APP_SECRET
DINGTALK_AGENT_ID
DINGTALK_AUTO_APPROVER_USER_ID
```

- 记录每次请求和钉钉响应日志，便于排查。

## 5. 推荐技术选型

推荐使用 Java Spring Boot 独立小服务。

原因：

- 与 PLM 后端技术栈一致。
- Docker 构建方式一致。
- 日志、配置、部署、排查方式更统一。
- 后续如果需要接入 PLM 内部日志或安全策略，迁移成本低。

建议目录：

```text
D:\work\Yuewei\dingtalk-outbound-connector
```

建议服务端口：

```text
8090
```

建议健康检查：

```text
GET /health
```

建议业务接口：

```text
POST /api/dingtalk/outbound
```

## 6. 接口设计

### 6.1 统一入口

```http
POST /api/dingtalk/outbound
Content-Type: application/json
```

建议增加一个内部 token，避免外部任意调用：

```http
Authorization: Bearer ${DINGTALK_OUTBOUND_TOKEN}
```

第一版如果只在 Docker 内网调用，也建议保留 token 校验，但可以先用固定配置值：

```env
DINGTALK_OUTBOUND_TOKEN=dev-outbound-token
```

### 6.2 workflow-task-lookup 请求

PLM 发送：

```json
{
  "action": "workflow-task-lookup",
  "projectId": 42,
  "projectCode": "PRD-xxx",
  "projectName": "HR X8D",
  "productType": "model_variant",
  "model": "HR X8D",
  "nodeKey": "MODEL_VARIANT_MOLD_TRANSFER",
  "nodeName": "运模",
  "sourceApprovalInstanceId": "钉钉审批实例ID",
  "processCode": "PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C",
  "processInstanceId": "钉钉审批实例ID",
  "approvalInstanceId": "钉钉审批实例ID",
  "actionerUserId": "02356802443226388318"
}
```

中间服务返回：

```json
{
  "status": "success",
  "taskId": "钉钉当前待办任务ID",
  "approvalInstanceId": "钉钉审批实例ID"
}
```

PLM 当前兼容读取：

```text
taskId
approvalTaskId
task_id
id
```

所以只要返回 `taskId` 即可。

### 6.3 agree 请求

PLM 发送：

```json
{
  "action": "agree",
  "projectId": 42,
  "projectCode": "PRD-xxx",
  "projectName": "HR X8D",
  "productType": "model_variant",
  "model": "HR X8D",
  "nodeKey": "MODEL_VARIANT_MOLD_TRANSFER",
  "nodeName": "运模",
  "sourceApprovalInstanceId": "钉钉审批实例ID",
  "processCode": "PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C",
  "processInstanceId": "钉钉审批实例ID",
  "approvalInstanceId": "钉钉审批实例ID",
  "taskId": "钉钉当前待办任务ID",
  "actionerUserId": "02356802443226388318",
  "result": "agree",
  "remark": "PLM 运模已完成，项目已归档，自动代同意钉钉等待节点"
}
```

中间服务返回：

```json
{
  "status": "success",
  "approvalInstanceId": "钉钉审批实例ID",
  "taskId": "钉钉当前待办任务ID",
  "message": "agreed"
}
```

PLM 会把 `status` 作为 `external_status` 保存到 `plm_integration_record`。

### 6.4 错误返回

建议所有业务错误返回 HTTP 200，并在 body 中表达业务失败：

```json
{
  "status": "failed",
  "errorCode": "DINGTALK_TASK_NOT_FOUND",
  "message": "未找到当前审批人的待办任务",
  "approvalInstanceId": "钉钉审批实例ID"
}
```

原因：

- 钉钉连接器调试页经常要求 HTTP 状态码必须是 200。
- PLM 出站客户端会读取 body 中的 `status`。
- 远程网络级错误才返回 4xx/5xx，例如 token 缺失、路径不存在、服务不可用。

## 7. 钉钉 API 能力要求

中间服务需要具备以下能力：

### 7.1 获取 access token

输入配置：

```text
DINGTALK_APP_KEY
DINGTALK_APP_SECRET
```

服务启动后按需获取钉钉 access token，并缓存过期时间。

维护要求：

- token 过期前主动刷新。
- 调用钉钉接口遇到 token 过期错误时刷新后重试一次。
- 日志中不要打印 appSecret 和完整 accessToken。

### 7.2 查询当前待办 taskId

输入：

```text
approvalInstanceId
actionerUserId
```

目标：

```text
找到该审批实例当前等待 actionerUserId 处理的任务 ID
```

查询结果需要过滤：

```text
审批实例 ID 匹配
审批人 userId 匹配
任务状态为待处理
```

如果钉钉接口不能直接查到待办任务，备选方案：

1. 钉钉实际审批表入站时直接映射 `taskId` 给 PLM。
2. 中间服务监听钉钉审批任务事件，维护 `approvalInstanceId -> taskId` 缓存或数据库表。
3. 中间服务通过审批实例详情接口解析当前待办节点。

第一版优先使用当前可用的钉钉连接器变量直接传 `taskId`，中间服务实现 `agree`；再补 `workflow-task-lookup`。

### 7.3 代审批人同意

输入：

```text
taskId
actionerUserId
result = agree
remark
```

目标：

```text
以 actionerUserId 对应审批人身份，执行当前待办任务同意动作
```

前置条件：

- `actionerUserId` 必须是当前等待节点的审批人。
- 应用必须具备调用审批任务接口的权限。
- 当前审批实例必须正在等待该任务处理。

## 8. Docker Compose 配置

建议新增服务：

```yaml
dingtalk-outbound-connector:
  build:
    context: ./dingtalk-outbound-connector
    dockerfile: Dockerfile
  container_name: dingtalk-outbound-connector
  environment:
    SERVER_PORT: "8090"
    DINGTALK_CORP_ID: "${DINGTALK_CORP_ID:-}"
    DINGTALK_APP_KEY: "${DINGTALK_APP_KEY:-}"
    DINGTALK_APP_SECRET: "${DINGTALK_APP_SECRET:-}"
    DINGTALK_AGENT_ID: "${DINGTALK_AGENT_ID:-}"
    DINGTALK_AUTO_APPROVER_USER_ID: "${DINGTALK_AUTO_APPROVER_USER_ID:-02356802443226388318}"
    DINGTALK_OUTBOUND_TOKEN: "${DINGTALK_OUTBOUND_TOKEN:-dev-outbound-token}"
  ports:
    - "${DINGTALK_OUTBOUND_PORT:-8090}:8090"
  restart: unless-stopped
  networks:
    - plm-net
```

PLM server 环境变量：

```yaml
server:
  environment:
    DINGTALK_OUTBOUND_ENDPOINT: "${DINGTALK_OUTBOUND_ENDPOINT:-http://dingtalk-outbound-connector:8090/api/dingtalk/outbound}"
```

根目录 `.env`：

```env
DINGTALK_OUTBOUND_ENDPOINT=http://dingtalk-outbound-connector:8090/api/dingtalk/outbound
DINGTALK_OUTBOUND_PORT=8090
DINGTALK_OUTBOUND_TOKEN=dev-outbound-token
DINGTALK_AUTO_APPROVER_USER_ID=02356802443226388318

DINGTALK_CORP_ID=你的corpId
DINGTALK_APP_KEY=你的appKey
DINGTALK_APP_SECRET=你的appSecret
DINGTALK_AGENT_ID=你的agentId
```

## 9. cpolar 调试方式

如果要从钉钉开发者平台直接调试中间服务，则 cpolar 必须转发到中间服务端口：

```powershell
cpolar http 8090
```

钉钉执行动作接口路径填写：

```text
POST http://你的cpolar域名/api/dingtalk/outbound
```

HTTP 请求头：

```json
{
  "Content-Type": "application/json",
  "Authorization": "Bearer dev-outbound-token"
}
```

请求体调试值：

```json
{
  "action": "agree",
  "approvalInstanceId": "实际审批实例ID",
  "processInstanceId": "实际审批实例ID",
  "taskId": "当前待办任务ID",
  "actionerUserId": "02356802443226388318",
  "result": "agree",
  "remark": "PLM运模已完成，自动同意"
}
```

如果返回 401：

```text
Authorization 不正确，检查 DINGTALK_OUTBOUND_TOKEN。
```

如果返回 404：

```text
cpolar 没转到中间服务，或接口路径不是 /api/dingtalk/outbound。
```

如果返回 200 但钉钉没流转：

```text
中间服务没有真正调用钉钉同意接口，或 taskId/actionerUserId 不匹配当前待办任务。
```

## 11. 日志排查

PLM 日志：

```powershell
docker compose logs --tail=300 server | Select-String -Pattern "DingTalk project completion return|workflow-task-lookup|taskId|dry_run|model_variant_mold_transfer_completed|ERROR|WARN" -Context 3,6
```

中间服务日志：

```powershell
docker compose logs --tail=300 dingtalk-outbound-connector
```

关键字段：

```text
approvalInstanceId
taskId
action
actionerUserId
dingTalkErrorCode
dingTalkErrorMessage
```

排查优先级：

1. PLM 是否生成 outbound 记录。
2. PLM outbound payload 是否包含 `approvalInstanceId` 和 `taskId`。
3. 中间服务是否收到请求。
4. 中间服务是否拿到钉钉 access token。
5. `taskId` 是否属于 `actionerUserId` 当前待办。
6. 钉钉接口是否返回成功。

## 12. 最小可用版本范围

第一版只实现：

- `GET /health`
- `POST /api/dingtalk/outbound`
- `action=agree`
- `action=workflow-task-lookup` 的接口结构和日志
- access token 获取和缓存
- 钉钉同意接口调用
- 明确错误返回

第一版可以先不实现：

- 前端页面。
- 数据库持久化。
- 管理后台重试。
- 新产品线 `cc` 正式通知。
- 多租户、多企业组织隔离。

这些内容后续在服务稳定后再补。

## 13. 后续维护建议

1. 生产环境不要使用 `dev-outbound-token`，必须换成随机强 token。
2. appSecret、outbound token 只放 `.env` 或服务器密钥配置，不写入代码和文档示例以外的位置。
3. 中间服务日志不要打印完整 access token。
4. 钉钉审批模板调整审批节点后，必须重新验证 `taskId` 查询和 `actionerUserId` 权限。
5. 如果钉钉不支持直接查询当前任务，优先让实际审批表入站时映射 `taskId`。
6. `cc` 能力接入前，新产品线完成抄送可以继续只记录 PLM outbound，等通知服务完成后再打开真实发送。
7. 后续可以增加一个只读日志表或文件日志归档，用于审计每次代同意请求。

## 14. 本方案结论

方案 B 可行，且是更稳的长期方案。

当前不要再把钉钉执行动作地址指向 PLM 后端。应新增并部署：

```text
dingtalk-outbound-connector
```

然后让：

```text
DINGTALK_OUTBOUND_ENDPOINT=http://dingtalk-outbound-connector:8090/api/dingtalk/outbound
```

cpolar 调试时也必须转发到该中间服务，而不是 PLM 后端。
