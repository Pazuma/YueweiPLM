## 5. 代码逻辑说明

前端请求仍统一从 `request.ts` 进入，基础地址为：

```text
${VITE_API_BASE_URL}/api/v1
```

本地验证时使用：

```text
VITE_API_BASE_URL=http://localhost:8080
```

M1 登录成功后，后端返回 token 和 user。前端保存 token 到 `localStorage.plm_token`，后续请求由请求拦截器自动加：

```text
Authorization: Bearer {token}
```

M2 项目当前按后端约定处理为 Product-as-project：

```text
projectId = productId
```

项目中心和工作台都不引入新的项目主对象，只把后端 Product 视图映射成前端现有项目展示结构。

## 6. 作用功能

- 登录页可以使用后端 M1 账号登录。
- 刷新页面时可以通过 `/auth/profile` 恢复当前用户。
- 退出登录会通知后端并清理前端状态。
- 首页进行中项目来自后端 M2 工作台接口。
- 项目中心列表来自后端 M2 项目列表接口。
- 项目详情中的当前节点和时间轴可以使用 M2 时间轴查询结果。
- M3 动作不会误连到未完成前端验证的接口，避免用户误以为确认、推进、退回已经可在前端使用。

## 9. 本地环境修复记录

首次验证 M2 接口时，登录和 profile 正常，但：

```text
GET /api/v1/workbench/projects/in-progress -> 500
GET /api/v1/projects -> 500
```

排查结果：

```text
当前后端 Product 实体已经包含 M3 的 timeline_* 字段。
本地 PostgreSQL 的 plm_product 表只有 M2 的 current_step_no，缺少 timeline_* 列。
MyBatis Plus 查询 Product 时会按实体字段查询，导致 M2 查询也被缺列拖成 500。
```

处理方式：

```text
执行仓库内幂等迁移 V20260708_1000__m3_timeline_actions.sql 的 ALTER TABLE 部分，补齐本地开发库 timeline_* 列。
前端仍未接入 M3 动作接口。
```

补齐后验证：

```text
information_schema.columns 中已存在 7 个 timeline_* 列。
M2 工作台、项目列表、summary、detail、timeline 均恢复 code=0。
```

注意：

```text
当前 src/main/resources/db/migration 目录只是迁移脚本沉淀，项目尚未接入 Flyway 自动迁移。
后续如果新环境复现 M2 500，应优先检查数据库结构是否包含 current_step_no 和 timeline_* 列。
```

## 10. 未自动覆盖的人工前端点测项

本次环境没有可调用的浏览器自动化工具，且前端项目未安装 Playwright，因此没有宣称完成浏览器点击流自动化验证。

需要人工在浏览器确认：

- 登录按钮点击后是否正常跳转。
- 首页进行中项目卡片是否按预期渲染。
- 项目中心列表字段是否符合业务展示预期。
- 打开项目详情后，时间轴视觉状态是否正确。
- 刷新页面后是否仍保持登录态。
- 点击退出登录后是否清理 token 并返回登录页。

这些人工测试的合格标准见第 7 节。

## 11. 后续维护建议

- 后端正式接入 Flyway 或统一数据库迁移执行机制，避免实体字段领先数据库结构导致接口 500。
- M3 前端接入前，先完成 Apifox 或后端集成测试验证，再把 `confirmTimelineNode()`、`advanceTimelineNode()`、`returnTimelineNode()` 切换为真实请求。
- 项目中心仍有部分详情展示来自原有 presentation fallback，后续 M4/M5 如果补齐 BOM、文档、成本等接口，应逐步替换为真实数据。
- 前端构建出现大 chunk 警告，后续可按路由或 Element Plus 做更细的分包优化。
