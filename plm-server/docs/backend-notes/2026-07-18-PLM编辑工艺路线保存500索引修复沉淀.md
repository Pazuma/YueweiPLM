# 2026-07-18 PLM 编辑工艺路线保存 500 索引修复沉淀

## 1. 问题现象

前端在“编辑工艺路线”弹窗点击“保存完整路线”时，请求：

```text
PUT /api/v1/process-routes/{processId}
```

返回 500。截图中实际失败接口为：

```text
PUT http://localhost:5173/api/v1/process-routes/58
500 Internal Server Error
```

## 2. 规则来源

1. `D:\Yuewei\资料\PLM\docs\README.md`：Process 是七个核心对象之一，承载工艺路线与工序。
2. `D:\Yuewei\资料\PLM\docs\05-数据模型与编码规范.md`：业务表使用 `deleted_flag` 软删除，编码字段使用 `xxx_code`。
3. `D:\Yuewei\资料\PLM\docs\modules\06-工艺路线管理.md`：工艺路线由 Product + Process + version_no 决定，工序可编辑、可追溯。
4. 现有后端代码 `ProcessRouteServiceImpl.update`：编辑路线时采用软删除旧工序后重建新工序。

## 3. 根因

早期迁移 `V20260710_1000__m4_bom_process_attachment.sql` 创建了 `process_code` 全局唯一索引：

```sql
create unique index if not exists uk_plm_process_code
    on plm_process (process_code)
    where process_code is not null;
```

但后端编辑路线的逻辑是：

1. 更新路线主记录。
2. `softDeleteOperations(processId)` 将旧工序设置为 `deleted_flag=1`。
3. `rebuildOperations(...)` 重新插入新工序。

旧工序虽然已软删除，但全局唯一索引仍然占用旧的 `process_code`。新工序重建时使用同样的 `process_code`，数据库抛唯一约束异常，接口最终表现为 500。

## 4. 修改文件

### 4.1 新增迁移

`src/main/resources/db/migration/V20260718_1002__process_code_active_unique_index.sql`

```sql
alter table if exists plm_process
    drop constraint if exists uk_plm_process_code;

drop index if exists uk_plm_process_code;

create unique index if not exists uk_plm_process_code
    on plm_process (process_code)
    where process_code is not null and deleted_flag = 0;
```

### 4.2 新增测试

`src/test/java/com/yuewei/plm/module/process/ProcessMigrationContractTest.java`

```java
class ProcessMigrationContractTest {

    @Test
    void processCodeUniqueIndexIgnoresSoftDeletedRows() throws Exception {
        Path migrationPath = Path.of("src/main/resources/db/migration/V20260718_1002__process_code_active_unique_index.sql");

        assertThat(Files.exists(migrationPath)).isTrue();

        String migration = Files.readString(migrationPath).toLowerCase();
        assertThat(migration).contains("alter table if exists plm_process");
        assertThat(migration).contains("drop constraint if exists uk_plm_process_code");

        assertThat(migration).contains("where process_code is not null and deleted_flag = 0");
    }
}
```

## 5. 逻辑说明

修复后，`process_code` 仍然保证“未删除记录唯一”，符合企业级编码不可重复要求。

已软删除的历史工序不再阻塞同一路线编辑重建，数据库唯一索引与服务层 `ensureProcessCodeAvailable(... deleted_flag=0)` 的校验口径保持一致。

## 7. 前端直接验收步骤

1. 重启后端，让 Flyway 执行 `V20260718_1002__process_code_active_unique_index.sql`。
2. 刷新前端并重新登录。
3. 进入项目中心，打开已有工艺路线。
4. 修改路线备注、工艺参数或工序明细。
5. 点击“保存完整路线”。

合格标准：

1. `PUT /api/v1/process-routes/{processId}` 返回 200。
2. 页面不再出现该接口 500。
3. 保存后刷新页面，工序明细仍能回显。
4. 工序编码未出现重复的未删除记录。

## 8. 后续维护建议

1. 所有软删除表的唯一索引应采用“业务编码 + `deleted_flag=0`”的部分唯一索引口径。
2. 服务层唯一性校验必须与数据库索引条件一致，避免服务层认为可保存、数据库层实际拒绝。
3. 工艺路线后续如果改为“差量更新工序”，仍应保留该部分唯一索引，防止历史软删除数据影响编辑。
