# 2026-07-18 PLM 工作台新建工艺路线与产品编码版本化方案沉淀

## 1. 任务理解

本次只生成方案沉淀文档，不修改前端、后端、数据库业务代码。

业务调整目标：

1. 手机壳 PLM 的工艺路线不是随意上传文件，而是由少数几类标准工艺路线组合而成。
2. 标准工艺路线组合参考 `D:\Yuewei\资料\PLM\seeds` 下的种子数据，重点参考 `master_route_seed.json`。
3. 工作台当前“上传工艺路线/上传工艺方案”的业务口径应调整为“新建工艺路线”。
4. 工艺路线编码应由产品编码和对应路线编码派生，并考虑同一产品存在多个工艺路线版本。
5. 工艺路线仍然归入七大核心对象中的 `Process`，不能新增 `Routing` 根对象。

## 5. 目标业务口径

### 5.1 对象口径

工艺路线是 `Process`：

| 业务概念 | 系统表达 |
| --- | --- |
| 工艺路线 | `plm_process.process_type = routing` |
| 工艺路线版本 | `plm_process.version_no` |
| 工艺路线编码 | `plm_process.process_code` |
| 工艺路线下的工序 | `plm_process.process_type = operation`，通过 `parent_process_id` 绑定路线 |
| 工序顺序 | `sequence_no` |
| 工艺参数 | `process_param_json` |
| 质量要求 | `quality_requirement` |

不新增 `Routing`、`Operation` 根对象。

### 5.2 编码口径

建议编码格式：

```text
{product_code}-{route_template_code}-{version_no}
```

示例：

```text
NHA4030-ROUTE-SUPER-CAPITAN-V1
NHA4030-ROUTE-SUPER-CAPITAN-V2
NWV4030-ROUTE-WAVESHELL-V1
```

如果团队希望所有 Process 编码以 `PROC-` 开头，也可采用：

```text
PROC-{product_code}-{route_template_code}-{version_no}
```

推荐先采用不重复前缀的短格式 `{product_code}-{route_template_code}-{version_no}`，原因是 seed 中 `route_code` 已带 `ROUTE-...`，再加 `PROC-` 会让编码过长。最终格式需要业务确认一次，但后端必须统一生成，不能让前端手写。

### 5.3 版本口径

同一产品可存在多条工艺路线版本：

| 场景 | 版本策略 |
| --- | --- |
| 第一次从模板新建 | 默认 `V1` 或模板版本 |
| 同产品同模板再建新版本 | 自动建议下一个版本，例如 `V2` |
| 工艺路线已锁定后需要调整 | 新建版本，不直接修改 locked 版本 |
| 新型号仅有差异工艺 | 可以继承父产品路线后生成差异版本，仍保存为该 Product 下的 Process |

唯一性建议：

```text
product_id + route_template_code + version_no 唯一
process_code 全局唯一
```

如果短期不新增数据库字段 `route_template_code`，也要至少保证：

```text
product_id + process_code 唯一
```

### 5.4 工艺路线、型号颜色、BOM 与最终确认口径

用户在 2026-07-18 补充修正：当前讨论对象是 Product，不包括 SKU。同一个产品最终会确定几条适用的工艺路线；面对不同型号、不同颜色时可能存在多个路线版本，这些版本对应的 BOM 也可能不同，因为型号、颜色、材料、包装或局部工艺存在差异。不能简单理解为“同一个产品最终只有一个默认路线”。

业务规则建议：

| 业务点 | 规则 |
| --- | --- |
| 同一产品多路线版本 | 允许同一 `product_id` 下存在多条 `process_type=routing` 的 Process 版本 |
| 型号/颜色差异 | 型号、颜色差异不新增根对象，作为 Product 的规格/版本维度和 Process/BOM 的适用范围保存 |
| BOM 差异 | BOM 仍作为 Product 下的版本化资料或明细表达，但必须能关联到对应工艺路线版本 |
| 最终确认路线 | 同一产品在项目流程最后一步确认一组最终可用路线，而不是只确认一条默认路线 |
| 确认时机 | 路线新建时只是草稿或候选，最终可用路线清单在项目流程最后一步由业务确认 |
| 发布门禁 | Product 发布或最终投产前，应校验最终确认的路线均为 locked，且每条路线都有匹配 BOM 版本 |
| SKU 边界 | 当前不讨论 SKU，不按 SKU 生成路线；型号、颜色只是 Product 维度下的适用范围 |

推荐数据关系：

```text
Product
  -> Process(process_type=routing, version_no=V1, applicable_model/color, final_selected=true)
      -> Operation(process_type=operation)
      -> Product BOM version A / BOM config for this route
  -> Process(process_type=routing, version_no=V2, applicable_model/color, final_selected=true)
      -> Operation(process_type=operation)
      -> Product BOM version B / BOM config for this route
  -> Process(process_type=routing, version_no=V3, applicable_model/color, final_selected=false)
      -> Operation(process_type=operation)
      -> candidate / history route
```

关键口径：

1. “最终确认路线”是最终被投产、发布、报价、BOM 校验引用的一组路线版本。
2. 未最终确认的版本仍可保留，用于试制、历史追溯或后续切换。
3. BOM 不能只按产品粗粒度判断完整性，还需要判断是否与每条最终确认工艺路线版本匹配。
4. 工作台前期可以新建多个路线版本，最后一步必须有“确认最终工艺路线/BOM 版本清单”的业务动作。
5. 当前方案只描述 Product 下的型号/颜色适用差异，不把 SKU 作为对象、字段或测试粒度。

## 6. 推荐方案

采用“模板选择 + 后端复制成项目 Process”的方案。

### 6.1 核心流程

```text
工作台当前项目
  -> 到达“加工艺/敲定工序”相关小步骤
  -> 点击“新建工艺路线”
  -> 选择标准工艺路线组合
  -> 系统根据 Product.product_code + route_template_code + version_no 生成 process_code
  -> 后端把模板 nodes 复制为 plm_process(operation)
  -> 路线保存为 draft
  -> 工程确认后锁定 locked
  -> 项目中心、工艺路线中心、发布门禁读取同一套 Process 数据
```

### 6.2 为什么不继续用“上传工艺路线”

上传文件只能沉淀附件，无法结构化表达：

1. 哪些工序组成路线。
2. 工序顺序和依赖关系。
3. 工艺参数和质量要求。
4. 路线版本。
5. 后续 BOM、成本、样品、生产资料是否引用的是同一个已锁定路线。

因此工作台应将“工艺路线资料上传”改为“新建工艺路线”，SOP/SIP、测试报告仍保留附件上传。

```java
private String buildRouteProcessCode(Product product, String routeTemplateCode, String versionNo) {
```

```java
        .eq(ProcessEntity::getProductId, productId)
        .eq(ProcessEntity::getProcessCode, processCode)
```

## 8. 数据库与迁移建议

最小改动方案：

1. 继续使用 `plm_process.process_code` 保存最终路线编码。
2. 继续使用 `plm_process.version_no` 保存产品工艺路线版本。
3. 继续用 `process_param_json` 保存模板来源和 edge 信息。

建议增强字段：

```sql
ALTER TABLE plm_process
ADD COLUMN IF NOT EXISTS route_template_code varchar(100),
ADD COLUMN IF NOT EXISTS source_process_id bigint,
```

### 9.4 工艺路线编排界面参考

用户在 2026-07-18 补充界面口径：工艺路线页面可采用“上方画布 + 下方核对表”的双层结构。

目标效果：

1. 上方画布用于编辑草稿路线，支持新增工序节点、调整展示顺序、拖拽位置、连接前置/后置节点。
2. 下方表格用于核对真实后端保存后的节点配置，展示顺序、工序、前置节点、后置节点、并行关系等字段必须来自同一份结构化数据。
3. 画布不是单独数据源，保存前要转换成标准节点表和边表；保存后下方表格重新读取后端返回结果。
4. 用户以画布完成编排，系统以表格确认后端关系，避免“页面画出来了，但后端节点没保存对”的问题。

界面结构建议：

```text
工艺路线编辑页 / 弹窗
├─ 顶部：产品编码、产品名称、路线模板、版本号、最终确认状态、适用型号/颜色、关联 BOM 版本
├─ 上方：可编辑路线画布
│  ├─ 工序节点卡片：工序名、operation_code、顺序号、状态
│  ├─ 连线：前置 -> 后置
│  └─ 操作：新增节点、删除节点、连线、取消连线、自动布局
└─ 下方：后端节点配置核对表
   ├─ 展示顺序
   ├─ 工序
   ├─ 前置节点
   ├─ 后置节点
   ├─ 并行/分支关系
   ├─ 适用型号/颜色
   └─ 后端保存状态
```

下方表格字段建议：

| 字段 | 前端显示 | 后端来源/保存建议 | 说明 |
| --- | --- | --- | --- |
| `displayOrder` | 展示顺序 | 可由 `sequence_no` 或画布排序派生 | 只用于页面顺序，不一定等于执行依赖 |
| `operationCode` | 工序编码 | `process_code` 或模板 `operation_code` | 例如 `PROC_INJ_PC_PART` |
| `operationName` | 工序名称 | `process_name` | 例如“注塑 PC 部件” |
| `predecessorNodeCodes` | 前置节点 | edge 表或 `process_param_json.edges` | 支持多个前置，例如组装依赖 PC/TPU |
| `successorNodeCodes` | 后置节点 | edge 表或 `process_param_json.edges` | 支持多个后置 |
| `relationType` | 关系类型 | `finish_to_start` 等 | 先支持完成后开始 |
| `applicableModel` | 适用型号 | `applicable_model` 或 JSON | 型号差异路线使用 |
| `applicableColor` | 适用颜色 | `applicable_color` 或 JSON | 颜色差异路线使用 |
| `backendPersisted` | 保存状态 | 接口返回值派生 | 用于区分草稿编辑和已落库配置 |

前端类型草稿：

```ts
export interface ProcessRouteCanvasNode {
  nodeCode: string
  operationCode: string
  operationName: string
  displayOrder: number
  positionX: number
  positionY: number
  applicableModel?: string
  applicableColor?: string
}

export interface ProcessRouteCanvasEdge {
  edgeNo: number
  fromNodeCode: string
  toNodeCode: string
  relationType: 'finish_to_start'
}

export interface ProcessRouteNodeCheckRow {
  displayOrder: number
  operationCode: string
  operationName: string
  predecessorNodeCodes: string[]
  successorNodeCodes: string[]
  relationType: string
  applicableModel?: string
  applicableColor?: string
  backendPersisted: boolean
}
```

画布转核对表逻辑草稿：

```ts
function buildNodeCheckRows(
  nodes: ProcessRouteCanvasNode[],
  edges: ProcessRouteCanvasEdge[],
  persistedNodeCodes = new Set<string>()
): ProcessRouteNodeCheckRow[] {
  return [...nodes]
    .sort((left, right) => left.displayOrder - right.displayOrder)
    .map((node) => ({
      displayOrder: node.displayOrder,
      operationCode: node.operationCode,
      operationName: node.operationName,
      predecessorNodeCodes: edges
        .filter((edge) => edge.toNodeCode === node.nodeCode)
        .map((edge) => edge.fromNodeCode),
      successorNodeCodes: edges
        .filter((edge) => edge.fromNodeCode === node.nodeCode)
        .map((edge) => edge.toNodeCode),
      relationType: 'finish_to_start',
      applicableModel: node.applicableModel,
      applicableColor: node.applicableColor,
      backendPersisted: persistedNodeCodes.has(node.nodeCode)
    }))
}
```

保存校验建议：

1. 至少存在一个起始节点，即没有前置节点的节点。
2. 至少存在一个结束节点，即没有后置节点的节点。
3. 不允许出现孤立节点，除非整条路线只有一个节点。
4. 不允许出现循环依赖，例如 A -> B -> A。
5. 同一路线内 `nodeCode`、`operationCode + displayOrder` 不重复。
6. 保存后必须重新调用后端详情接口，用后端返回数据刷新画布和下方表格。

企业级实现建议：

1. 第一阶段可不引入复杂流程图库，用表格和简易节点卡片完成数据闭环。
2. 第二阶段再引入成熟画布库，例如 Vue Flow，用于拖拽、连线、自动布局。
3. 无论画布如何实现，后端保存结构必须稳定为节点和边，不能只保存前端坐标。
4. 下方核对表应作为验收主视图，实施测试时以表格关系为准。

## 10. 工作台目标效果

用户在工作台推进项目时看到的效果应是：

1. 当前到达工艺相关小步骤时，页面显示“新建工艺路线”，不是“上传工艺路线”。
2. 点击后可以选择标准路线组合，例如注塑 + 喷油 + 组装包装，或 TPU + 打孔 + 组装包装。
3. 选择模板后自动生成路线名称、路线编码预览、版本号建议和工序明细。
4. 保存后路线状态为 `draft`，项目中心工艺路线 Tab 可立即看到。
5. 锁定后路线状态为 `locked`，发布门禁可识别“已有已锁定工艺路线”。
6. 同一产品再次调整路线时，不覆盖旧路线，而是“新建版本”。
7. 文件资料仍保留上传功能，但上传的是 SOP/SIP、测试报告、确认资料，不承担路线结构本身。
8. 同一产品可保留多个面向型号/颜色差异的路线版本，列表中应清晰展示适用型号、适用颜色、关联 BOM 版本、是否已最终确认。
9. 项目流程最后一步应出现“确认最终工艺路线/BOM 版本清单”的动作，确认后同一产品可保留多条最终路线。

## 11. 企业级开发要求

| 维度 | 要求 |
| --- | --- |
| 对象边界 | 不新增 `Routing` 根对象，全部归入 `Process` |
| 后端校验 | 校验模板存在、模板状态、产品编码、版本号、编码唯一、工序不为空 |
| 状态控制 | `locked` 工艺路线不可直接编辑，只能新建版本 |
| 权限控制 | 工程角色可创建/编辑/锁定，其他角色按只读或审批权限控制 |
| 操作日志 | 创建、编辑、锁定、新建版本全部记录 operation log |
| 版本追溯 | 每个版本独立 `process_id` 和 `process_code`，旧版本不物理删除 |
| 最终确认路线 | 后端应支持同一产品多条 `final_selected=true` 的路线，并记录确认人、确认时间 |
| BOM 联动 | BOM 版本需要绑定工艺路线版本，发布门禁校验最终确认路线与对应 BOM 是否匹配 |
| 可测试性 | API 单测、服务单测、前端 API 单测、组件交互测试、前端整体流程测试 |
| 可维护性 | 模板读取逻辑独立成 service，避免散落在 Controller 或 Vue 组件内 |
| 数据质量 | seed 自动导入前必须先清洗编码和 JSON 格式 |

## 12. 前端直接测试方式与合格标准

本方案后续落地后，按前端整体流程测试，不使用 APIFOX。

### 12.1 新产品线工艺路线创建

测试步骤：

1. 启动后端、本地数据库、前端。
2. 登录系统。
3. 进入工作台，选择一个新产品线项目。
4. 推进到“样品与工艺/加工艺”或“敲定工序”步骤。
5. 点击“新建工艺路线”。
6. 选择一个标准路线组合。
7. 检查路线编码预览是否为 `产品编码 + 路线编码 + 版本号`。
8. 保存。
9. 进入项目中心 -> 工艺路线 Tab 查看。

合格标准：

1. 工作台不再把工艺路线作为普通文件上传。
2. 路线模板可选，选择后工序自动带出。
3. 保存成功后项目中心能看到同一条路线。
4. 路线编码不是时间戳格式。
5. 控制台无 400/500 错误。

### 12.2 同一产品多版本

测试步骤：

1. 在项目中心选择已存在的工艺路线。
2. 点击锁定。
3. 再点击“新建版本”。
4. 输入或选择下一版本号，例如 `V2`。
5. 保存。

合格标准：

1. 旧版本仍存在且只读。
2. 新版本独立展示，编码包含 `V2`。
3. 新版本工序默认继承旧版本或模板。
4. 不能直接编辑 locked 旧版本。

### 12.3 发布门禁联动

测试步骤：

1. 创建一条工艺路线但不锁定。
2. 尝试进入发布/冻结检查。
3. 锁定工艺路线。
4. 再次检查发布门禁。

合格标准：

1. 未锁定时提示缺少已锁定工艺路线。
2. 锁定后门禁中的工艺路线计数增加。
3. 发布门禁读取的是后端 Process 数据，不是前端假数据。

### 12.4 新型号线差异工艺

测试步骤：

1. 创建一个新型号线项目。
2. 推进到“差异组件/工艺确认”步骤。
3. 点击“新建工艺路线”。
4. 选择继承父产品路线或选择差异模板。
5. 保存并查看项目中心。

合格标准：

1. 新型号路线归属到当前 Product。
2. 不覆盖父产品路线。
3. 可清楚看到来源模板/来源版本。
4. 新型号后续可单独锁定、追溯。

### 12.5 最终工艺路线与 BOM 版本清单确认

测试步骤：

1. 在同一产品下创建至少 2 个工艺路线版本，例如 `V1` 和 `V2`。
2. 分别给不同版本配置或关联不同 BOM 版本，例如 BOM `A`、BOM `B`。
3. 将两个工艺路线版本都推进到 locked。
4. 在项目流程最后一步执行“确认最终工艺路线/BOM 版本清单”。
5. 按产品实际型号/颜色/材料/包装差异，选择一条或多条 locked 工艺路线版本，并分别选择匹配的 BOM 版本。
6. 回到项目中心工艺路线列表、BOM 区域和发布门禁查看。

合格标准：

1. 同一产品可以看到多个工艺路线版本，且可有多条显示为“已最终确认”。
2. 最终确认的路线必须是 locked 状态，draft 版本不能进入最终确认清单。
3. 每条最终确认工艺路线都能显示关联 BOM 版本。
4. 如果选择的 BOM 与工艺路线不匹配，前端应提示，后端应拒绝。
5. 项目发布门禁读取最终确认工艺路线清单和对应 BOM 版本，不使用未确认候选版本凑数。
6. 调整最终确认清单时，系统保留旧清单、变更前后差异和操作日志。
7. 测试维度停留在 Product 的型号/颜色适用范围，不以 SKU 作为验收对象。

### 12.6 工艺路线画布与后端节点配置核对

测试步骤：

1. 在工作台或项目中心打开“新建工艺路线”。
2. 选择一个标准路线模板，进入路线编排界面。
3. 在上方画布中调整节点关系，例如“注塑 PC 部件”和“注塑 TPU 部件”都连接到“组装”，“组装”再连接到“打包”。
4. 查看下方核对表，确认“组装”的前置节点显示为两个注塑节点，“打包”的前置节点显示为“组装”。
5. 保存工艺路线。
6. 保存后刷新页面或重新进入该路线详情。
7. 再次查看画布和下方核对表。

合格标准：

1. 上方画布的节点和连线能正确转换成下方表格的前置/后置节点。
2. 保存后下方表格展示的是后端返回的真实节点配置，不是未保存的前端草稿。
3. 重新进入详情后，画布和表格关系一致。
4. 不允许保存循环依赖路线，例如“组装 -> 打包 -> 组装”。
5. 不允许保存孤立节点，除非整条路线只有一个工序。
6. 表格中每行至少能看清展示顺序、工序名称、工序编码、前置节点、后置节点。

| 问题 | 风险 | 建议 |
| --- | --- | --- |
| 最终编码格式是否带 `PROC-` 前缀 | 如果后续 ERP/MES 映射要求固定前缀，早期编码可能需要迁移 | 先由业务确认 `{product_code}-{route_template_code}-{version_no}` 或 `PROC-{product_code}-{route_template_code}-{version_no}` |
| `master_route_seed.json` 编码和 JSON 损坏 | 直接导入会失败，甚至写入乱码模板 | 先清洗 seed，再建立导入测试 |
| 标准路线组合是否按产品线绑定 | 如果模板和产品线不匹配，用户可能选错路线 | 模板接口按 `productCode` 和默认优先级筛选，同时保留高级搜索 |
| route_template_code 是否新增字段 | 不新增字段也能用 `process_param_json` 保存，但查询和唯一性较弱 | 企业级建议新增字段和唯一索引 |
| 工作台直接弹窗还是跳项目中心 | 直接弹窗体验好但改动大，跳项目中心改动小 | 推荐第一期跳项目中心工艺路线 Tab，第二期抽公共弹窗组件 |
| 最终路线清单由哪个角色确认 | 如果权限不清，可能出现工程创建后直接进入投产清单 | 建议最后一步由项目经理发起，管理层或工程负责人确认，按现有权限规则记录日志 |
| BOM 版本与工艺路线版本如何强绑定 | 如果只靠前端选择，可能出现错配 | 建议后端保存 `process_id` 关联并在发布门禁校验 |

## 14. 后续维护建议

1. 先修复 `master_route_seed.json` 的编码和 JSON 格式，建立 `seed -> template -> Process` 的导入校验链路。
2. 工艺路线模板服务独立封装，不要让工作台、项目中心各自解析模板。
3. 所有新建路线必须由后端生成 `process_code`，前端只展示预览。
4. locked 路线严禁直接编辑，变更必须新建版本或走变更流程。
5. 工艺路线模板和产品路线版本要分清：模板是可复用组合，产品路线是某个 Product 的实际版本。
6. 前端工作台只负责入口和状态可视化，最终数据以项目中心/后端 Process 为准。
7. 后续如果接 ERP/MES，只映射已锁定或已发布的 Process，不让外部系统反向改 PLM 核心数据。
