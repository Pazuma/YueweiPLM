本次实现遵守的业务口径：

1. 推进对象是小步骤，不是大节点。
2. 大节点负责资料门禁。
3. 确认当前小步骤后，后端自动进入下一小步骤。
4. 从当前大节点最后一个小步骤进入下一个大节点时，后端校验当前大节点要求资料是否齐套。
5. 上传资料时可以选择当前大节点内的小步骤作为资料归属。
6. 文件中心需要展示项目编码、项目名称、大节点、小步骤等可读字段。
7. Product 仍是项目生命周期核心对象，附件仍写入 `plm_attachment`，不新增 FileVersion 等根对象。

## 3. 后端实现逻辑

### 3.1 时间轴定义从大节点展开为小步骤

`TimelineNodeConstants` 将产品线从 6 个大节点展开为 22 个小步骤，新型号线从 6 个大节点展开为 16 个小步骤。每个小步骤保留所属大节点和资料分类：

```java
public record TimelineNodeDefinition(
    Integer stepNo,
    String nodeCode,
    String nodeName,
    String stageCode,
    String stageName,
    String phaseName,
    String requiredFileCategory
) {}
```

`TimelineDefinitionProvider` 增加按步骤编码、步骤序号、阶段步骤集合、阶段必传资料查询能力，用于推进、上传和文件中心字段翻译。

### 3.2 确认小步骤并自动推进

`TimelineActionServiceImpl.confirm()` 现在只校验当前小步骤是否匹配，然后完成当前小步骤：

- 如果存在下一小步骤：`currentStepNo` 自动变成下一步，`timelineCurrentConfirmed=false`。
- 如果当前是最后一步：保留当前步并标记已确认。
- 如果下一小步骤属于下一个大节点：先调用大节点资料门禁。

核心逻辑：

```java
boolean hasNextStep = context.currentStepNo() < context.definitions().size();
TimelineNodeDefinition nextNode = hasNextStep
    ? context.definitions().get(context.currentStepNo())
    : context.current();
boolean crossingStage = hasNextStep && !context.current().stageCode().equals(nextNode.stageCode());

if (crossingStage) {
    requireStageDocuments(product, context.current());
}
```

### 3.3 大节点资料门禁

进入下一个大节点前，系统读取当前大节点内所有带 `requiredFileCategory` 的小步骤，要求附件表中存在同项目、同小步骤、同资料分类的附件。

附件匹配键：

```text
timelineNodeKey::fileCategory
```

缺失时返回：

```text
current stage documents are incomplete: {nodeCode}:{fileCategory}
```

### 3.4 上传限制在当前大节点

`AttachmentServiceImpl.uploadProjectTimelineAttachment()` 保留原接口：

```text
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/attachments
```

但 `nodeKey` 现在表示用户选择的小步骤。后端新增校验：所选小步骤必须属于当前项目所在大节点，否则返回 `STATUS_TRANSITION_ILLEGAL`。

### 3.5 文件中心字段补充

`AttachmentVO` 增加：

- `projectId`
- `projectCode`
- `projectName`
- `timelineStageCode`
- `timelineStageName`
- `timelineStepCode`
- `timelineStepName`

`pageFileCenter()` 批量查询 Product，并根据 `timelineNodeKey` 翻译大节点和小步骤，避免文件中心只能看到附件编码。

仍需补齐项：
