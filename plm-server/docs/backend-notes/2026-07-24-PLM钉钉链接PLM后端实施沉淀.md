## 1. 本次完成内容

本次按方案把“钉钉审批表链接 PLM”的后端骨架落入项目，核心效果是：

- 新增统一钉钉审批回调接口，按 `processCode` 分流到新产品线或新型号开模。
- 新增新产品研发产品申请接入服务，审批通过后创建 `product_type=product_line` 的 Product 项目。
- 完善新型号开模接入服务，项目名称改为 `Tipo 类型 + Modelos 型号`。
- 明确“生成的编码”继续作为 `moldCodes` 进入 Inventory 模具编码处理，不作为 Product 编码。
- 新增钉钉附件元数据归档能力，有附件时写入项目资料区；无附件不阻断项目创建。
- 时间轴详情返回项目数据版字段：项目编码、项目名称、预计交付时间、来源审批信息。
- 时间轴确认动作增加“小步骤必传资料”后端校验。
- 新型号“运模到墨西哥”复用 `MODEL_VARIANT_MOLD_TRANSFER` 节点，节点确认成功后触发钉钉出站连接器。
- 出站连接器默认 dry-run；配置 endpoint 后可 POST 到外部钉钉连接器。调用失败时记录 failed 集成记录，不回滚 PLM 节点确认。

## 3. 关键代码逻辑

### 3.1 统一审批回调

入口：

```http
POST /api/v1/integrations/dingtalk/approval-callbacks
```

核心分流：

```java
if (properties.getProductLineProcessCode().equals(dto.getProcessCode())) {
    return productLineService.receive(toProductLine(dto));
}
if (properties.getModelVariantProcessCode().equals(dto.getProcessCode())) {
    return modelVariantService.receive(toModelVariant(dto));
}
```

逻辑说明：

- 新产品研发申请走 `DingTalkProductLineService`。
- 新型号开模申请走已有 `DingTalkModelVariantService`。
- 字段暂按 Map 解析，兼容 `productName`、`产品名称`、`tipo`、`Tipo 类型`、`generatedCode`、`生成的编码` 等字段名。
- 后续拿到真实钉钉控件 ID 后，只需要调整 `DingTalkApprovalDispatchService` 中的字段映射。

### 3.2 新产品线自动创建

关键落点：

```java
product.setProductType("product_line");
product.setProductName(dto.getProductName().trim());
product.setProductCode(generateUniqueProductCode(dto));
product.setStatus("developing");
product.setCurrentStepNo(1);
product.setExpectedDeliveryDate(dto.getExpectedDeliveryDate());
product.setSourceSystem("dingtalk");
product.setSourceInstanceId(externalInstanceId);
```

幂等规则：

```text
source_system = dingtalk
integration_type = product_line
external_instance_id = approvalInstanceId / approvalNo
```

审批状态不是 `approved` 时，仅记录 `ignored` 集成记录，不创建 Product。

### 3.3 新型号开模项目命名

原实现使用：

```text
parentProductName + model
```

本次调整为：

```java
private String projectName(DingTalkModelVariantReceiveDTO dto) {
    return dto.getTipo().trim() + " " + dto.getModel().trim();
}
```

这样符合业务确认口径：PLM 项目名称 = `Tipo 类型 + Modelos 型号`。

### 3.4 模具编码进入 Inventory

本次保留现有 `MoldCodeIntakeService`：

```text
moldCodes 已存在于 plm_inventory.inventory_code -> linked_existing
moldCodes 不存在 -> 创建 inventory_type=tooling/status=draft -> created_draft
```

说明：

- 钉钉“生成的编码”仍映射为 `moldCodes`。
- 不覆盖 `Product.product_code`。
- Product 编码仍由 PLM 自己生成。

### 3.5 附件元数据归档

本次新增：

```java
attachment.setOwnerObjectType("PRODUCT");
attachment.setOwnerObjectId(product.getProductId());
attachment.setFileCategory("other");
attachment.setStorageType("dingtalk");
attachment.setStorageKey(downloadUrl 或 dingtalk://fileId);
attachment.setSourceSystem("dingtalk");
attachment.setSourceFileId(fileId);
attachment.setSourceUrl(downloadUrl);
```

当前阶段不强制下载钉钉文件流，原因是正式下载需要钉钉应用权限和临时下载地址确认。好处是业务已经能在资料区看到来源附件记录，后续只需增强下载入库，不影响建项主流程。

### 3.6 当前小步骤必传资料校验

新增校验点：

```java
requireBusinessGate(projectId, nodeKey);
requireCurrentNodeAttachment(product, context.current());
```

校验条件：

```text
owner_object_type = PRODUCT
owner_object_id = product_id
timeline_node_key = currentNode.nodeCode
file_category = currentNode.requiredFileCategory
deleted_flag = 0
```

缺失时返回：

```text
当前步骤必传资料未上传：{节点名称}
```

这样可以避免只靠前端提示“待上传”，后端状态推进仍被放过。

### 3.7 运模到墨西哥触发钉钉后续流程

节点边界：

```text
MODEL_VARIANT_MOLD_TRANSFER = 运模到墨西哥
```

触发时机：

```java
if (dingTalkShipMoldTriggerService != null) {
    dingTalkShipMoldTriggerService.triggerIfNeeded(product, context.current(), currentUser.displayName());
}
```

出站幂等：

```text
source_system = dingtalk
integration_type = model_variant_ship_mold
project_id = product_id
node_key = MODEL_VARIANT_MOLD_TRANSFER
direction = outbound
```

出站行为：

- 未配置 `DINGTALK_OUTBOUND_ENDPOINT`：dry-run 成功记录，不调用外网。
- 已配置 endpoint：POST payload 到外部连接器。
- 调用失败：记录 `processing_status=failed`，不回滚 PLM 节点确认，后续可重试。
- 已有 success 记录：直接命中幂等，不重复触发。

## 4. 配置说明

新增配置均在 `application.yml`：

```yaml
plm:
  integrations:
    dingtalk:
      enabled: ${DINGTALK_INTEGRATION_ENABLED:true}
      corp-id: ${DINGTALK_CORP_ID:}
      app-key: ${DINGTALK_APP_KEY:}
      app-secret: ${DINGTALK_APP_SECRET:}
      agent-id: ${DINGTALK_AGENT_ID:}
      product-line-process-code: ${DINGTALK_PRODUCT_LINE_PROCESS_CODE:PROC-88C58F86-D55A-4A04-BA6E-CB71071F0468}
      model-variant-process-code: ${DINGTALK_MODEL_VARIANT_PROCESS_CODE:PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C}
      ship-mold-process-code: ${DINGTALK_SHIP_MOLD_PROCESS_CODE:}
      outbound-endpoint: ${DINGTALK_OUTBOUND_ENDPOINT:}
```

维护要求：

- `DINGTALK_APP_SECRET` 只能由 Secret 注入。
- 不要把生产数据库密码、钉钉密钥、ERP Token 写入 Git。
- `DINGTALK_OUTBOUND_ENDPOINT` 建议指向内部连接器服务，而不是直接把复杂钉钉 API 逻辑散落到 PLM 核心流程。

## 6. 好处

- 业务人员只填钉钉审批表，PLM 自动建项，减少重复录入。
- 新产品线和新型号开模通过 `processCode` 分流，后续维护边界清楚。
- 新型号项目名称按业务口径生成，减少前端或人工再修正。
- 模具编码进入 Inventory，符合七个核心对象约束，不新增 Tooling 根对象。
- 附件先沉淀元数据，后续有权限后可平滑增强为文件下载入库。
- 必传资料节点由后端兜底，避免状态推进绕过资料要求。
- 运模到墨西哥节点作为 PLM 和钉钉后续流程边界，有幂等记录和失败重试入口。
- 密钥全部环境变量化，降低泄露风险。

## 8. 后续维护建议

1. 拿到真实钉钉审批表后，优先用控件 ID 做字段映射，不要长期依赖中文 / 西语标题。
2. 钉钉附件下载权限确认后，把 `DingTalkAttachmentArchiveService` 从“元数据归档”增强为“下载文件并上传 MinIO/S3”。
3. 钉钉出站建议保持连接器服务隔离，PLM 只负责发送业务 payload 和记录结果。
4. 定期清理或重试 `plm_integration_record.processing_status=failed` 的 outbound 记录。
5. 如果业务新增钉钉审批流程，只在 `DingTalkApprovalDispatchService` 增加新的 `processCode` 分支，不要复制 Controller。
6. 必传资料节点清单应由业务最终确认后调整 `TimelineNodeConstants.requiredFileCategory`。
7. 生产环境上线前必须在 CI 跑完整后端测试，并用验收库执行 Flyway 迁移。
