# PLM 后端 M2 工作台进行中项目与项目时间轴查询实施沉淀

日期：2026-07-06

## 1. 任务理解

M2 的目标是让前端工作台不再依赖 mock 数据，而是从真实数据库读取“进行中项目”，并在打开项目详情时查询该项目的时间轴节点。

本阶段只做查询能力，不做节点推进。核心原则是：

- `projectId` 先等同于 `productId`。
- 不新增 `Project` 根对象，项目概念由 `plm_product` 承载。
- `product_type=product_line` 表示新产品线。
- `product_type=model_variant` 表示新型号线。
- `status` 仍使用 Product 状态机：`draft`、`developing`、`reviewing`、`released`、`archived`。
- `current_step_no` 表示当前走到第几个节点。
- 时间轴节点根据 `product_type` 使用固定定义生成。
- `documentCount` 第一阶段允许返回 0，后续接附件表后再做真实统计。

## 3. 所属 PLM 业务链路

M2 属于“产品主数据 / 项目工作台 / 产品生命周期状态查看”链路。

- 新产品线：市场或客户需求形成 Product 后，工作台展示该产品线当前阶段。
- 新型号线：已有产品线下扩展机型、颜色、包装或客户版本，仍作为 Product 子项展示。
- 当前阶段只查询项目状态和节点状态，不改变状态，不写推进日志。

## 4. 涉及前端页面

前端预计使用位置：

- 工作台首页：展示进行中项目列表。
- 项目列表页：按 `product_type`、`status`、关键字筛选。
- 项目详情弹窗：展示产品基础信息、负责人、状态、当前节点。
- 项目时间轴区域：展示 6 个节点的 `completed/current/pending` 状态和资料数量。

## 11. 核心代码逻辑

### 11.1 ProjectService

职责：

- 查询 `plm_product`。
- 把 `productId` 映射为 `projectId`。
- 根据 `ownerUserId` 查询 `sys_user.display_name`。
- 根据 `productType + currentStepNo` 计算当前节点名。
- 返回前端工作台和详情弹窗需要的 VO。

伪代码：

```java
public PageVO<ProjectSummaryVO> pageInProgress(ProjectQueryDTO queryDTO) {
    LambdaQueryWrapper<Product> wrapper = baseProjectQuery(queryDTO)
        .in(Product::getStatus, List.of("draft", "developing", "reviewing"))
        .orderByDesc(Product::getUpdatedAt);
    return mapPage(productRepository.selectPage(page, wrapper));
}
```

### 11.2 TimelineDefinitionProvider

职责：

- 根据 `productType` 返回固定 6 个节点。
- 不查数据库，不带业务状态。
- 不认识的 `productType` 返回明确参数错误。

伪代码：

```java
public List<TimelineNodeDefinition> getDefinitions(String productType) {
    if ("product_line".equals(productType)) {
        return TimelineNodeConstants.PRODUCT_LINE_NODES;
    }
    if ("model_variant".equals(productType)) {
        return TimelineNodeConstants.MODEL_VARIANT_NODES;
    }
    throw new BusinessException(ErrorCodeConstants.VALIDATION_ERROR, "不支持的产品类型");
}
```

### 11.3 TimelineService

职责：

- 查询 Product。
- 规范化 `currentStepNo`，小于 1 时按 1，大于 6 时按 6。
- 生成每个节点的 `nodeStatus`。
- 保证只有一个 `current` 节点。
- `documentCount` 第一阶段统一返回 0。

节点状态规则：

```text
stepNo < currentStepNo  -> completed
stepNo = currentStepNo  -> current
stepNo > currentStepNo  -> pending
```

伪代码：

```java
private String resolveNodeStatus(int stepNo, int currentStepNo) {
    if (stepNo < currentStepNo) {
        return "completed";
    }
    if (stepNo == currentStepNo) {
        return "current";
    }
    return "pending";
}
```

### 11.4 documentCount 策略

M2 第一阶段：

```java
private int countDocuments(Long productId, Integer stepNo) {
    return 0;
}
```

后续接附件模块后建议：

- `owner_object_type='Product'`
- `owner_object_id=productId`
- 如果附件表后续有节点字段，再按 `timeline_step_no` 分组统计。
- 如果没有节点字段，则项目级资料总数可放到 summary，节点级仍为 0 或按类别映射。

## 15. 后续维护建议

1. 时间轴节点先用代码常量，等流程配置模块成熟后再迁移为数据库配置。
2. `current_step_no` 只能由后续 M3“推进节点”接口更新，M2 查询接口不应写库。
3. 节点推进必须记录 `plm_operation_log`，包含操作人、节点、业务对象、requestId、时间。
4. 如果未来节点数量可配置，`TimelineDefinitionProvider` 改为读取配置表，但 VO 字段保持不变。
5. `documentCount` 接入附件模块时，优先按 Product 维度统计；节点级统计需要附件表或关联表具备节点字段。
6. 工作台接口不要返回成本、报价等敏感字段，避免绕过成本权限。
7. 不要把 `Project` 做成新根对象。若需要项目扩展字段，优先评估是否应沉淀到 Product、Order 或 Process。

## 16. 验收标准

- 登录后携带 token 可以访问 M2 查询接口。
- 未携带 token 访问 M2 查询接口返回未登录。
- 工作台接口能返回真实 `plm_product` 数据。
- `GET /api/v1/projects` 支持 `productType` 筛选。
- `GET /api/v1/projects/{projectId}` 返回产品基础信息、负责人、状态、当前节点。
- `GET /api/v1/projects/{projectId}/summary` 返回弹窗头部所需摘要。
- `GET /api/v1/projects/{projectId}/timeline` 返回 6 个节点。
- 时间轴节点状态只出现一个 `current`。
- `documentCount` 可返回 0，不允许接口因未接附件统计而报错。
- 查询不存在项目返回业务错误，不返回服务器内部错误。
