# 2026-07-24 PLM 钉钉链接 PLM 实现方案

> 文档类型：实现前方案沉淀  
> 目标沉淀目录：`D:\work\资料\PLM\docs\后端-沉淀`  
> 本次范围：只沉淀方案文档，不修改 PLM 后端、前端或数据库业务代码  
> 业务结论：钉钉审批表作为业务入口，审批通过后由连接器把数据传入 PLM；PLM 自动创建项目、关联审批来源，并在新型号开模链路中负责推进到“运模到墨西哥”节点，之后再触发钉钉继续后续流程。

## 1. 任务理解

业务人员不再在 PLM 系统里重复填写新产品开发申请表或新型号开模申请表，而是在钉钉审批表中完成申请和审批。审批通过后，钉钉连接器把审批表数据传给 PLM，PLM 自动创建对应 Product 项目并进入原有时间轴推进。

本方案覆盖两条入口：

| 钉钉入口 | 钉钉 processCode | PLM 创建结果 |
| --- | --- | --- |
| 新产品研发产品申请 | `PROC-88C58F86-D55A-4A04-BA6E-CB71071F0468` | 创建 `product_type=product_line` 的新产品线项目 |
| 新型号的开模申请 | `PROC-89949932-19DE-48EB-A20B-2595CB0F804D` | 创建 `product_type=model_variant` 的新型号项目 |

其中新型号开模申请已明确以下业务规则：

- `Tipo 类型` 表示产品 / 产品类型。
- `Modelos 型号` 表示手机型号。
- PLM 项目名称按 `Tipo 类型 + Modelos 型号` 生成。
- 钉钉表单中的“生成的编码”是模具编码，不是产品编码。
- 模具编码要进入物料管理 / Inventory，建议使用 `inventory_type=tooling`。
- `Adjunto 附件` 如果有，则归档到项目资料区；没有附件不阻断创建项目。
- PLM 负责从钉钉审批传入、创建新项目、推进到“运模到墨西哥”节点。
- “运模到墨西哥”节点确认后，PLM 再通过连接器通知钉钉，由钉钉承接后续流程。

## 2. 所属 PLM 业务链路

本方案属于“新产品线”和“新型号线”的外部入口适配，不新增业务根对象。

```text
钉钉填写审批表
  -> 钉钉审批通过
  -> 钉钉连接器调用 PLM 接入接口
  -> PLM 校验签名、流程编码、审批状态、幂等键
  -> PLM 解析审批表字段
  -> PLM 创建 Product 项目
  -> PLM 关联审批来源和表单快照
  -> PLM 进入原时间轴节点
  -> 必传资料节点由后端校验附件
  -> 新型号开模推进到“运模到墨西哥”
  -> PLM 触发钉钉连接器
  -> 钉钉继续后续流程
```

边界说明：

- 钉钉负责申请入口、审批和“运模到墨西哥”之后的后续协同。
- PLM 负责项目主数据、时间轴推进、附件资料、模具编码落 Inventory、日志和追溯。
- 不在 PLM 内新增一张业务人员填写的申请表页面。
- 不新增 `ApprovalForm`、`IntegrationJob`、`Tooling` 等根对象。
- 集成记录只能作为辅助追溯和幂等记录，不能变成新的业务主对象。

### 5.2 状态建议

钉钉审批通过后，PLM 自动创建项目的推荐默认状态：

```text
Product.status = developing
Product.product_type = product_line 或 model_variant
Product.current_step_no = 1
Product.timeline_current_confirmed = false
```

说明：

- 钉钉审批已经承接“申请入口审批”，PLM 不再重复做一张申请表。
- PLM 第一节点仍保留业务完善 / 确认能力，便于补齐生产颜色、客户要求、附件和资料。
- 如果业务最终要求“钉钉审批通过即视为第一节点完成”，可在实现阶段把 `current_step_no` 初始化到第二节点，但当前建议先保持第一节点可见。

### 5.3 钉钉与 PLM 字段映射

新产品研发产品申请字段建议：

| 钉钉字段 | PLM 字段 / 落点 |

| 产品编码 / 编码前缀 | `plm_product.product_code` 生成输入或表单快照 |
| 预计交付时间 | `expected_delivery_date`，并在时间轴数据版展示 |
| 申请人 | 来源申请人字段、`created_by` 映射或表单快照 |
| 审批单号 / 实例 ID | `plm_integration_record.external_instance_id` |
| 审批附件 | 归档到项目资料区，如果钉钉允许服务端下载 |

新型号开模申请字段建议：

| --- | --- | --- |
| `Tipo 类型` | 产品 / 产品类型 | `RequirementForm.tipo`，并参与项目名称 |
| `Modelos 型号` | 手机型号 | `Product.model`，并参与项目名称 |

新型号项目名称规则：

```text

```

模具编码处理规则：

```text

moldCodes 中不存在的 inventory_code -> 创建 inventory_type=tooling/status=draft -> created_draft
```

## 6. 实施方案

### 6.1 连接器 A：钉钉审批通过后创建 PLM 项目

建议钉钉连接器统一调用一个 PLM 入站接口，由后端按 `processCode` 分流：

```http
POST /api/v1/integrations/dingtalk/approval-callbacks
Content-Type: application/json
X-Dingtalk-Signature: {signature}
X-Dingtalk-Timestamp: {timestamp}
X-Request-Id: {uuid}
```

处理流程：

```text
接收钉钉连接器请求
  -> 校验签名 / 时间戳 / 请求体
  -> 按 processCode 判断审批类型
  -> 审批状态不是 approved 时只记录，不创建项目
  -> 使用 source_system + integration_type + external_instance_id 做幂等
  -> 解析表单字段
  -> 校验必填字段
  -> 调用 product_line 或 model_variant 创建服务
  -> 处理附件归档
  -> 写入 plm_integration_record
  -> 写入操作日志
  -> 返回 projectId、productCode、处理状态
```

幂等键建议：

```text
source_system = dingtalk
integration_type = product_line 或 model_variant
external_instance_id = 钉钉审批实例 ID / 审批单号
```

### 6.2 新产品研发产品申请接入

新产品研发产品申请对应 `product_type=product_line`。

建议新增 `DingTalkProductLineService`，不要把新产品线逻辑硬塞进 `DingTalkModelVariantService`。原因是两条流程字段差异较大：新产品线创建的是父级产品线，新型号开模创建的是已有产品线下的子项目。

关键逻辑：

```java
@Transactional
public DingTalkProductLineResultVO receive(DingTalkProductLineReceiveDTO dto) {
    IntegrationRecord existing = findByExternalInstance(dto.getApprovalInstanceId(), "product_line");
    if (existing != null) {
        return result(existing, true);
    }
    if (!"approved".equals(dto.getApprovalStatus())) {
        return ignored(dto);
    }

    Product product = new Product();
    product.setProductType("product_line");
    product.setProductName(dto.getProductName());
    product.setProductCode(productCodeGenerator.generate(dto.getProductName()));
    product.setStatus("developing");
    product.setCurrentStepNo(1);
    productRepository.insert(product);

    archiveAttachmentsIfPresent(dto, product.getProductId());
    saveIntegrationRecord(dto, product.getProductId());
    writeOperationLog("DINGTALK_PRODUCT_LINE_CREATE", product);
    return created(product);
}
```

### 6.5 节点必传资料校验

现有 `TimelineNodeConstants` 中已经给部分小步骤配置了 `requiredFileCategory`，现有 `TimelineActionServiceImpl` 在跨大阶段时会检查阶段资料。业务提出“在一定要上传资料的步骤加必填”，建议从“跨阶段门禁”加强为“小步骤确认门禁”。

建议确认当前节点时增加：

```java
private void requireCurrentNodeAttachment(Product product, TimelineNodeDefinition currentNode) {
    if (!StringUtils.hasText(currentNode.requiredFileCategory())) {
        return;
    }
    long count = attachmentRepository.selectCount(new LambdaQueryWrapper<Attachment>()
        .eq(Attachment::getOwnerObjectType, AttachmentOwnerTypeConstants.PRODUCT)
        .eq(Attachment::getOwnerObjectId, product.getProductId())
        .eq(Attachment::getTimelineNodeKey, currentNode.nodeCode())
        .eq(Attachment::getFileCategory, currentNode.requiredFileCategory())
        .eq(Attachment::getDeletedFlag, 0));
    if (count == 0) {
        throw new BusinessException(
            ErrorCodeConstants.STATUS_TRANSITION_ILLEGAL,
            "当前步骤必传资料未上传：" + currentNode.nodeName()
        );
    }
}
```

调用位置建议放在 `TimelineActionServiceImpl.confirm(...)` 中 `requireBusinessGate(...)` 之后、状态更新之前：

```java
requireBusinessGate(projectId, nodeKey);
requireCurrentNodeAttachment(product, context.current());
```

### 6.6 连接器 B：PLM 运模到墨西哥后回传钉钉

新型号开模链路中，PLM 只负责推进到“运模到墨西哥”部分。当前代码中的节点为：

```text
MODEL_VARIANT_MOLD_TRANSFER = 运模
```

业务口径“运模到墨西哥”建议在界面文案或节点配置中明确；如果节点仍使用 `MODEL_VARIANT_MOLD_TRANSFER`，则连接器触发条件以该节点为准。

触发原则：

```text
确认当前节点成功
  -> product_type == model_variant
  -> 当前节点 == MODEL_VARIANT_MOLD_TRANSFER
  -> 来源 integration_record 为 dingtalk/model_variant
  -> 已有有效 DHL / 运模单号
  -> 当前项目该节点尚未成功触发过钉钉后续流程
  -> 调用钉钉连接器 / 发起钉钉后续流程
  -> 保存 outbound 集成结果
```

建议新增 `DingTalkShipMoldTriggerService`，由 `TimelineActionServiceImpl.confirm(...)` 在节点确认成功后调用：

```java
if (shipMoldTriggerService != null) {
    shipMoldTriggerService.triggerIfNeeded(product, context.current(), currentUser.displayName());
}
```

`DingTalkShipMoldTriggerService` 伪代码：

```java
@Transactional
public void triggerIfNeeded(Product product, TimelineNodeDefinition node, String operator) {
    if (!"model_variant".equals(product.getProductType())) return;
    if (!"MODEL_VARIANT_MOLD_TRANSFER".equals(node.nodeCode())) return;

    IntegrationRecord inbound = findInboundModelVariant(product.getProductId());
    if (inbound == null) return;

    IntegrationRecord outbound = findOutboundTrigger(product.getProductId(), node.nodeCode());
    if (outbound != null && "success".equals(outbound.getProcessingStatus())) return;

    DingTalkShipMoldRequest request = buildRequest(product, inbound);
    DingTalkResult result = dingTalkOutboundApprovalClient.startProcess(request);
    saveOutboundRecord(product, node, result, operator);
    writeOperationLog("DINGTALK_SHIP_MOLD_TRIGGER", product);
}
```

回传钉钉建议字段：

| 字段 | 来源 |
| --- | --- |
| PLM 项目 ID | `product.product_id` |
| PLM 项目名称 | `product.product_name` |
| 产品类型 / Tipo | `plm_project_requirement_form.tipo` |
| 手机型号 / Modelos | `product.model` |
| 模具编码 | `plm_project_requirement_form.mold_codes` |
| 模具匹配结果 | `mold_match_json` |
| 运模单号 | `plm_project_mold_transfer_express.tracking_no` |
| 钉钉原审批单号 | `plm_integration_record.external_instance_id` |
| PLM 节点 | `MODEL_VARIANT_MOLD_TRANSFER` |

## 11. 测试与验收

### 11.1 后端自动化测试

建议覆盖：

- 新产品研发审批通过后创建 `product_type=product_line` 项目。
- 新产品研发重复回调命中幂等，不重复创建项目。
- 新型号开模审批通过后创建 `product_type=model_variant` 项目。
- 新型号项目名称等于 `Tipo 类型 + Modelos 型号`。
- 钉钉“生成的编码”写入 Inventory 模具编码，不覆盖 Product 编码。
- 已存在模具编码返回 `linked_existing`。
- 不存在模具编码自动创建 `tooling/draft`，返回 `created_draft`。
- `Adjunto` 有附件时归档到项目资料区。
- `Adjunto` 无附件时仍允许创建项目。
- 必传资料节点缺附件时确认失败。
- 必传资料节点上传附件后确认成功。
- 运模节点确认成功后触发钉钉 outbound。
- 运模节点重复确认或重复重试不重复创建钉钉后续流程。
- 钉钉 outbound 失败时记录错误，可人工重试。

### 11.2 联调验收

联调步骤建议：

1. 在钉钉提交“新产品研发产品申请”并审批通过。
2. 确认 PLM 自动创建新产品线项目。
3. 打开项目进度弹窗，确认红框数据版展示名称、编码、预计交付时间。
4. 在钉钉提交“新型号的开模申请”并审批通过。
5. 确认 PLM 自动创建新型号项目，名称为 `Tipo + Modelos`。
6. 查询 Inventory，确认模具编码已匹配或创建。
7. 如果审批表带 `Adjunto`，确认资料区能看到附件。
8. 在必传资料节点未上传附件时点击确认，预期后端阻断。
9. 上传资料后再次确认，预期可继续推进。
10. 填写运模单号并确认“运模到墨西哥”节点。
11. 确认 PLM 触发钉钉连接器，钉钉继续后续流程。

## 12. 预计效果

业务效果：

- 业务人员只在钉钉填写审批表，不在 PLM 重复填申请表。
- 审批通过后 PLM 自动创建项目，减少人工建档和复制粘贴。
- PLM 项目自动关联钉钉审批单，后续可追溯来源。
- 新产品线和新型号两条入口通过 `processCode` 清晰分流。
- 新型号项目名称按业务口径生成：`Tipo 类型 + Modelos 型号`。
- 钉钉“生成的编码”作为模具编码进入物料管理，不误当成产品编码。
- 附件有则归档到资料区，无则不阻断项目创建。
- 必传资料节点由后端兜底校验，避免只靠前端提示。
- 新型号开模流程在 PLM 推进到“运模到墨西哥”后，自动把结果交回钉钉继续后续流程。

技术效果：

- 复用现有 `DingTalkModelVariantService`、`MoldCodeIntakeService`、`IntegrationRecord` 和时间轴能力。
- 不新增业务根对象，符合 PLM 七个核心对象约束。
- 集成入站和出站都有幂等记录，避免重复创建项目或重复发起钉钉流程。
- 配置和密钥走环境变量 / Secret，避免硬编码。
- 通过操作日志沉淀关键行为，便于审计和排查。

## 13. 风险点

| 风险 | 说明 | 建议 |
| --- | --- | --- |
| 钉钉表单字段变化 | 管理员修改控件名后，按名称解析可能失败 | 优先使用控件 ID 或配置化字段映射 |
| 审批回调重复 | 钉钉可能重复推送同一审批事件 | 必须以审批实例 ID 做幂等 |
| 附件下载权限不足 | 钉钉附件可能无法由服务端直接下载 | 第一阶段保存附件元数据和审批链接，不阻断创建 |
| 模具编码误用 | “生成的编码”容易被误认为 Product 编码 | 接口和文档明确该字段为 moldCodes |
| 运模节点触发重复 | 用户重复确认或接口重试可能重复发起钉钉流程 | outbound 记录加唯一索引 |
| Secret 泄露 | 用户已提供密钥，但文档和代码不能明文沉淀 | 使用 Secret 注入和脱敏展示 |
| PLM 与钉钉流程边界不清 | 新型号后半段由钉钉继续，容易重复推进 | 以 `MODEL_VARIANT_MOLD_TRANSFER` 作为 PLM 责任边界 |
