# 2026-08-06 历史导入工艺路线工序库绑定问题分析与修复方案沉淀

## 1. 问题背景

历史产品及其工艺路线通过主数据导入功能进入 PLM。业务已确认：

- 导入的工艺路线均为历史最终确认路线；
- 导入路线及其工序统一以 `confirmed` 状态落库；
- 从已发布正式 BOM 自动继承的工艺路线一般也默认视为已确认，路线和工序均应落为 `confirmed`；
- 历史工序已经携带产品工序编码、工序名称、顺序、材料/状态编码、成品标识等快照数据；
- 历史工序名称以导入文件中的名称为准，导入、匹配工序库和自动继承均不得自动改名；
- 历史数据导入时不一定存在对应的 PLM 工序库主数据。

在项目工艺路线编辑弹窗中打开这类路线并点击“保存完整路线”时，页面提示：

```text
顺序 10 请选择工序库中的工序
```

页面现象是：下方“节点配置核对表”可以显示历史工序名称，但上方“工序名称”选择器仍显示“选择工序名称”。

## 2. 根因定位

### 2.1 导入链路未建立工序库引用

主数据导入服务创建 `process_type = operation` 的历史工序时，会写入：

- `process_code`
- `process_name`
- `sequence_no`
- `operation_craft_code`
- `material_status_code`
- `business_operation_code`
- `finished_product_flag`
- `quality_requirement`
- `status = confirmed`

但当前没有写入：

```text
operation_master_process_id
```

因此历史工序是完整的业务快照，却没有绑定 `process_type = operation_master` 的工序库记录。

### 2.2 前端校验对所有路线执行同一规则

`ProjectProcessRoutePanel.vue` 在保存前执行：

```ts
if (!operation.operationMasterProcessId) {
  return `顺序 ${operation.sequenceNo} 请选择工序库中的工序`
}
```

该规则适合新建路线，但没有区分：

- 新建或人工维护的路线；
- 已绑定工序库的标准路线；
- 未绑定工序库的历史导入最终路线。

所以历史快照虽然名称、编码齐全，仍被前端当成“未选择工序”。

### 2.3 前后端约束当前并不完全一致

后端 `ProcessRouteServiceImpl.validateOperations` 已允许 `operationMasterProcessId` 为空，但要求此时必须提供：

- `processName`
- `qualityRequirement`

也就是说，后端实际上支持“无工序库引用的工序快照”，而前端进行了更严格的一刀切拦截。

## 3. 数据语义

`operationMasterProcessId` 和工序快照承担不同职责：

| 数据 | 职责 |
| --- | --- |
| `operation_master_process_id` | 指向当前工序库主数据，用于新建路线时选择和带出默认值 |
| `process_name`、工序编码、参数、质量要求 | 保存路线确认时的业务快照，保证历史可追溯 |

历史路线没有工序库引用，不代表历史工序无效。只要快照字段完整，路线仍应能够被查看和用于继承。

不能仅按名称强制绑定工序库，因为同名工序可能存在不同工艺编码、参数和质量要求，错误绑定会改变历史含义。

## 4. 修复原则

1. 历史最终确认路线以快照为准，不因当前工序库变化而被自动改写。
2. 新建路线和新增工序仍必须从已确认或已锁定的工序库中选择。
3. 自动匹配只能在唯一且可靠时建立引用，不能按模糊名称静默绑定。
4. 已最终确认的导入路线不应通过普通编辑直接覆盖；需要调整时应创建新版本。
5. 修复必须同时覆盖后续导入和存量历史数据。
6. 从已发布正式 BOM 自动继承到新型号项目的路线属于已确认业务成果复制，默认保持 `confirmed`；只有人工创建并调整的新版本从 `draft` 开始。
7. 导入工序名称是历史确认快照。补充工序库引用只能建立关联，不能用工序库名称覆盖导入名称。

## 5. 建议方案

采用“导入时可靠匹配 + 历史快照兼容 + 存量回填”的组合方案。

### 5.1 导入时自动匹配工序库

导入 `operation` 时按以下优先级查找可用的 `operation_master`：

1. 工序库 `process_code` 与导入工序的标准工序编码完全一致；
2. 工艺编码 `operationCraftCode` 完全一致且只命中一条；
3. 规范化工序名称完全一致且只命中一条。

只有唯一匹配时才写入 `operation_master_process_id`。零匹配或多匹配时保留为空，并在导入明细中记录待治理原因。

匹配成功后只补充引用，不改写以下历史快照：

- `process_name`：严格保留导入文件中的工序名称；
- `process_code` 和 `business_operation_code`；
- 工艺参数、标准工时和质量要求；
- 材料/状态编码和成品标识。

不建议为每条历史产品工序自动创建独立工序库记录，否则会把产品级编码误当成全局工序主数据，造成工序库膨胀。

### 5.2 前端兼容历史快照

编辑器加载历史工序时：

- 有 `operationMasterProcessId`：正常显示工序库选择结果；
- 无引用但快照完整：显示“历史导入工序”状态及导入原名称，不显示为空白选择；
- 无引用且快照不完整：提示数据治理，不允许保存。

对于历史导入工序，即使已经回填 `operationMasterProcessId`，页面默认显示名称仍应取工序快照 `processName`，不能改为当前工序库名称。只有用户在 `draft` 新版本中明确重新选择工序时，才使用新选择的工序库名称生成新的版本快照。

对新添加的工序仍要求选择工序库。是否允许无引用的判断不能只看 ID，还应由后端返回明确来源，例如：

```text
operationSource = master | imported_snapshot
```

### 5.3 最终确认路线采用只读和新版本机制

当前更新实现会软删除路线原工序并重新创建工序。重建后的工序状态为 `draft`，而路线本身可能仍保持 `confirmed`，会造成路线与工序状态不一致。

因此建议：

- `confirmed`、`locked`、`archived` 路线默认只读；
- 页面提供“基于此路线创建新版本”；
- 新版本复制历史快照，状态从 `draft` 开始；
- 用户在新版本中逐步将历史工序映射到工序库；
- 原最终路线保持不变，用于审计、BOM 关联和项目继承。

这里的“新版本”是用户主动编辑产生的派生版本，不等同于系统在创建新型号项目时执行的自动继承。

### 5.4 自动继承状态规则

新型号项目从父产品的已发布正式 BOM 继承工艺路线时，来源已经通过正式 BOM 发布和路线确认，因此默认规则为：

| 场景 | 目标路线状态 | 目标工序状态 |
| --- | --- | --- |
| 从已发布正式 BOM 自动继承 | `confirmed` | `confirmed` |
| 人工基于确认路线创建可编辑新版本 | `draft` | `draft` |
| 新建空白路线或模板路线 | `draft` | `draft` |

继承时应保留：

- 工序库引用 `operationMasterProcessId`，若来源历史工序没有引用则继续保留历史快照语义；
- 工序名称、参数、工时、质量要求等确认时快照，其中工序名称保持导入原样；
- 最终确认标识及与 BOM 路线、颜色的继承关系；
- 来源路线 ID、来源产品 ID 或等价追溯信息。

当前 `ProcessRouteInheritanceService.copyRoute` 和 `copyOperation` 均强制写入 `STATUS_DRAFT`，与上述业务规则不一致，属于后续实现时需要修正的明确缺口。

### 5.5 存量数据回填

提供一次可审计的存量治理任务：

1. 查询 `process_type = operation` 且 `operation_master_process_id IS NULL` 的记录；
2. 仅按确定性规则匹配 `confirmed/locked` 的工序库记录；
3. 唯一命中时回填引用；
4. 未命中或多命中时输出清单，不自动修改；
5. 回填不覆盖工序名称、参数、工时、质量要求等历史快照。

存量回填必须支持预览、执行结果统计和操作日志，不建议直接执行无审计 SQL。

## 6. 不建议方案

### 6.1 只删除前端校验

虽然可以立即消除当前提示，但会让所有新建工序都能绕过工序库，破坏主数据治理规则。

### 6.2 自动按名称创建工序库

历史产品工序名称通常包含产品名称或型号，同一基础工序会生成大量重复主数据。

### 6.3 原地覆盖最终确认路线

这会破坏历史版本和确认状态，并可能影响已有 BOM、颜色、SKU 和项目继承关系。

## 7. 验收标准

### 7.1 历史导入路线

1. 打开历史最终确认路线时，所有历史工序名称正常显示。
2. 未绑定工序库的工序明确标识为“历史导入工序”，不显示成空白数据。
3. 原最终路线不可被普通编辑覆盖。
4. 可以基于历史路线创建新版本。
5. 唯一匹配并回填工序库引用后，工序名称仍与导入文件完全一致。

### 7.2 新建和新版本路线

1. 新增工序必须从 `confirmed/locked` 工序库中选择。
2. 选择后保存 `operationMasterProcessId` 和完整工序快照。
3. 新版本保存后不修改原历史路线和原 BOM 关联。

### 7.3 自动继承路线

1. 从已发布正式 BOM 继承后的路线状态为 `confirmed`。
2. 继承路线下的全部工序状态为 `confirmed`。
3. 继承后的路线可直接作为确认路线使用，不要求用户再次逐行选择工序库。
4. 用户需要调整继承路线时，通过创建 `draft` 新版本完成，不覆盖继承确认版本。
5. 继承后的工序名称与来源路线的工序名称一致，不使用当前工序库名称覆盖。

### 7.4 导入和存量治理

1. 可唯一匹配的导入工序自动建立工序库引用。
2. 不确定匹配不会被静默绑定。
3. 导入预览或结果中可以查看匹配状态和原因。
4. 存量回填前后均可统计未绑定工序数量。

## 8. 建议实施顺序

1. 修正自动继承状态：路线和工序默认写入 `confirmed`。
2. 前端正确显示历史快照，并禁止最终确认路线原地覆盖。
3. 增加“基于此路线创建新版本”能力，新版本状态为 `draft`。
4. 导入服务增加确定性工序库匹配和导入结果提示。
5. 增加存量数据预览与回填任务。
6. 补充前后端测试，覆盖历史快照、确认状态继承、新增工序、唯一匹配、多匹配和版本隔离。

## 9. 当前结论

当前提示不是导入工艺路线内容缺失，而是历史导入模型与后来新增的工序库强制选择规则之间存在兼容缺口。

处理方向不应是让用户逐条重新选择并覆盖最终路线，而应保留历史快照，通过唯一匹配补引用，并通过新版本完成后续调整。自动继承属于确认成果复制，默认保持 `confirmed`；人工调整产生的新版本才进入 `draft`。
## 10. 实施结果

### 10.1 实际修改

- `ProcessRouteInheritanceService`：正式 BOM 自动继承的路线和工序状态改为 `confirmed`，保留来源工序名称和快照字段。
- `ProcessRouteServiceImpl`：确认路线只读，调整时创建 `draft` 新版本；历史快照工序不再强制要求工序库引用，并记录 `operationSource`。
- `ProjectProcessRoutePanel.vue`：历史导入工序显示原名称和“历史导入”，支持基于确认路线创建新版本。
- `MasterDataImportExportServiceImpl`：导入工序标记为 `imported_snapshot`，按工序编码、工艺编码、工序名称唯一匹配，只补充工序库引用，不覆盖导入快照。

### 10.2 目标效果

历史导入的最终确认路线可直接查看和保存，工序名称保持导入原样；正式 BOM 继承结果默认为 `confirmed`；人工调整通过新建 `draft` 版本完成，不污染原确认路线；非唯一匹配不会静默绑定。

### 10.3 验证结果

- 后端定向测试 44 个通过：`ProcessRouteInheritanceServiceTest`、`ProcessRouteServiceImplTest`、`MasterDataImportExportServiceImplTest`。
- 前端 M4 测试 19 个通过：`project-m4-panels.spec.ts`。
- 已修复前端保存载荷类型和测试断言类型问题，需重新执行 `vue-tsc --noEmit` 完成最终类型验证。

### 10.4 后期维护建议

- 为导入预览增加匹配方式、唯一性和未匹配原因，并保留批次审计日志。
- 后续补充存量数据回填的预览、执行和统计能力；本次仅兼容后续导入数据，未新增专门回填页面或批次任务。
- 保持快照字段不可被主数据自动覆盖；名称或参数变更必须通过新版本和明确的用户操作完成。
## 11. 业务规则补充：确认路线允许修正

经实际导入数据验证，历史导入过程会统一将路线标记为 `confirmed`，但部分历史路线仍存在缺失或错误，需要允许业务人员直接修正。因此最终规则调整如下：

- `draft`、`confirmed` 路线允许直接编辑和软删除。
- 编辑 `confirmed` 路线时，路线状态保持 `confirmed`，重建后的工序状态也保持 `confirmed`，避免出现确认路线包含草稿工序。
- 删除 `confirmed` 路线前仍检查有效 BOM 引用；存在引用时禁止删除，需先调整 BOM 关联。
- `locked`、`archived`、`changed` 路线继续保持只读，需要调整时创建新版本或走变更流程。
- 前端对 `confirmed` 路线启用“编辑路线”和“删除版本”，不再显示“已确认只读”；只读状态仍提供“创建新版本”。

该补充规则优先于本文前述“确认路线默认只读”的方案描述。确认状态表示当前导入或确认结果，不再等同于不可修改；真正不可直接修改的边界由锁定、归档、变更状态和有效 BOM 引用共同控制。
## 12. 最终确认与路线状态同步

### 12.1 问题表现

页面的“草稿”标签读取路线字段 `status`，而“最终确认”标签读取元数据字段 `finalSelected`。历史数据可能出现 `status = draft` 且 `finalSelected = true`，因此同一条路线同时显示两个互相矛盾的状态。

### 12.2 修复规则

- 新建或保存时，`finalSelected = true` 会同步写入路线 `status = confirmed`。
- 路线为 `confirmed` 时，重建工序也写入 `confirmed`，保持路线和工序状态一致。
- 取消最终确认不会自动把已经确认的路线降级为草稿，避免历史确认结果被无意覆盖。
- 已存在的矛盾数据需要再次编辑保存一次完成修正；本次修复不直接批量改写存量数据。

## 13. 业务工序编码唯一范围修正

`businessOperationCode` 表示路线内工序的业务编码，不是跨工艺路线的全局主数据编码。原服务查询和数据库唯一索引都按全表唯一处理，导致另一条路线使用相同编码（例如 `NFA1010`）时保存失败。

修复后的规则：

- 同一工艺路线内 `businessOperationCode` 仍然不可重复。
- 不同工艺路线允许使用相同的 `businessOperationCode`。
- 服务层按 `parent_process_id` 查询重复编码。
- 数据库唯一索引调整为 `(parent_process_id, business_operation_code)` 的有效工序部分唯一索引，保证并发保存时仍遵守路线内唯一规则。
- 部署时必须执行 Flyway 迁移 `V20260806_1000__scope_business_operation_code_to_route.sql`，仅更新 Java 包而不执行迁移仍会被旧全局唯一索引拦截。

## 14. 已确认路线编辑时工序编码超长修复

实际编辑历史确认路线时，后端在软删除旧工序并重建新工序阶段出现：

```text
ERROR: value too long for type character varying(64)
ProcessRouteServiceImpl.rebuildOperations
```

根因是系统生成的工序 `process_code` 直接拼接“路线编码 + 工序顺序 + 来源工序编码”，没有遵守 `plm_process.process_code varchar(64)` 的数据库边界。历史导入工序编码较长时，保存会触发数据库约束并导致整个更新事务回滚。

修复后规则：

- 生成结果不超过 64 个字符时保持原编码。
- 超过 64 个字符时保留可读前缀，并附加原完整编码的 8 位确定性哈希。
- 不直接静默截断完整编码，避免不同长编码拥有相同前缀时发生碰撞。
- 增加长工序编码回归测试，验证确认路线可更新、工序状态保持 `confirmed` 且生成编码不超过 64 位。
