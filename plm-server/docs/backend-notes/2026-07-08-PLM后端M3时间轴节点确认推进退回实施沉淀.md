# PLM 后端 M3 时间轴节点确认、推进、退回实施沉淀

> 日期：2026-07-08  
> 适用仓库：`D:\Yuewei\git\YUEWEI\plm-server`  
> 沉淀目录：`D:\Yuewei\资料\PLM\docs\后端-沉淀`  
> 目标：让工程部可以在项目时间轴上真实推动项目，把“当前做到哪一步、是否已确认、下一步是谁、退回原因是什么”落成系统数据。

## 1. 任务理解

M3 的目标不是再做一个资料展示页，而是把 M2 已经可以查询的项目时间轴变成可操作的业务流程。

```text
M1 解决：是谁在操作，以及成功动作可以写 plm_operation_log。
M2 解决：工作台可以查询进行中项目和项目时间轴。
M3 解决：工程部可以确认当前节点、推进到下一节点、退回修改，并留下可追溯记录。
```

本阶段仍然遵守当前后端架构约束：

```text
projectId 当前仍等同于 productId。
不新增 Project 根对象，项目概念继续由 plm_product 承载。
时间轴节点定义继续复用 TimelineNodeConstants。
推进动作必须使用当前登录用户。
成功动作必须写 plm_operation_log。
失败动作不能伪装成功，也不能写成功日志。
```

## 3. 建议接口设计

### 3.1 当前节点确认

```http
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/confirm
Authorization: Bearer {{token}}
Content-Type: application/json
X-Request-Id: m3-confirm-001
```

Body：

```json
{
  "remark": "设计资料已确认，可以进入下一步"
}
```

语义：

```text
确认当前节点已经完成业务核对。
只允许确认 current 节点。
确认后不改变 current_step_no。
确认后写 plm_product.timeline_current_confirmed=true。
确认成功写 TIMELINE_CONFIRM 操作日志。
```

### 3.2 推进到下一节点

```http
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/advance
Authorization: Bearer {{token}}
Content-Type: application/json
X-Request-Id: m3-advance-001
```

Body：

```json
{
  "remark": "设计确认完成，推进到开模试模"
}
```

语义：

```text
把当前节点推进到下一节点。
只允许推进 current 节点。
不能跳过节点。
最后一个节点不能继续推进。
推荐要求当前节点已 confirm 后才允许 advance。
推进后 current_step_no + 1。
推进后新的 current 节点确认状态重置为 false。
推进后根据节点更新 Product.status。
推进成功写 TIMELINE_ADVANCE 操作日志。
```

### 3.3 退回修改或退回上一节点

```http
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/return
Authorization: Bearer {{token}}
Content-Type: application/json
X-Request-Id: m3-return-001
```

Body：

```json
{
  "reason": "开模资料不完整，需要退回补充结构图",
  "returnToPrevious": true
}
```

语义：

```text
记录当前节点退回原因。
只允许从 current 节点发起 return。
returnToPrevious=true 时，如果当前不是第一个节点，则 current_step_no - 1。
returnToPrevious=false 时，只记录当前节点退回修改原因，不改变 current_step_no。
退回后当前节点确认状态重置为 false。
退回成功写 TIMELINE_RETURN 操作日志。
```

## 4. 推荐最小落地方案

M3 推荐先采用“Product 字段 + OperationLog 审计”的最小闭环，不立即引入完整流程实例表。

### 4.1 为什么这样做

```text
当前系统已经明确 projectId = productId。
M2 时间轴已经由 Product.currentStepNo 驱动。
M1 操作日志已经可以追踪动作、人、时间、requestId、业务对象。
当前阶段重点是把流程推动起来，不宜先扩成完整工作流引擎。
```

### 4.2 最小新增字段

建议在 `plm_product` 增加以下字段：

```sql
    add column if not exists timeline_last_action varchar(64),

    add column if not exists timeline_last_operated_at timestamp,

comment on column plm_product.timeline_confirmed_node_key is '最近一次确认的节点 key';
comment on column plm_product.timeline_last_action is '最近一次时间轴动作：confirm/advance/return';
comment on column plm_product.timeline_last_reason is '最近一次时间轴动作原因或备注';
comment on column plm_product.timeline_last_operated_at is '最近一次时间轴动作时间';
comment on column plm_product.timeline_last_operator_user_id is '最近一次时间轴操作人 ID';
comment on column plm_product.timeline_last_operator_user_name is '最近一次时间轴操作人姓名';
```

说明：

```text

timeline_confirmed_node_key 用来避免节点推进后旧确认状态误用。
timeline_last_* 字段用于列表和详情快速展示最近动作。

```

如果后续需要节点级完整历史、多人会签、节点审批意见，再新增 `plm_timeline_action` 或流程实例表。

## 7. 核心业务逻辑

### 7.1 查找当前节点

统一流程：

```text
1. 根据 projectId 查询 Product。
2. Product 不存在或 deletedFlag=1，抛 RESOURCE_NOT_FOUND。
3. 根据 product.productType 获取节点定义列表。
4. 规范化 currentStepNo，范围必须落在 1 到节点总数之间。
5. 找到 currentStepNo 对应的 TimelineNodeDefinition。
6. 比较请求 path 中的 nodeKey 是否等于当前节点 nodeCode。
7. 不一致时抛业务错误：只能操作当前节点。
```

伪代码：

```java
private TimelineNodeDefinition requireCurrentNode(Product product, String nodeKey) {
    List<TimelineNodeDefinition> definitions = timelineDefinitionProvider.getDefinitions(product.getProductType());
    int currentStepNo = normalizeStepNo(product.getCurrentStepNo(), definitions.size());
    TimelineNodeDefinition current = definitions.get(currentStepNo - 1);
    if (!current.nodeCode().equals(nodeKey)) {
        throw new BusinessException(ErrorCodeConstants.STATUS_TRANSITION_ILLEGAL, "只能操作当前时间轴节点");
    }
    return current;
}
```

### 7.2 confirm 逻辑

规则：

```text
当前节点 confirm 成功。
非当前节点 confirm 失败。
confirm 不推进 current_step_no。
confirm 写当前节点已确认。
confirm 写操作日志。
```

更新字段：

```text
timeline_current_confirmed=true
timeline_confirmed_node_key=nodeKey
timeline_last_action=confirm
timeline_last_reason=remark
timeline_last_operated_at=now
timeline_last_operator_user_id=currentUser.userId
timeline_last_operator_user_name=currentUser.displayName
updated_at=now
updated_by=currentUser.displayName
```

日志 detailJson 建议：

```json
{
  "projectId": 1,
  "productId": 1,
  "action": "confirm",
  "nodeKey": "PRODUCT_LINE_DESIGN_CONFIRM",
  "stepNo": 2,
  "remark": "设计资料已确认，可以进入下一步"
}
```

### 7.3 advance 逻辑

规则：

```text
当前节点 advance 成功。
非当前节点 advance 失败。
不能跳过节点。
最后节点不能继续 advance。
推荐当前节点未 confirm 时不允许 advance。
advance 后下一节点变 current。
advance 后新节点确认状态为 false。
advance 后根据节点更新 Product.status。
advance 成功写操作日志。
```

确认门槛：

```text
timeline_current_confirmed=true
timeline_confirmed_node_key=当前 nodeKey
```

如果不满足，返回明确业务错误：

```text
当前节点尚未确认，不能推进
```

更新字段：

```text
current_step_no=currentStepNo + 1
timeline_current_confirmed=false
timeline_confirmed_node_key=null
timeline_last_action=advance
timeline_last_reason=remark
timeline_last_operated_at=now
timeline_last_operator_user_id=currentUser.userId
timeline_last_operator_user_name=currentUser.displayName
status=resolveProductStatusAfterAdvance(nextStepNo, maxStepNo)
updated_at=now
updated_by=currentUser.displayName
```

Product.status 建议映射：

```text
stepNo = 1 -> draft
stepNo = 2 到 maxStepNo - 1 -> developing
stepNo = maxStepNo -> reviewing
最后节点完成发布动作仍应由发布接口把 status 改为 released
```

说明：

```text
M3 的 advance 只是推进流程节点，不等同于正式发布。
最后节点不能继续 advance，是为了避免时间轴越界。
如果最后节点后续要转 released，应由 Product publish 或归档动作处理。
```

日志 detailJson 建议：

```json
{
  "projectId": 1,
  "productId": 1,
  "action": "advance",
  "fromNodeKey": "PRODUCT_LINE_DESIGN_CONFIRM",
  "fromStepNo": 2,
  "toNodeKey": "PRODUCT_LINE_MOLD_TRIAL",
  "toStepNo": 3,
  "remark": "设计确认完成，推进到开模试模"
}
```

### 7.4 return 逻辑

规则：

```text
return 只能从 current 节点发起。
return 必须记录 reason。
returnToPrevious=false 时，只记录退回修改，current_step_no 不变。
returnToPrevious=true 时，退回上一节点。
第一个节点不能退回上一节点。
return 后当前确认状态重置为 false。
return 成功写操作日志。
```

更新字段：

```text
current_step_no=returnToPrevious ? currentStepNo - 1 : currentStepNo
timeline_current_confirmed=false
timeline_confirmed_node_key=null
timeline_last_action=return
timeline_last_reason=reason
timeline_last_operated_at=now
timeline_last_operator_user_id=currentUser.userId
timeline_last_operator_user_name=currentUser.displayName
status=resolveProductStatusAfterReturn(targetStepNo)
updated_at=now
updated_by=currentUser.displayName
```

日志 detailJson 建议：

```json
{

  "action": "return",
```

## 9. 操作日志设计

成功动作必须写 `plm_operation_log`。

通用字段建议：

```text
businessType=PROJECT 或 PRODUCT
businessId=productId
businessCode=product.productCode
businessName=product.productName
operatorUserId=CurrentUser.userId
operatorUserName=CurrentUser.displayName
requestId=当前请求 X-Request-Id
result=success
```

动作映射：

| 接口 | action |
| --- | --- |
| confirm | `TIMELINE_CONFIRM` |
| advance | `TIMELINE_ADVANCE` |
| return | `TIMELINE_RETURN` |

重要规则：

```text
业务校验失败时直接抛 BusinessException。
不要先写日志再校验。
不要在失败动作里写 result=success。
如果后续要记录失败审计，必须使用单独的失败日志语义，不能混入成功日志。
```

## 10. 错误码和错误语义

建议优先复用现有错误码：

```text
40401 RESOURCE_NOT_FOUND：项目不存在。
40001 VALIDATION_ERROR：参数缺失，例如 return reason 为空。
40002 STATUS_TRANSITION_ILLEGAL：非当前节点操作、未确认就推进、最后节点继续推进、第一个节点退回上一节点。
40101 UNAUTHORIZED：未登录或 token 失效。
```

错误响应示例：

```json
{
  "code": 40002,
  "message": "只能操作当前时间轴节点",
  "data": null,
  "requestId": "m3-confirm-wrong-node-001",
  "timestamp": "2026-07-08T10:00:00+08:00"
}
```

必须避免：

```text
非法动作返回 code=0。
非法动作返回空对象。
非法动作修改 current_step_no。
非法动作写成功 operation_log。
```

## 17. 后续维护建议

### 17.1 节点定义配置化

当前 `TimelineNodeConstants` 使用代码常量定义 6 个节点。后续如果业务节点频繁调整，建议迁移到配置表：

```text
plm_timeline_node_config

enabled_flag

```

迁移时保持接口 VO 不变，避免影响前端。

### 17.2 节点历史表

如果需要查看每个节点的确认人、确认时间、退回次数、退回原因列表，建议新增：

```text
plm_timeline_action
```

字段建议：

```text
action_id
product_id
node_key
step_no
action
from_step_no
to_step_no
reason
remark
operator_user_id
operator_user_name
request_id
created_at
```

`plm_operation_log` 保留为系统通用审计日志，`plm_timeline_action` 负责业务视图查询。

### 17.3 权限控制

M3 初期可以沿用 `allPermissions=true`。后续应按角色限制：

```text
工程部可以 confirm / advance / return。
非工程部只读或按节点授权。
发布和归档仍应走单独权限。
```

### 17.4 并发控制

如果多人同时推进同一项目，可能出现重复 confirm 或重复 advance。建议后续加入乐观锁：

```text
update plm_product
set current_step_no = current_step_no + 1
where product_id = ?
  and current_step_no = ?
  and timeline_current_confirmed = true
```

如果更新行数为 0，返回：

```text
项目时间轴状态已变化，请刷新后重试
```

### 17.5 资料门禁

后续可以在 advance 前增加节点资料检查：

```text
设计确认节点必须有设计文件。
开模试模节点必须有试模记录。
小批量 MX 验证节点必须有验证报告。
```

M3 第一阶段先不强制资料门禁，避免阻塞核心推进闭环。
