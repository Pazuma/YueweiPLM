# PLM 钉钉方案 A 新增出站中转接口实施沉淀

日期：2026-07-29

## 1. 目标效果

本次按方案 A 在 PLM 后端新增钉钉出站中转接口，解决钉钉连接器调用 `/api/dingtalk/outbound` 时返回 404 的问题。

实施后目标链路为：

```text
PLM 项目完成对应节点
-> PLM 触发出站回传
-> 调用 PLM 出站中转接口
-> 中转接口按 action 返回结构化结果
-> 后续接入钉钉官方 API 后执行代同意或抄送
```

其中：

- 新型号线：PLM 流程到 `MODEL_VARIANT_MOLD_TRANSFER` 运模节点后触发 `agree`。
- 新产品线：PLM 流程到产品线最终节点后触发 `cc`。
- 当前阶段不伪造钉钉官方 API 成功；未接入官方 API 时返回 HTTP 200 + `data.status=failed`，便于钉钉连接器通过 HTTP 出参校验，同时让 PLM 记录业务失败。

## 3. 接口说明

### 正式路径

```http
POST /api/v1/integrations/dingtalk/outbound
```

### 兼容路径

```http
POST /api/dingtalk/outbound
```

### 鉴权

接口路径在 Spring Security 和 `SimpleTokenAuthenticationFilter` 中放行，避免被 PLM 登录态拦截。

Controller 内部复用 `plm.integrations.dingtalk.callback-token`：

- 未配置 token：允许调用，方便本地和联调环境。
- 已配置 token：请求头必须为 `Authorization: Bearer ${callback-token}`。

### 请求体示例


## 4. 代码逻辑

`DingTalkOutboundRelayController`：

- 接收两个路径的 POST 请求。
- 校验 `Authorization` 是否匹配 `callbackToken`。
- 返回统一 `ResponseVO.success(data)`。

`DingTalkOutboundRelayService`：

- `workflow-task-lookup`：如果请求体已有 `taskId`，返回 `success`；否则返回 `DINGTALK_TASK_LOOKUP_NOT_IMPLEMENTED`。
- `agree`：校验 `approvalInstanceId/taskId/actionerUserId`；参数完整但官方 API 未接入时返回 `DINGTALK_AGREE_NOT_IMPLEMENTED`。
- `cc`：校验 `receiverUserIds`；参数完整但官方 API 未接入时返回 `DINGTALK_CC_NOT_IMPLEMENTED`。
- 未知 action 返回 `DINGTALK_ACTION_UNSUPPORTED`。

`DingTalkOutboundApprovalClient`：

- 原来只从响应根节点解析 `status/taskId`。
- 现在优先从统一响应的 `data` 节点解析，再回退到根节点，兼容 PLM 标准响应和外部服务裸响应。

`DingTalkProjectCompletionReturnService`：

- 如果中转接口返回 `externalStatus=failed`，出站记录 `processingStatus` 标记为 `failed`。
- 避免 HTTP 200 但业务失败时被 PLM 错记为成功。

## 5. 好处

- 解决当前钉钉连接器访问 `/api/dingtalk/outbound` 的 404。
- 钉钉连接器可拿到 HTTP 200，减少“出参校验不通过”的干扰。
- PLM 不会把未真正完成的钉钉代同意/抄送误记为成功。
- 后续接入钉钉官方 API 时，只需替换 `DingTalkOutboundRelayService` 中对应 action 的实现。
- 新型号线和新产品线共用同一个中转入口，便于日志排查和维护。

## 7. 前端/联调测试方法

### 方式一：钉钉连接器调试

请求地址建议配置：

```text
https://你的公网域名/api/v1/integrations/dingtalk/outbound
```

如果钉钉页面已经配置了旧地址，也可临时使用：

```text
https://你的公网域名/api/dingtalk/outbound
```

请求头：

```http
Authorization: Bearer dev-token
Content-Type: application/json
```

其中 `dev-token` 需要和服务端 `plm.integrations.dingtalk.callback-token` / `DINGTALK_CALLBACK_TOKEN` 保持一致。

### 方式二：本地 curl 验证

```bash
curl -X POST "http://localhost:8080/api/v1/integrations/dingtalk/outbound" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer dev-token" \
  -d '{"action":"agree","approvalInstanceId":"ding-instance-001","taskId":"ding-task-001","actionerUserId":"02356802443226388318"}'
```

当前未接入钉钉官方 API 时，预期返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "failed",
    "action": "agree",
    "externalStatus": "failed",
    "errorCode": "DINGTALK_AGREE_NOT_IMPLEMENTED"
  }
}
```

## 8. 后续维护建议

1. 接入钉钉官方审批任务查询 API 后，替换 `workflow-task-lookup` 的未实现返回，并返回真实 `taskId`。
2. 接入钉钉官方审批同意 API 后，替换 `agree` 的未实现返回，成功时返回 `status=success`。
3. 接入钉钉工作通知或抄送 API 后，替换 `cc` 的未实现返回。
4. 生产环境必须配置固定 `DINGTALK_CALLBACK_TOKEN`，钉钉连接器请求头保持一致。
5. 保留 `/api/dingtalk/outbound` 一段时间用于兼容，后续统一迁移到 `/api/v1/integrations/dingtalk/outbound`。
6. 排查问题优先看 `integration_record` 的 outbound 记录、`processing_status`、`external_status`、`error_message`。
