# PLM 假数据清理与项目全流程验收实施前沉淀

日期：2026-07-15

## 1. 背景和目标

本次先生成实施前沉淀文档，不修改前端或后端业务代码。

用户目标是：先把运行时假数据清理掉，再完整跑一遍 PLM 项目流程。这里的“完整流程”优先按当前已实现的项目研发闭环理解，即：

1. 登录系统。
2. 工作台查看进行中项目。
3. 工作台或项目中心确认当前时间轴节点。
4. 推动项目进入下一节点。
5. 上传当前节点资料。
6. 在项目中心、文件中心、BOM、工艺路线、发布门禁等模块查看同一份后端沉淀数据。

核心原则：后端是唯一真实数据源。前端不能再用静态数组、`mockResolve`、本地临时状态伪造核心业务结论。

## 3. 清理边界

### 3.1 必须清理或隔离的范围

- 前端运行时业务假数据。
- 前端 API 模块中直接返回 `mockResolve` 的模块。
- 页面上明确标注“前端假数据演示”“仅前端假数据”的业务入口。
- 会影响项目全流程判断的静态项目、静态废弃项目、静态 BOM/工艺/文件/审批数据。

### 3.2 暂不应直接删除的范围

- `__tests__` 下的 Vitest mock、测试桩、测试 fixtures。这些是自动化测试隔离依赖，不属于运行时假数据。
- 后端单元测试里的 Mockito mock。这些只用于服务层和控制器测试，不会进入运行时。
- Flyway 中的最小登录种子用户 `engineer01`、`engineer02`。当前本地 MVP 登录依赖它们，除非先补齐真实用户管理和初始化流程。
- 仍没有真实后端接口支撑的模块页面。不能直接删除依赖导致页面崩溃，应先从 MVP 导航隔离或显式标记为“未纳入本轮全流程验收”。

### 3.3 不建议“一把删除 src/mock”

当前 `src/mock` 被多个运行时模块直接引用。如果直接删除，会导致前端编译失败或页面空白。正确顺序应是：

1. 先保证项目全流程 MVP 路径全走后端。
2. 再把非 MVP 的 mock 模块从导航或验收范围隔离。
3. 最后逐模块替换 API，并删除对应 mock 依赖。

## 6. 推荐实施方案

### 阶段一：保护项目全流程 MVP

目标：先让用户完整跑一条真实项目流程，不被其他模块假数据干扰。

建议动作：

1. 确认前端运行配置指向后端 `http://localhost:8080`。
2. 确认登录使用后端种子账号 `engineer01 / plm123456`。
3. 工作台和项目中心只展示后端进行中项目、时间轴、附件、BOM、工艺、发布门禁。
4. 废弃项目视图移除或替换 hardcoded 数据。
5. 对未接真实后端的模块，在本轮 MVP 导航或验收清单中标记为“未纳入全流程”。

通过标准：

- 不出现“前端假数据演示”“仅前端假数据”作为真实验收入口。
- 推动节点后，刷新页面仍能从后端看到节点变化。
- 上传资料后，刷新文件中心仍能看到附件。
- BOM 冻结、工艺锁定后，发布门禁状态来自后端重新计算。

### 阶段二：API 模块去 mock 化

目标：运行时 API 层不再直接返回本地 mock。

建议顺序：

1. `product.ts`：优先处理，因为产品/项目是主线对象。
2. `foundation.ts`：拆分“字典/配置”和“业务数据”，业务数据接后端。
3. `bom.ts`：保留真实项目级接口，替换 BOM 中心总览 mock。
4. `process.ts`：保留真实项目级接口，替换工艺中心总览 mock。
5. `approval.ts`：未补后端前先隔离审批流，不伪造审批通过。
6. `customer.ts`、`supplier.ts`、`system.ts`：逐模块补后端后再打开导航验收。

通过标准：

- `src/api/modules` 中生产 API 不再导入 `@/mock/*`。
- `mockResolve` 不再被运行时业务模块调用。
- 无后端接口时返回明确错误或空状态，不用假数据填充。

### 阶段三：清理 `src/mock` 运行时依赖

目标：`src/mock` 只保留测试或开发样例，不参与生产运行。

建议动作：

1. 先用 `rg "@/mock|mockResolve" plm-web/src -n` 做门禁扫描。
2. 每迁移一个模块，就删除对应运行时 mock import。
3. 如果仍需测试数据，迁移到 `__tests__/fixtures` 或测试文件内部。
4. 删除 `src/mock` 前必须跑 `type-check` 和页面 smoke test。

通过标准：

- `plm-web/src` 的非测试代码不再引用 `@/mock`。
- 测试仍可通过本地 fixtures 隔离。

### 阶段四：全流程验收

目标：用户可以按同一项目从工作台跑到模块查看。

验收路径：

1. 打开前端：`http://localhost:5173`。
2. 后端服务：`http://localhost:8080`。
3. 登录：`engineer01 / plm123456`。
4. 进入工作台，选择一个进行中项目。
5. 打开项目进度弹窗，读取真实时间轴。
6. 确认当前节点。
7. 推动到下一节点。
8. 上传当前节点附件。
9. 刷新工作台，确认当前节点变化仍存在。
10. 进入项目中心，确认时间轴与工作台一致。
11. 进入文件中心，按项目 ID 或节点筛选附件。
12. 在项目中心维护 BOM 并冻结。
13. 在项目中心维护工艺路线并锁定。
14. 检查发布门禁，确认缺失项随真实数据变化。

## 7. 最小 MVP 当前判断

| 范围 | 当前判断 | 原因 |
| --- | --- | --- |
| 工作台读取进行中项目 | 基础可跑 | 前端已接 `getWorkbenchInProgressProjects`。 |
| 时间轴确认/推进/退回 | 基础可跑 | 前端项目中心和工作台已接真实后端接口，但要保证节点 key 是当前节点。 |
| 附件上传和文件中心 | 基础可跑 | 后端已有时间轴附件和文件中心接口，需用真实项目和真实 token 验证。 |
| 项目级 BOM | 基础可跑 | 项目级 BOM API 已是真实接口。 |
| 项目级工艺路线 | 基础可跑 | 项目级工艺 API 已是真实接口。 |
| 发布门禁 | 基础可跑 | M5 门禁逻辑已存在，但依赖真实 BOM、工艺、附件状态。 |
| 产品中心、客户、供应商、审批、系统管理 | 不能作为真实 MVP 验收 | 当前仍存在运行时 mock 或后端闭环不足。 |
| 企业级完整 PLM | 暂不满足 | RBAC、全模块后端闭环、对象存储、Docker 一键运行、OpenAPI、审计覆盖仍需补齐。 |

结论：可以先跑“项目研发窄口 MVP”，但不能把所有菜单都当作真实企业级 PLM 验收。

## 8. 实施风险

1. 直接删除 `src/mock` 会造成编译失败。
2. 删除后端种子用户会导致当前登录验收不可用。
3. 隐藏或隔离未接后端模块，会让菜单看起来变少，但这是避免假通过的必要边界。
4. 空状态必须和错误状态区分。后端返回失败时不能在前端用空数组伪装。
5. 如果数据库里没有可用项目，工作台真实返回空列表是合法结果，但这时应先创建或准备一条真实项目数据。
6. 当前用户本地已存在上传文件和运行日志，不能自动删除。

## 9. 后续维护建议

1. 建立“运行时禁止 mock”扫描门禁：
   ```powershell
   rg "@/mock|mockResolve" src -n
   ```
   允许范围只应包含 `__tests__`、测试 fixtures 或明确的开发样例。

2. 为每个模块增加数据源说明：
   - `real-backend`：已接真实后端，可纳入验收。
   - `mock-only`：仅前端演示，不纳入验收。
   - `mixed`：项目级真实、中心总览仍 mock，需要继续拆分。

3. 项目全流程优先维护同一条主线：
   ```text
   工作台动作 -> 后端项目/时间轴/附件/BOM/工艺 -> 项目中心和模块重新读取
   ```

4. 清理完成后补一条浏览器端到端验收：
   ```text
   登录 -> 工作台确认节点 -> 推进节点 -> 上传资料 -> 项目中心一致 -> 文件中心可见 -> 门禁变化
   ```

5. 新增模块时禁止先写假数据“顶页面”。如果后端未实现，应显示真实空状态或“模块未接入”，不要伪造业务结果。

## 10. 下一步建议

建议下一步不要直接全量删除，而是按下面顺序实施：

1. 先处理 `ProjectCenterView.vue` 的 hardcoded `abandonedProjects`。
2. 再把 MVP 导航中仍标注“前端假数据”的入口隔离或降级。
3. 然后逐个替换 `product.ts`、`foundation.ts`、`bom.ts`、`process.ts` 的运行时 mock。
4. 最后删除不再被运行时引用的 `src/mock` 文件。

本轮文档仅完成实施前沉淀，未执行代码清理，未删除任何数据或文件。
