# 2026-07-18 PLM 产品工艺路线弹窗字段与节点名称可读性方案沉淀

## 1. 本次任务

根据前端实际测试反馈，对“项目中心/工作台 - 新建工艺路线”弹窗做方案沉淀，本次只沉淀方案，不修改业务代码。

用户反馈点：

1. 产品下的工艺路线名称应以产品工艺路线本身为主，不需要在弹窗中维护“适用型号”。
2. 颜色后续应进入“系统管理 - 编码管理”，维护颜色名称和颜色编码；工艺路线弹窗到时候从编码管理选择颜色。
3. 工序明细区域每一列需要明确标题，用户要知道每个框填写的是什么。
4. 节点配置核对表里的“前置节点”和“后置节点”不要显示编码，要显示工序名称。
5. 本次只涉及前端体验和展示优化，不涉及后端业务逻辑改动。

## 3. 当前问题定位

### 3.1 路线表头字段

当前 `routeForm` 中包含：

```ts
applicableModel: '',
applicableColor: '',
```

弹窗中也有：

```vue
<el-form-item label="适用型号">
  <el-input v-model="routeForm.applicableModel" maxlength="100" placeholder="可选" />
</el-form-item>
<el-form-item label="适用颜色">
  <el-input v-model="routeForm.applicableColor" maxlength="100" placeholder="可选" />
</el-form-item>
```

问题：

1. 现在讨论的是产品工艺路线，不是 SKU/具体型号路线，“适用型号”会让用户误以为一条路线绑定某个型号。
2. 颜色后续要走编码管理，当前自由输入容易产生“黑色/雅黑/BLK/black”等不一致数据。

### 3.2 工序明细区域

当前工序编辑行直接排列控件：

```vue
<div v-for="(operation, index) in routeForm.operations" class="operation-row">
  <el-input-number v-model="operation.sequenceNo" />
  <el-input v-model="operation.operationCode" />
  <el-select v-model="operation.operationMasterProcessId" />
  <el-input-number v-model="operation.standardTimeMins" />
  <el-input v-model="operation.processParamJson" />
  <el-input v-model="operation.qualityRequirement" />
</div>
```

问题：

1. 用户只能靠占位符猜测字段含义。
2. 一旦字段内容较长，用户不知道“第 2 列是编码还是名称”、“JSON 是参数还是备注”。
3. 企业级录入界面需要稳定表头，避免培训成本和误填。

### 3.3 节点配置核对表

当前 `buildNodeCheckRows` 使用前后相邻工序的编码：

```ts
predecessorNodeCodes: index > 0 ? [sorted[index - 1].operationCode || `OP-${sorted[index - 1].sequenceNo}`] : [],
successorNodeCodes: index < sorted.length - 1 ? [sorted[index + 1].operationCode || `OP-${sorted[index + 1].sequenceNo}`] : [],
```

问题：

1. `PROC_TRIMMING`、`PROC_ASSEMBLY` 对业务用户不直观。
2. 用户确认节点关系时，想看到的是“注塑成型 -> 修边去披锋 -> 组装”，不是编码链路。

## 4. 方案口径

### 4.1 推荐方案

采用“前端展示与录入口径优化，不改后端合同”的方式：

1. 弹窗去掉“适用型号”字段。
2. “适用颜色”本次不继续自由输入；如果后端字段仍存在，前端暂时不展示，后续接入系统管理编码管理后改为下拉选择。
3. 工艺路线名称保留用户可编辑，但默认由路线模板名称带出，例如“标准注塑组装路线”。
4. 工序明细增加一行固定表头，列名清楚写明：顺序、工序编码、工序名称、标准工时、工艺参数、质量要求、操作。
5. 节点核对表保留工序编码列，但“前置节点/后置节点”展示工序名称。
6. 保存 payload 暂时不强传 `applicableModel/applicableColor`，避免把不规范自由文本写进后端。

### 4.2 为什么不改后端

1. 后端 `ProcessRouteSaveDTO` 可能仍支持 `applicableModel/applicableColor`，保留兼容不会影响旧数据。
2. 颜色编码管理属于系统管理能力，需要独立设计编码类型、颜色编码、状态、权限和引用校验，不应混在本次弹窗可读性优化里。
3. 本次用户明确要求只生成方案文档，不修改业务代码。

### 6.3 前后置节点显示名称

调整接口类型：

```ts
interface NodeCheckRow {
  displayOrder: number
  operationCode: string
  operationName: string
  predecessorNodeNames: string[]
  successorNodeNames: string[]
  backendPersisted: boolean
}
```

调整构造逻辑：

```ts
function buildNodeCheckRows(operations: ProcessOperationSavePayload[], persisted: boolean): NodeCheckRow[] {
  const sorted = [...operations].sort((left, right) => left.sequenceNo - right.sequenceNo)
  return sorted.map((operation, index) => ({
    displayOrder: index + 1,
    operationCode: operation.operationCode || `OP-${operation.sequenceNo}`,
    operationName: operation.processName,
    predecessorNodeNames: index > 0 ? [sorted[index - 1].processName || '上一道工序'] : [],
    successorNodeNames: index < sorted.length - 1 ? [sorted[index + 1].processName || '下一道工序'] : [],
    backendPersisted: persisted
  }))
}
```

调整表格展示：

```vue
<el-table-column label="前置节点" min-width="180">
  <template #default="{ row }">{{ row.predecessorNodeNames.join('、') || '--' }}</template>
</el-table-column>
<el-table-column label="后置节点" min-width="180">
  <template #default="{ row }">{{ row.successorNodeNames.join('、') || '--' }}</template>
</el-table-column>
```

目标展示：

```text
顺序  工序编码              工序名称    前置节点      后置节点
1     PROC_INJECTION       注塑成型    --            修边去披锋
2     PROC_TRIMMING        修边去披锋  注塑成型      组装
3     PROC_ASSEMBLY        组装        修边去披锋    成品检验
```

## 7. 目标效果

1. 新建工艺路线弹窗不再出现“适用型号”，减少产品级路线和型号/SKU 级路线混淆。
2. 颜色不再由用户自由输入，避免脏数据；后续统一从系统管理编码管理选择。
3. 工序明细区域有固定表头，用户能明确知道每个输入框含义。
4. 节点配置核对表用“注塑成型、修边去披锋、组装”等名称展示前后置节点，业务可读性明显提高。
5. 保留工序编码列用于追溯和技术核对，但不把编码作为用户判断流程关系的主要信息。
6. 前端改动不破坏现有后端接口兼容，不新增根对象，不绕过 Process 现有建模。

## 9. 风险点

1. 如果后端当前依赖 `applicableModel` 做编码或校验，去掉前端传参可能影响旧逻辑；实施前需要确认后端 `ProcessRouteServiceImpl.buildProcessCode` 只依赖 `productCode + templateCode + versionNo`。
2. 历史数据中可能已有 `applicableModel/applicableColor`，前端隐藏后不会删除后端旧数据，只是不再新增自由文本。
3. 颜色编码管理后续需要独立设计，不能只在本弹窗加一个静态颜色数组，否则仍会形成新的维护分叉。
4. 工序明细表头在窄屏下需要响应式处理，避免表头和输入行错位。

## 10. 后续维护建议

1. 系统管理编码管理应统一维护颜色编码，例如 `BLK=黑色`、`WHT=白色`、`RED=红色`，并提供启用/停用状态。
2. 工艺路线弹窗后续只引用已启用颜色编码，不允许手写颜色。
3. 如果未来确实要表达“产品 + 型号 + 颜色”的差异路线，应先确认是否进入 Product 子版本或后续 SKU 视图，不建议在当前产品级工艺路线弹窗里直接放回“适用型号”自由输入。
4. 节点核对表应坚持“业务名称优先、编码辅助追溯”的展示原则。
5. 前端测试用例可补充断言：页面不出现“适用型号”，节点前后置列不包含 `PROC_` 前缀。

## 11. 本次结论

本方案符合当前企业级前端使用要求：减少无效自由输入，降低用户理解成本，保留编码追溯能力，同时不新增后端对象、不改变现有 Process 建模。实施时建议优先修改 `ProjectProcessRoutePanel.vue`，完成后用前端直接测试验证弹窗字段、工序明细表头、节点名称展示和保存回显。
