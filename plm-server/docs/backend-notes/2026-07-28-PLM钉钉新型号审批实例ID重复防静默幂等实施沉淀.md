## 2. 问题背景

钉钉新型号审批提交后，PLM 没有创建新项目。排查发现后端返回过：

```json
{
  "projectId": 42,
  "dingTalkApprovalNo": "111",
  "idempotentHit": true
}
```

这说明后端把当前请求识别成历史审批实例 `111` 的重复回调，直接返回旧项目 42，没有进入新建项目逻辑。

原设计里，`approvalInstanceId` 是钉钉审批实例唯一标识，用它做幂等是正确的。但如果钉钉连接器把它错误配置成固定值，例如 `111`，后端原逻辑会静默命中旧项目，业务侧不容易发现配置错误。

## 3. 目标效果

保留正确幂等：

- 同一张钉钉审批重复回调，仍然返回历史项目，不重复创建。

阻止错误静默：

- 如果同一个 `approvalInstanceId` 已存在，但新请求的 `approvalNo`、来源产品、类型、型号或模具编码与历史记录不一致，后端返回 `40001` 业务校验错误。
- 错误消息明确提示检查 `approvalInstanceId` 是否被配置为固定值。
- 不创建新项目，也不误返回旧项目。

预期错误示例：

```json
{
  "code": 40001,
  "message": "钉钉审批实例ID重复但审批内容不一致，请检查 approvalInstanceId 是否被配置为固定值: 111"
}
```

## 5. 核心代码逻辑

### 5.1 原幂等入口

新型号入站时仍然先按钉钉审批实例查询历史记录：

```java
IntegrationRecord existing = first(integrationRepository.selectList(new LambdaQueryWrapper<IntegrationRecord>()
    .eq(IntegrationRecord::getSourceSystem, "dingtalk")
    .eq(IntegrationRecord::getIntegrationType, "model_variant")
    .eq(IntegrationRecord::getExternalInstanceId, externalInstanceId(dto))
    .eq(IntegrationRecord::getDeletedFlag, 0)));
```

### 5.2 新增一致性校验

命中历史记录后，不再直接返回，而是先检查是否真的是同一张审批：

```java
if (existing != null) {
    ensureSameApprovalCallback(existing, dto);
    return result(existing, true);
}
```

校验字段：

- `approvalNo / dingTalkApprovalNo`
- `parentProductId / parent_product_id / 来源产品ID / 父产品ID`
- `tipo`
- `model`
- `moldCodes / generatedCode / 生成的编码 / 模具编码`

只要历史记录和当前请求都有值，且值不一致，就判定为疑似固定 `approvalInstanceId` 映射错误。

### 5.3 历史 payload 兼容

历史记录可能来自统一回调入口，也可能来自旧的直接新型号入口，所以代码同时兼容：

- 根字段：`approvalNo`、`dingTalkApprovalNo`、`model` 等。
- 表单字段：`form.approvalNo`、`form.model`、`form.generatedCode` 等。

如果旧数据没有 `source_payload_json`，为了兼容历史记录，仍按旧逻辑幂等返回。

## 6. 好处

1. 不破坏正确幂等，重复回调仍不会重复建项目。
2. 钉钉连接器字段配错时，后端返回明确错误，不再悄悄返回旧项目。
3. 排查成本降低，看到错误消息就能定位到 `approvalInstanceId` 映射问题。
4. 不新增表、不改 API、不影响前端页面，改动范围小。
5. 保持 `Product` 作为新型号项目载体，不新增根对象，符合 PLM 现有对象边界。

## 8. 前端和钉钉测试方法

### 8.1 正常新建测试

钉钉连接器提交一张新审批，确保：

```text
approvalInstanceId = 当前审批实例ID动态变量
approvalNo = 当前审批编号动态变量
processCode = PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C
```

预期：

```json
{
  "idempotentHit": false,
  "status": "success"
}
```

PLM 前端项目中心能看到新型号项目。

### 8.2 重复回调测试

用同一张审批再次触发连接器，字段内容保持一致。

预期：

```json
{
  "idempotentHit": true
}
```

PLM 不重复创建项目。

### 8.3 固定值错误测试

故意把第二张审批的 `approvalInstanceId` 配成历史值，例如 `111`，但 `approvalNo` 或型号不同。

预期：

```json
{
  "code": 40001,
  "message": "钉钉审批实例ID重复但审批内容不一致，请检查 approvalInstanceId 是否被配置为固定值: 111"
}
```

PLM 不创建项目，也不返回旧项目。

## 9. 后续维护建议

1. 钉钉连接器里 `approvalInstanceId` 必须使用“审批实例ID/流程实例ID”动态变量，不能手写固定值。
2. 如果业务人员看到 `approvalInstanceId重复但审批内容不一致`，优先检查钉钉连接器字段映射。
3. 后续可以在 PLM 后台增加“钉钉集成记录查询页”，展示审批实例 ID、审批编号、项目 ID、幂等命中状态和错误消息。
4. 后续如果接入更多钉钉流程，也建议复用这个模式：幂等命中后先校验关键业务字段是否一致。
5. 如果历史数据缺少 `source_payload_json`，后端无法判断是否配置错误，建议后续通过补偿脚本或管理页完善历史集成记录。
