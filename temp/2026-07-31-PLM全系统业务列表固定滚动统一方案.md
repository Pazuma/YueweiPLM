# 2026-07-31 PLM 全系统业务列表固定滚动统一方案

## 1. 任务理解

PLM 前端中所有业务页面的主列表统一采用固定列表视口：表头固定、表体在列表范围内纵向滚动、横向滚动条始终位于该列表区域底部。列表数据增多时不再将整页拉长，宽表的横向滚动范围也不得延伸到页面级别。

截图红框中的“进行中项目”列表是首个落地场景，但统一规则应覆盖其它同类型业务列表；详情弹窗、导入预览、嵌入式明细表不强制使用相同高度策略。

本次只沉淀方案，不修改业务代码、接口、数据库、状态机、权限或业务数据。

## 2. 所属业务链路与范围

- 核心对象：Customer、Product、Order、ProductionOrder、Process、Inventory、Workstation 及其 PLM 资料明细。
- 前端范围：Vue 3 业务页面的主数据列表、项目列表、任务列表和台账列表。
- 统一目的：让用户在高频查找、筛选、比对和打开详情时，始终可见字段表头和横向滚动条，避免在大量记录后才找到滚动轨道。
- 不新增 SKU、BOM 等根对象，不改变对象关系、生命周期或原有审批流程。

## 3. 统一交互规范

### 3.1 主列表标准

以下表格定义为“业务主列表”，必须统一采用固定滚动：

1. 页面主体区域内用于浏览同类业务记录的主表格。
2. 表格记录可能随筛选、分页或历史数据增长而超过一屏。
3. 表格存在多列、固定操作列或需要横向查看字段。

标准效果：

- 列表拥有明确、稳定的视觉边界，横向滚动条只在该边界底部显示。
- `el-table` 使用受控 `height` 或 `max-height`，由组件内部提供表体纵向滚动和横向滚动。
- 表头固定在列表顶部；数据行滚动不影响表头。
- 固定左/右列、操作按钮、筛选结果、排序、分页和详情跳转保持既有行为。
- 页面整体只承担页面级内容切换，不承担某个宽表的横向滚动。

### 3.2 不纳入强制统一的表格

以下情况不直接复用主列表固定高度，改为按所在容器单独评估：

- 详情弹窗内的成本、供应商、质量、流程明细等短表。
- 导入预览、导出映射、审批表单和临时编辑弹窗中的表格。
- 产品详情、BOM 编辑器、附件清单、版本历史等与上方内容强耦合的嵌入式明细。
- 明确只有少量固定行、无需横向浏览的统计或说明表。

原因是这些表格受到弹窗高度、表单操作区或上下文内容约束；强行使用全局固定高度会产生双重纵向滚动，压缩编辑空间。

## 5. 技术方案

### 5.1 可复用主列表容器

新增或复用一个前端布局组件/组合式能力，例如 `FixedTableViewport` 或 `useFixedTableHeight`，统一负责：

- 接收表格实例、页面内容区域引用和高度预留参数。
- 计算可用高度：可视区域高度减去该页面筛选栏、标题、工具栏、分页栏等同页面元素的实际占用高度。
- 提供 `min-height`、`max-height` 和当前表格高度，避免单一硬编码屏幕高度。
- 在窗口尺寸、侧栏宽度、筛选条件、页签、折叠区、数据加载和分页变化后，于 `nextTick` 调用 `table.doLayout()`。
- 在组件卸载时清除监听；如使用 `ResizeObserver`，同时断开观察对象。

页面通过统一的 CSS 类提供边界、滚动条空间和小屏样式，避免每个页面复制不同的 `overflow` 规则。

### 5.2 Element Plus 表格约束

- 业务主列表优先将计算高度传给 `el-table` 的 `height`；表头、表体、横向滚动轨道均由 Element Plus 维护。
- 当页面需要让短数据表自然收缩时，允许使用 `max-height`，但横向滚动条仍必须在该表格底部。
- 禁止在 `el-table` 外层再叠加无边界的 `overflow: auto`，防止双滚动条、固定列错位和滚动条落到页面最下方。
- 使用局部 `:deep()` 样式检查横向滚动条未被面板 `overflow: hidden` 裁切，并在表格底部保留轨道空间。

### 5.3 高度分级

按页面结构分为三种模式：

| 模式 | 使用场景 | 高度策略 |
| --- | --- | --- |
| 标准主列表 | 产品、订单、客户、库存、项目“全部/归档”等以列表为主体的页面 | 视口自适应固定高度，优先显示 8-12 行。 |
| 上方内容可变主列表 | 项目进行中视图含流程筛选、时间轴和节点提示 | 实测上方内容后计算余量，保留最小可用高度；截图红框属于此模式。 |
| 紧凑主列表 | 审批、系统配置、报表等同页工具栏或提示较多的页面 | 较小最小高度和较严格最大高度，优先不遮挡保存、分页和批量操作。 |

### 5.4 响应式与可访问性

- 桌面端固定列表区域优先保证横向滚动条常驻可见。
- 窄屏和 125% 缩放时，表格横向滚动仍局限在列表区域，禁止触发页面横向溢出。
- 不删除业务字段、不把主列表改为营销式卡片；固定列是否在极窄屏保留需按各页面操作需求确认。
- 键盘聚焦到表格内单元格、按钮和链接时，浏览器应能将焦点行滚入列表可视区；不以 CSS 覆盖原生滚动行为。

## 7. 验收标准

1. 上述每个业务页面的主列表在记录超过一屏时，页面不因数据行无限拉长。
2. 主列表纵向滚动时，表头固定在列表区域顶部。
3. 主列表横向滚动条始终位于该列表边界底部，用户滚到任意数据行时都可直接拖动。
4. 宽表不会制造页面级横向滚动条；固定操作列和详情/编辑操作可用。
5. 切换筛选、页签、分页、展开/收起工具区、调整窗口或侧栏后，列宽和滚动条正常刷新。
6. 弹窗、导入预览和详情内嵌短表不出现新增的双重滚动条或布局压缩。
7. 在 1920x1080、1440x900、1366x768、1024px 宽及浏览器 125% 缩放下完成手工验证。
8. 前端执行 `npm run type-check` 通过。

## 8. 风险与实施顺序

- 风险：逐页直接复制高度值会导致不同工具栏高度下内容被遮挡；必须采用公共计算逻辑和最小高度兜底。
- 风险：Element Plus 固定列、横向滚动条和外层裁切样式之间存在耦合，需逐页浏览器验证。
- 风险：一次改动全部表格会扩大回归范围；应先落地公共能力，再按“项目管理、产品、订单、工艺、库存、文件、审批、基础配置”的顺序批量接入并逐组验收。
- 风险：有分页的页面需确认分页栏位于列表视口内或表格下方；本次默认保持现有分页位置和请求逻辑。
